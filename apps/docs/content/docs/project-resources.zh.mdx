[專案](/projects)資源會告訴 Agent 這組工作會使用哪些程式碼，以及要在哪裡執行。資源會持續連結至專案，不必在每項任務中重複貼上儲存庫網址或本機路徑。

目前支援兩種資源：

| 資源 | 適用場景 | 執行位置 |
|---|---|---|
| **GitHub 儲存庫** | 團隊共享的程式碼庫，希望由執行時管理 checkout | 執行時管理的工作目錄 |
| **本地目錄** | 已經存在的 checkout、很大的儲存庫，或需要直接檢視本地改動 | 指定電腦上的原資料夾或獨立 worktree |

## 執行時如何使用資源

Agent 處理專案中的任務時，Multica 會將專案名稱、描述和資源清單加入執行脈絡，並在工作目錄寫入 `.multica/project/resources.json`。

工作區連結的儲存庫清單一定會包含在執行脈絡中。專案連結的儲存庫則會進一步指出這組工作使用的程式碼和預設 ref。

本地目錄只對繫結它的守護程序有效。執行所在的守護程序有匹配的本地目錄時，智慧體按 `in_place` 模式在原目錄工作，或按 `worktree` 模式在其獨立 worktree 中工作；其他電腦仍使用專案中的 GitHub 儲存庫或工作區儲存庫。

## 新增 GitHub 儲存庫

開啟專案，在 **資源 → 儲存庫** 中點選 **新增儲存庫**。搜尋已關聯到工作區的儲存庫，或貼上 Git URL。工作區儲存庫在 **設定 → 程式碼** 中維護；連線 GitHub 後，可在同一頁面透過 **從 GitHub 選擇** 匯入 App 已授權的儲存庫。

儲存庫不限定 GitHub：任何執行環境可以存取的 Git URL 都能作為儲存庫資源。自行託管的 Multica 也可以在 **設定 → 程式碼** 連結自行託管的 Forgejo、Gitea 或 GitLab，請參閱[自行託管 Git 代管服務](/vcs-integration)。

建立專案時，也可以直接從 **Repos** 選取儲存庫。一個專案可以連結多個 GitHub 儲存庫。

資源中的 `ref` 可以指定之後 checkout 預設使用的分支、tag 或 commit。`default_branch_hint` 只會提示 Agent 預設分支，不會強制切換分支。

## 新增本機目錄

只有 Desktop 提供新增本機目錄的介面，因為瀏覽器無法選取電腦上的資料夾。

<Callout type="warning">
**這是特殊情況下的選項，不要因為方便就選它。** `local_directory` 是給那些"不得不這麼開發"的人準備的，典型是一個 checkout 就幾十 GB 的遊戲專案，不可能每來一次執行就重新 clone 一份。

如果你的目錄只是一個能正常 clone 的普通 git 儲存庫，請用 `github_repo`：它預設走 worktree 模式，同一個儲存庫上的執行可以同時進行，數量不受限制。`local_directory` 預設同一時間只進行一次執行；如果這個目錄本身是 git 儲存庫，可以主動開啟 worktree 模式恢復併發（見[執行如何共享這個目錄](#執行如何共用這個目錄)）。拿不準時，先對照頁首的兩種資源。
</Callout>

預選只作用於你此刻正在關聯的目錄。之前關聯好的目錄仍然保持儲存時的模式，已有設定不會在你不知情時被切換。

目錄必須使用絕對路徑、已存在，而且目前的常駐程式必須能讀寫。系統會拒絕以下路徑：系統根目錄和磁碟根目錄（`/`、`C:\`）、使用者家目錄及其上層目錄（例如 `/Users`、`/home`、`/root`），以及 `/etc`、`/var`、`/tmp`、`/usr`、`/opt` 等系統目錄。如果選取的路徑是符號連結，系統會先解析實際路徑，再依相同規則重新檢查；序列鎖也會依實際路徑運作。

同一個專案在同一個常駐程式上最多隻能連結一個本機目錄。團隊成員可以在不同電腦上分別為同一專案連結各自的目錄。

<Callout type="warning">
在預設的 `in_place` 模式下，本地目錄不是隔離環境：Agent會直接看到並修改目前分支和未提交的檔案，Multica 也不會自動切換分支、stash、commit、push 或建立 PR。worktree 模式不一樣，見下面的[執行如何共享這個目錄](#執行如何共用這個目錄)。
</Callout>

## 執行如何共用這個目錄

本地目錄有兩種執行模式，按資源逐個設定。在資源面板裡可以直接切換，CLI 用 `--execution-mode`。Desktop 裡這兩種模式顯示為 **直接修改** 和 **並行執行**；API、CLI 和本頁其餘部分都使用識別符號。

<LocalDirModeDemo />

<Tabs items={["in_place（直接修改，默认）", "worktree（并行运行）"]}>
<Tab value="in_place（直接修改，默认）" id="in-place">

Agent 會直接在你的目錄中工作，同一時間只能執行一項工作。若兩次執行使用同一個實際目錄，後到的執行會進入 `waiting_local_directory`，等前一次釋放目錄後再繼續。不同路徑若透過符號連結指向同一目錄，也會依序執行。

等待期間不會修改目錄。你可以取消等待中的執行；否則它會持續等到目錄可用。

普通的非 git 目錄只能用這種模式：worktree 模式只面向 git 儲存庫。

</Tab>
<Tab value="worktree（并行运行）" id="worktree">

每次執行拿到你儲存庫的一個獨立 [git worktree](https://git-scm.com/docs/git-worktree)，建在runtime自己的工作區目錄裡。同一目錄上的執行併發執行，誰都不用排隊，也都不會寫你的工作副本。

這個目錄必須是至少有一次提交的 git 儲存庫；不滿足時執行會明確報錯，不會悄悄退回序列。

那臺機器上的runtime也必須實現了該模式。runtime在連線時會宣告這項能力，Multica 只看這個宣告，不看版本號：一個開發構建完全可能帶著看起來足夠新的版本號，卻沒有對應的實現。這個宣告會被檢查兩次。儲存資源時，只要那臺機器的runtime沒有宣告該能力，儲存就會被拒絕，並提示去升級那臺機器上的 App；每次執行被真正領取時，還會按領取它的runtime再檢查一次，所以資源儲存之後才降級的機器，其執行會被帶原因取消，不會悄悄在原目錄裡跑掉。選擇 `worktree` 就是在要求隔離，Multica 不會拿"直接改你的工作副本"來兜底。

Agent 會看到什麼、你會取得什麼：

<Accordions type="multiple">
<Accordion title="Agent從你眼前的狀態開始，不是從 HEAD 開始" id="starts-from-your-working-state">

你未提交的改動和未跟蹤的檔案會被回放進 worktree，所以它不會去 review 一份你已經不用的程式碼。你自己的工作副本、暫存區和 stash 列表都不會被動到。

如果這個狀態無法忠實還原，包括未跟蹤內容超出回放上限（2000 個檔案 / 200 MiB），執行會直接失敗，不會從一棵你認不出來的樹開始。通常的解決辦法是把還沒被忽略的構建產物加進 gitignore 或清理掉。

</Accordion>
<Accordion title="結果是你倉庫裡的一個分支" id="result-is-a-branch">

分支按任務而不是按每次執行來分：`agent/<agent>/<issue>`（chat 則是 `agent/<agent>/chat-<session>`）。本次執行的**詳情**面板裡會顯示分支名（可直接複製），也可以用 `git branch` 找到它。用 `git log` / `git diff` review，然後自己決定 merge 還是 cherry-pick，Multica 不會替你合併。

`<agent>` 由Agent名字得來：轉成小寫後只保留英文字母和數字，其餘字元換成 `-`，最長 30 個字元；名字裡沒有英文字母和數字時寫作 `agent`。所以"運營助手"處理 OPS-21 時，分支是 `agent/agent/ops-21`。`<issue>` 是小寫的任務編號。

中途失敗的執行同樣會報告它的分支：Agent的提交都在上面，沒提交的部分按[不會靜默丟東西](#nothing-is-silently-lost)裡的方式保留。

</Accordion>
<Accordion title="後續對話接著上一輪繼續" id="follow-ups-continue-the-branch">

同一個任務的下一條留言會重新 check out 這個分支，Agent站在自己剛交付的成果上繼續做，不會從 `HEAD` 重新開始、把上一輪的改動落在另一個分支上。只有你在上一輪之後改動的部分會被重放上去，其餘部分分支裡已經有了。把分支 merge 掉之後，下一輪又會從你的 `HEAD` 重新開始。

同一個任務上有兩次執行重疊時，後一個會從前一個的成果分叉到 `agent/<agent>/<issue>-<task>`，因為 git 規定一個分支只能有一棵 worktree。

</Accordion>
<Accordion title="提交到本地 HEAD 的改動和未提交的改動分開處理" id="committed-head-changes-stay-separate">

兩輪之間在本地做的 pull 或提交不會重放到任務分支上，需要時把這些提交明確 merge 進去。上一輪記下了未提交的改動時，要在新的 `HEAD` 上比較這些改動，需要 Git 2.40 或更高版本。

這些舊改動和新的已提交基線衝突時，runtime會記一條警告，只對受影響的路徑改用目前 `HEAD`；其他草稿照常增量比較。所以把其中一份草稿完成並提交，不會阻塞之後的執行，也不會把你沒動過的草稿再次拿去和Agent的成果比較。你目前的改動和Agent的成果之間若有衝突，仍然交給Agent解決。

</Accordion>
<Accordion title="你的改動和Agent的成果衝突時，由Agent來解決" id="conflicts-are-resolved-by-the-agent">

如果你重寫了Agent也重寫過的那幾行，git 無法判斷誰對，這一輪就會在一棵帶衝突的 worktree 上啟動，並被要求先把 merge 做完（在那棵 worktree 裡 `git status` 會列出未合併的檔案）。

只要還有檔案沒合完，這一輪就什麼都不交付：執行失敗、worktree 保留，下一輪會再次把同樣的改動送上來，你的修改不會被悄悄丟掉。

</Accordion>
<Accordion title="只有 Multica 自己的分支才會被續接" id="only-multica-branches-resume">

是否續接由歸屬記錄決定，跟分支名無關：記錄裡既寫了屬於哪個會話，也寫了這條分支當時停在哪個 commit。你自己建的、恰好叫 `agent/<agent>/<issue>` 的分支永遠不會被 check out、被追加提交，也不會被當成上一輪的成果讀取；已經不包含記錄中那個 commit 的分支同樣如此。所以把 Multica 的分支刪掉再自己建一條同名的，或者把它 force-move 到別的歷史上，都是安全的，執行會改用 `agent/<agent>/<issue>-<id>`。在已交付的分支上繼續提交則是正常用法，續接照常，你的提交下一輪就在那裡。

每條分支還會以一個屬於自己的 baseline commit 開頭，標記第一輪開始時的目錄狀態。後續正是靠這個 commit 辨認這條分支，`git diff <baseline>..<branch>` 也恰好就是Agent做的改動。

如果某一輪沒能記錄它的分支，比如中途失敗、記錄寫不進去，或者把 worktree reset 到了"把你的改動帶進分支的那個 commit"之前，這一輪會報失敗並保留 worktree，後續幾輪會另起一條分支，不去續接一條無法證明歸屬的分支。

</Accordion>
<Accordion title="不會靜默丟東西" id="nothing-is-silently-lost">

Agent留下的未提交改動不會隨 worktree 一起刪除，執行中途失敗時同樣如此。它們去哪裡，取決於Agent這次執行有沒有自己提交：

- **Agent沒有提交過：** 所有沒被 gitignore 的檔案都會提交到分支上。這次提交不會執行儲存庫的提交鉤子。
- **Agent自己提交過：** 只交付它的提交。沒提交的部分（生成的產物、臨時檔案、沒提交的修改）存到隱藏 ref `refs/multica/leftovers/<branch>/<task>` 下，不進分支。每次執行開始時都會把這條規則告訴Agent，所以自己提交的Agent決定交付哪些內容。

例外：一開始要先和你的本地改動完成 merge 的執行（見[衝突處理](#conflicts-are-resolved-by-the-agent)）會提交它留下的全部內容，因為這些未提交的改動裡有你的修改。

想看某次執行存下了什麼，用 `git for-each-ref refs/multica/leftovers` 列出這些 ref，再用 `git show --stat <ref>` 檢視。`git restore --source=<ref> -- <path>` 可以把某個檔案取回到你的工作目錄。

極少數情況下連這次提交或儲存都做不了，例如儲存庫開了 `commit.gpgSign` 而runtime拿不到簽名金鑰。這時 worktree 會被刻意保留，執行標記為失敗，在你儲存庫裡執行 `git worktree list` 就能看到存放這些改動的目錄。

</Accordion>
<Accordion title="沒有產生改動的執行不留下任何東西" id="no-changes-leave-nothing">

它的分支會被刪除，不會作為一個空條目留在 `git branch` 裡；但如果這是承載了之前幾輪成果的任務分支，它一定會保留。

</Accordion>
<Accordion title="留在你倉庫裡的分支和隱藏 ref" id="what-stays-in-your-repo">

worktree 位於runtime的工作區目錄內，會按[正常的清理週期](/daemon-runtimes#cleanup)回收。留在你儲存庫裡的有：分支；每條分支對應的一個隱藏 ref（在 `refs/multica/local-state/` 下），記錄這條分支歸誰所有、以及上次續接時你目錄裡的內容；以及Agent自己提交後又留下未提交改動的每次執行，各對應一個隱藏 ref（在 `refs/multica/leftovers/` 下）。

隱藏 ref 不會出現在 `git branch` 裡，可以用 `git for-each-ref refs/multica` 檢視。Multica 刪除分支時會一併刪掉它；你自己刪掉的分支所對應的 ref，會在下一次該儲存庫上有執行開始時被清理。也可以用 `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` 一次性清掉。

</Accordion>
</Accordions>

<Callout type="warn">
**自託管運維注意：** 該模式的隔離由服務端強制（儲存資源時檢查一次，runtime每次領取runtime再檢查一次），所以無論何時降級runtime都會被攔住。唯一攔不住的組合是：把服務端回滾到本功能之前的版本，同時還連著沒有實現該模式的runtime。舊服務端沒有這道門禁，而這樣的runtime會忽略 `execution_mode`、直接在原目錄裡執行。只要還存在 `worktree` 資源，就不要把服務端回滾到本版本之前，除非那些機器上的runtime全部升級到位。
</Callout>

</Tab>
</Tabs>

## 執行期間寫入的內容

除了 Agent 產生的程式碼變更，執行環境也可能在目錄中寫入目前 AI 程式開發工具需要的指引檔，以及 `.multica/project/resources.json`。若不希望這些檔案納入版本控制，請將它們加入 `.gitignore`。

Multica 清理執行環境時不會刪除連結的本機目錄。Agent 對該目錄所做的變更，和你在終端機直接執行 AI 程式開發工具所做的變更相同，都需要仔細檢查。

## 使用 CLI 管理資源

```bash
# 创建项目时关联仓库
multica project create \
 --title "Agent UX" \
 --repo https://github.com/multica-ai/multica

# 查看和添加资源
multica project resource list <project-id>
multica project resource add <project-id> \
 --type github_repo \
 --url https://github.com/multica-ai/multica \
 --ref main

# 关联指定守护进程上的本地目录
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id>

# 关联一个本地 git 仓库，并让每次运行在各自的 worktree 中并发执行
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id> \
 --execution-mode worktree

# 为已有的本地目录切换模式
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# 移除资源
multica project resource remove <project-id> <resource-id>
```

資源變更只會影響之後建立的執行，不會改寫已完成的執行紀錄。

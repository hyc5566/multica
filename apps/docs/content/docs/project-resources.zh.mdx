[專案](/projects)資源會告訴 Agent 這組工作會使用哪些程式碼，以及要在哪裡執行。資源會持續連結至專案，不必在每項任務中重複貼上儲存庫網址或本機路徑。

目前支援兩種資源：

| 資源 | 適用場景 | 執行位置 |
|---|---|---|
| **GitHub 儲存庫** | 團隊共用的程式碼庫，由執行環境管理 checkout | 執行環境管理的工作目錄 |
| **本機目錄** | 已存在的 checkout、大型儲存庫，或需要直接查看本機變更 | 指定電腦上的原始目錄 |

## 執行時如何使用資源

Agent 處理專案中的任務時，Multica 會將專案名稱、描述和資源清單加入執行脈絡，並在工作目錄寫入 `.multica/project/resources.json`。

工作區連結的儲存庫清單一定會包含在執行脈絡中。專案連結的儲存庫則會進一步指出這組工作使用的程式碼和預設 ref。

本機目錄只對與它連結的常駐程式有效。如果執行這項工作的常駐程式有相符的本機目錄，Agent 就會直接在該目錄工作；其他電腦仍會使用專案或工作區連結的 GitHub 儲存庫。

## 新增 GitHub 儲存庫

開啟專案，在 **資源** 中選擇"新增資源"。你可以選擇已連結至工作區的儲存庫，也可以貼上 Git URL。請在 **設定 → 程式碼** 管理工作區儲存庫；連結 GitHub 後，也可以在同一頁按 **從 GitHub 選取**，匯入 app 已授權的儲存庫。

儲存庫不限定 GitHub：任何執行環境可以存取的 Git URL 都能作為儲存庫資源。自行託管的 Multica 也可以在 **設定 → 程式碼** 連結自行託管的 Forgejo、Gitea 或 GitLab，請參閱[自行託管 Git 代管服務](/vcs-integration)。

建立專案時，也可以直接從 **Repos** 選取儲存庫。一個專案可以連結多個 GitHub 儲存庫。

資源中的 `ref` 可以指定之後 checkout 預設使用的分支、tag 或 commit。`default_branch_hint` 只會提示 Agent 預設分支，不會強制切換分支。

## 新增本機目錄

只有 Desktop 提供新增本機目錄的介面，因為瀏覽器無法選取電腦上的資料夾。

<Callout type="warning">
**這是特殊用途，不是比較方便的預設選項。** `local_directory` 適用於"只能這樣開發"的情況，例如 checkout 後就有數十 GB 的遊戲專案，不可能每次執行都重新 clone 一份。

如果你的目錄只是一般可正常 clone 的 Git 儲存庫，**請使用 `github_repo`**：它預設採用 worktree 模式，同一儲存庫可以讓多次執行同時進行。`local_directory` **預設一次只能執行一項工作**；如果這個目錄本身是 Git 儲存庫，可以啟用 worktree 模式，讓多次執行並行（請參閱下方"執行如何共用這個目錄"）。請先比較上方的兩種資源，再決定使用哪一種。
</Callout>


1. 確認 Desktop 的本機常駐程式在線。
2. 開啟專案的 **資源**，或在建立專案對話框中開啟 **本機目錄** 分頁；建立專案前也能先選取目錄。
3. 選擇"新增本機目錄"，再選取要使用的資料夾。
4. 選擇執行時如何使用該目錄：**原地**或**並行**。兩種模式的差異請參閱"執行如何共用這個目錄"。如果資料夾是 Git 儲存庫，而且該電腦上的執行環境支援隔離，Desktop 會預選**並行**；否則會預選**原地**。你可以當場變更，也可以之後在 **資源** 中點選目錄旁的鉛筆圖示修改。

預選只會套用到目前要連結的目錄。既有目錄會保留儲存時的模式，不會在你不知情時被切換。

目錄必須使用絕對路徑、已存在，而且目前的常駐程式必須能讀寫。系統會拒絕以下路徑：系統根目錄和磁碟根目錄（`/`、`C:\`）、使用者家目錄及其上層目錄（例如 `/Users`、`/home`、`/root`），以及 `/etc`、`/var`、`/tmp`、`/usr`、`/opt` 等系統目錄。如果選取的路徑是符號連結，系統會先解析實際路徑，再依相同規則重新檢查；序列鎖也會依實際路徑運作。

同一個專案在同一個常駐程式上最多只能連結一個本機目錄。團隊成員可以在不同電腦上分別為同一專案連結各自的目錄。

<Callout type="warning">
在預設的 `in_place` 模式下，本機目錄不是隔離環境：Agent 會直接看到並修改目前分支和未提交的檔案；Multica 不會自動切換分支、stash、commit、push 或建立 PR。worktree 模式會提供隔離，詳情請參閱下方"執行如何共用這個目錄"。
</Callout>

## 執行如何共用這個目錄

本機目錄有兩種執行模式，可針對每項資源分別設定。你可以在資源面板切換，也可以透過 CLI 的 `--execution-mode` 設定。Desktop 會將兩種模式顯示為**原地**和**並行**；API、CLI 和本頁其他內容則使用識別碼。

### `in_place`（預設）——"原地"

Agent 會直接在你的目錄中工作，同一時間只能執行一項工作。若兩次執行使用同一個實際目錄，後到的執行會進入 `waiting_local_directory`，等前一次釋放目錄後再繼續。不同路徑若透過符號連結指向同一目錄，也會依序執行。

等待期間不會修改目錄。你可以取消等待中的執行；否則它會持續等到目錄可用。

### `worktree` ——"並行"

每次執行都會取得儲存庫的一個獨立 [git worktree](https://git-scm.com/docs/git-worktree)，並建立在執行環境自己的工作區目錄中。**同一目錄上的多次執行可以並行，不必排隊**，也都不會修改你的工作副本。

目錄必須是至少有一次提交的 Git 儲存庫。若不符合條件，執行會明確報錯，不會悄悄改為依序執行。該電腦上的執行環境也必須支援此模式；執行環境連線時會宣告支援能力，Multica 會檢查宣告內容，而不是版本號。開發版可能帶有看似夠新的版本號，實際上卻沒有對應功能。系統會檢查兩次：儲存資源時，若執行環境未宣告支援，系統會拒絕儲存並提示升級該電腦上的 App；每次執行真正被領取時，也會由領取它的執行環境再次檢查。因此，若資源儲存後才降級，執行會附上原因並取消，不會悄悄在原目錄執行。選擇 `worktree` 就表示要求隔離；直接修改工作副本永遠不是替代方式。

Agent 會看到什麼、你會取得什麼：

- **Agent 會從你目前的工作狀態開始，而不是從 `HEAD` 開始。** 未提交的變更和未追蹤檔案會重建到 worktree 中，避免 Agent 檢查你已不再使用的程式碼。你的工作副本、暫存區和 stash 清單都不會被動到。如果狀態無法忠實還原（包括未追蹤內容超過 2,000 個檔案或 200 MiB 的上限），執行會直接失敗，不會從不完整的目錄開始。通常可將尚未忽略的建置產物加入 gitignore，或將它們清除。
- **結果會存成儲存庫中的一個分支**，以任務而非單次執行為單位：`agent/<agent>/<issue>`（Chat 則使用 `agent/<agent>/chat-<session>`）。本次執行的**詳細資訊**面板會顯示分支名稱，可直接複製；也可以用 `git branch` 查找。請使用 `git log`／`git diff` 檢視，再自行決定要 merge 或 cherry-pick。Multica 不會代為合併。即使執行中途失敗，也會回報分支，因為 Agent 已提交完成的部分變更。
- **後續留言會接續前一次執行。** 同一任務的下一則留言會重新 checkout 這個分支，讓 Agent 接著前次交付成果繼續工作，而不是從 `HEAD` 開始並把前次變更放到另一個分支。只有你在前次執行後所做的變更會重放到分支上，其他變更已包含在分支中。合併分支後，下一次執行會重新從你的 `HEAD` 開始。同一任務的兩次執行若重疊，後一次會從前一次成果分支出 `agent/<agent>/<issue>-<task>`；這是因為 Git 規定一個分支只能對應一個 worktree。
- **本機 `HEAD` 中已提交的更新，與未提交的編輯分開處理。** 兩次執行之間的 pull 或本機 commit 不會自動重放到任務分支；需要時，請明確將那些 commit 合併進去。如果前次執行曾擷取未提交的工作，要在新的 `HEAD` 上比較這些內容，需要 Git 2.40 或更新版本。若舊編輯與新的已提交基準衝突，執行環境會記錄警告，並只對受影響的路徑改用目前的 `HEAD`；其他草稿仍會做增量比較。因此，完成並提交其中一份草稿，不會阻擋後續執行，也不會把未變更的其他草稿重新套用到 Agent 的成果上。你目前的編輯若與 Agent 的成果衝突，仍會交由 Agent 處理。
- **你的變更和 Agent 的成果衝突時，由 Agent 處理衝突。** 如果你修改了 Agent 也改過的同一行，Git 無法判定哪一方正確，這次執行就會在有衝突的 worktree 中開始，並要求先完成 merge（該 worktree 中的 `git status` 會列出未合併檔案）。只要還有檔案未合併，執行就不會交付任何結果：執行會失敗、worktree 會保留，下一次執行會再次帶入相同變更，因此你的修改不會被悄悄丟棄。
- **只有 Multica 建立的分支會被接續使用。** 系統依據歸屬紀錄判斷是否接續，不會只看分支名稱：紀錄會標示所屬工作階段，以及該分支當時停留的 commit。你自行建立、剛好命名為 `agent/<agent>/<issue>` 的分支，不會被 checkout、追加 commit 或當作前次成果讀取；若分支已不包含紀錄中的 commit，也不會接續。因此，刪除 Multica 的分支後自行建立同名分支，或將該分支 force-move 到其他歷史，都不會被誤用；執行會改用 `agent/<agent>/<issue>-<id>`。在已交付分支上繼續 commit 則是正常用法，後續執行會照常接續並包含你的提交。每個分支也會以專屬 baseline commit 標記第一輪開始時的目錄狀態；後續會依此辨識分支，而 `git diff <baseline>..<branch>` 剛好會列出 Agent 的變更。如果某次執行未能記錄分支（例如中途失敗、無法寫入紀錄，或 worktree 被 reset 到帶入你變更的 commit 之前），執行會失敗並保留 worktree；之後會建立新分支，不會接續無法證明歸屬的分支。
- **不會默默丟失變更。** Agent 留下的未提交變更會在移除 worktree 前提交到該分支，**執行中途失敗時也一樣**。極少數情況下無法完成提交，例如儲存庫啟用了 `commit.gpgSign`，但執行環境無法取得簽章金鑰；這時 worktree 會刻意保留而不刪除，執行會標記為失敗。你可以在儲存庫執行 `git worktree list`，找到保留變更的目錄。
- **沒有產生變更的執行不會留下額外內容。** 對應分支會刪除，不會以空分支留在 `git branch` 中；但若任務分支已包含前幾次執行的成果，就會保留。

worktree 位於執行環境的工作區目錄中，會依一般清理週期回收。你的儲存庫會保留兩種項目：分支，以及每個分支對應的隱藏 ref（位於 `refs/multica/local-state/`），其中記錄分支擁有者和上次接續時目錄的內容。隱藏 ref 不會出現在 `git branch`，可用 `git for-each-ref refs/multica` 查看。Multica 刪除分支時也會移除對應 ref；你手動刪除分支後，該 ref 會在下次此儲存庫開始執行時清理。你也可以使用 `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` 一次清除。

<Callout type="warn">
**自行託管維運注意：** 此模式由伺服器強制執行隔離（儲存資源時檢查一次，每次執行環境領取工作時再檢查一次），因此執行環境降級時會被擋下。唯一無法阻擋的情況是：伺服器回復到不支援此功能的版本，同時仍連線著不支援此模式的執行環境。舊版伺服器沒有這項檢查，而這類執行環境會忽略 `execution_mode`，直接在原目錄工作。只要仍有 `worktree` 資源，就不要將伺服器回復到加入此功能前的版本，除非所有相關電腦上的執行環境都已升級。
</Callout>

<Callout type="info">
worktree 模式適用於 Git 儲存庫。一般非 Git 目錄仍會依序執行，這正是 `in_place` 的用途。
</Callout>

## 執行期間寫入的內容

除了 Agent 產生的程式碼變更，執行環境也可能在目錄中寫入目前 AI 程式開發工具需要的指引檔，以及 `.multica/project/resources.json`。若不希望這些檔案納入版本控制，請將它們加入 `.gitignore`。

Multica 清理執行環境時不會刪除連結的本機目錄。Agent 對該目錄所做的變更，和你在終端機直接執行 AI 程式開發工具所做的變更相同，都需要仔細檢查。

## 使用 CLI 管理資源

```bash
# 建立專案時連結儲存庫
multica project create \
 --title "Agent UX" \
 --repo https://github.com/multica-ai/multica

# 檢視和新增資源
multica project resource list <project-id>
multica project resource add <project-id> \
 --type github_repo \
 --url https://github.com/multica-ai/multica \
 --ref main

# 連結指定常駐程式上的本機目錄
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id>

# 連結本機 Git 儲存庫，讓每次執行都在自己的 worktree 中並行進行
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id> \
 --execution-mode worktree

# 為現有本機目錄切換模式
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# 移除資源
multica project resource remove <project-id> <resource-id>
```

資源變更只會影響之後建立的執行，不會改寫已完成的執行紀錄。

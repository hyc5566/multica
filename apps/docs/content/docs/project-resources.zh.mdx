[專案](/projects)資源告訴 Agent 這組工作會用到哪些程式碼，以及在哪裡執行。資源會持續關聯在專案上，不必在每條任務中重複粘貼倉庫地址或本地路徑。

目前支援兩種資源：

| 資源 | 適用場景 | 執行位置 |
|---|---|---|
| **GitHub 倉庫** | 團隊共享的程式碼庫，希望由執行環境管理 checkout | 執行環境管理的工作目錄 |
| **本地目錄** | 已經存在的 checkout、很大的倉庫，或需要直接查看本地改動 | 指定電腦上的原目錄 |

## 資源進入執行的方式

當 Agent 處理專案內的任務時，Multica 會把專案名稱、專案描述和資源列表加入執行上下文，並在工作目錄中寫入 `.multica/project/resources.json`。

工作區關聯的倉庫列表始終包含在執行上下文中。專案關聯的倉庫在此基礎上指明這組工作使用的程式碼和預設 ref。

本地目錄只對綁定它的守護程序有效。本次執行所在的守護程序有匹配的本地目錄時，Agent 直接進入該目錄工作；其他電腦仍使用專案中的 GitHub 倉庫或工作區倉庫。

## 新增 GitHub 倉庫

開啟專案，在 **資源** 中選擇"新增資源"。可以選擇已關聯到工作區的倉庫，也可以粘貼 Git URL。工作區倉庫在 **設定 → 程式碼** 中維護；連接 GitHub 後，可在同一頁面通過 **從 GitHub 選擇** 匯入 App 已授權的倉庫。

倉庫不限於 GitHub：任何執行環境能訪問的 Git URL 都可以作為倉庫資源。自部署的 Multica 還可以在 **設定 → 程式碼** 連接自託管的 Forgejo、Gitea 或 GitLab，見[自託管 Git 程式碼託管](/vcs-integration)。

建立專案時，也可以直接在 **Repos** 中選擇倉庫。一個專案可以關聯多個 GitHub 倉庫。

資源中的 `ref` 可以指定後續 checkout 預設使用的分支、tag 或 commit。`default_branch_hint` 只向 Agent 提供預設分支提示，不會強制切換分支。

## 新增本地目錄

新增本地目錄的介面只在 Desktop 中提供，因為瀏覽器不能選擇電腦上的資料夾。

<Callout type="warning">
**這是逃生艙，不是更方便的預設項。** `local_directory` 是給那些"不得不這麼開發"的人準備的 —— 典型是一個 checkout 就幾十 GB 的遊戲專案，不可能每來一次執行就重新 clone 一份。

如果你的目錄只是一個能正常 clone 的普通 git 倉庫，**請用 `github_repo`**：它預設走 worktree 模式，同一個倉庫上的執行可以無限併發。`local_directory` **預設同一時間只進行一次執行**；如果這個目錄本身是 git 倉庫，可以主動開啟 worktree 模式把併發拿回來（見“執行如何共享這個目錄”）。先看上面的兩種資源對照再決定。
</Callout>


1. 確認 Desktop 的本地守護程序在線。
2. 開啟專案的 **資源**，或者建立專案對話框裡的 **本地目錄** 標籤頁 —— 專案還沒建出來時也能做同樣的選擇。
3. 選擇"新增本地目錄"，再選擇要使用的資料夾。
4. 選擇執行如何使用它 —— **原地** 還是 **並行**，兩者的區別見"執行如何共享這個目錄"。如果這個資料夾是 git 倉庫、並且那臺機器上的執行環境能做隔離，Desktop 會預選 **並行**，否則預選 **原地**。當場可以改，之後也可以在 **資源** 裡點目錄旁邊的鉛筆圖示改。

預選只作用於你此刻正在關聯的目錄。之前關聯好的目錄仍然保持儲存時的模式 —— 已有的設定不會在你不知情的情況下被切換。

目錄必須是絕對路徑，已經存在，並且當前守護程序可以讀取和寫入。以下路徑會被拒絕：系統根目錄和盤符根（`/`、`C:\`）、使用者主目錄本身及各主目錄的上級（如 `/Users`、`/home`、`/root`），以及 `/etc`、`/var`、`/tmp`、`/usr`、`/opt` 等系統目錄。如果所選路徑是符號連結，會先解析為真實路徑再按同樣的規則校驗一次，串行鎖也按真實路徑生效。

每個專案在同一臺守護程序上最多關聯一個本地目錄。團隊中的不同電腦可以分別為同一個專案關聯各自的目錄。

<Callout type="warning">
在預設的 `in_place` 模式下，本地目錄不是隔離環境：Agent 會直接看到並修改當前分支和未提交的檔案，Multica 也不會自動切換分支、stash、commit、push 或建立 PR。worktree 模式會改變這一點 —— 見下面的“執行如何共享這個目錄”。
</Callout>

## 執行如何共享這個目錄

本地目錄有兩種執行模式，按資源逐個設定。在資源面板裡可以直接切換，CLI 用 `--execution-mode`。Desktop 裡這兩種模式顯示為 **原地** 和 **並行**；API、CLI 和本頁其餘部分都使用標識符。

### `in_place`（預設）—— “原地”

Agent 直接在你的目錄裡工作，同一時間只進行一次執行。兩次執行使用同一個真實目錄時，後到的執行進入 `waiting_local_directory`，等前一次釋放目錄後繼續。兩個路徑經不同符號連結指向同一目錄時，同樣串行。

等待不會修改目錄。等待中的執行可以取消，否則會一直等到目錄可用。

### `worktree` —— “並行”

每次執行拿到你倉庫的一個獨立 [git worktree](https://git-scm.com/docs/git-worktree)，建在執行環境自己的工作區目錄裡。**同一目錄上的執行併發執行，誰都不用排隊**，並且都不會寫你的工作副本。

要求這個目錄是一個至少有一次提交的 git 倉庫。如果不是，執行會明確報錯，而不是悄悄退回串行。那臺機器上的執行環境也必須實現了該模式。執行環境在連接時會聲明這項能力，Multica 判斷的是這個聲明而不是版本號 —— 一個開發構建完全可能帶著看起來足夠新的版本號，卻根本沒有對應的實現。這個聲明會被檢查兩次：只要那臺機器的執行環境沒有聲明該能力，儲存資源就會被拒絕，並提示去升級那臺機器上的 App；每次執行在被真正領取時還會再按領取它的執行環境檢查一次 —— 所以資源儲存之後才降級的機器，其執行會被帶原因取消，而不是悄悄原地跑掉。選擇 `worktree` 就是在要求隔離，把它換成“直接改你的工作副本”永遠不是兜底方案。

Agent 看到什麼、你拿回什麼：

- **Agent 從你眼前的狀態開始，而不是從 `HEAD` 開始。** 你未提交的改動和未追蹤的檔案會被回放進 worktree，所以它不會去 review 一份你已經不用的程式碼。你自己的工作副本、暫存區和 stash 列表都不會被動到。如果這個狀態無法忠實還原 —— 包括未追蹤內容超出回放上限（2000 個檔案 / 200 MiB）—— 執行會直接失敗，而不是從一棵你認不出來的樹開始。通常的解決辦法是把還沒被忽略的構建產物加進 gitignore 或清理掉。
- **結果是你倉庫裡的一個分支**，按任務而不是按每次執行來分：`agent/<agent>/<issue>`（chat 則是 `agent/<agent>/chat-<session>`）。本次執行的**詳情**面板裡會顯示分支名（可直接複製），也可以用 `git branch` 找到它。用 `git log` / `git diff` review，然後自己決定 merge 還是 cherry-pick。Multica 不會替你合併。中途失敗的執行同樣會報告它的分支，因為它已經把 Agent 做出來的部分提交進去了。
- **後續對話接著上一輪繼續。** 同一個任務的下一條留言會重新 check out 這個分支，Agent 站在自己剛交付的成果上繼續做，而不是從 `HEAD` 重新開始、把上一輪的改動落在另一個分支上。只有你在上一輪之後改動的部分會被重放上去 —— 其餘部分分支裡已經有了。把分支 merge 掉之後，下一輪又會從你的 `HEAD` 重新開始。同一個任務上有兩次執行重疊時，後一個會從前一個的成果分叉到 `agent/<agent>/<issue>-<task>`，因為 git 規定一個分支只能有一棵 worktree。
- **你的改動和 Agent 的成果衝突時，由 Agent 來解決。** 如果你重寫了 Agent 也重寫過的那幾行，git 無法判斷誰對，這一輪就會在一棵帶衝突的 worktree 上啟動，並被要求先把 merge 做完（在那棵 worktree 裡 `git status` 會列出未合併的檔案）。只要還有檔案沒合完，這一輪就什麼都不交付：執行失敗、worktree 保留，下一輪會再次把同樣的改動送上來，所以你的修改不會被悄悄丟掉。
- **只有 Multica 自己的分支才會被續接。** 是否續接由歸屬記錄決定，而不是看名字：記錄裡既寫了屬於哪個會話，也寫了這條分支當時停在哪個 commit。你自己建的、恰好叫 `agent/<agent>/<issue>` 的分支永遠不會被 check out、被追加提交，也不會被當成上一輪的成果讀取；已經不包含記錄中那個 commit 的分支同樣如此 —— 所以你把 Multica 的分支刪掉再自己建一條同名的，或者把它 force-move 到別的歷史上，都是安全的，執行會改用 `agent/<agent>/<issue>-<id>`。在已交付的分支上繼續提交則是正常用法，續接照常，你的提交下一輪就在那裡。每條分支還會以一個屬於自己的 baseline commit 開頭，標記第一輪開始時的目錄狀態 —— 後續正是靠這個 commit 來辨認這條分支，同時 `git diff <baseline>..<branch>` 恰好就是 Agent 做的改動。如果某一輪沒能記錄它的分支 —— 中途失敗、記錄寫不進去，或者把 worktree reset 到了「把你的改動帶進分支的那個 commit」之前 —— 這一輪會報失敗並保留 worktree，後續幾輪會另起一條分支，而不是去續接一條無法證明歸屬的分支。
- **不會靜默丟東西。** Agent 留下的未提交改動，會在 worktree 被移除前提交到那個分支上，**執行中途失敗時同樣如此**。極少數情況下連這次提交都做不了 —— 例如倉庫開了 `commit.gpgSign` 而執行環境拿不到簽名密鑰 —— worktree 會被刻意保留而不是刪除，執行標記為失敗，並且在你倉庫裡執行 `git worktree list` 就能看到存放這些改動的目錄。
- **沒有產生改動的執行不留下任何東西。** 它的分支會被刪除，而不是作為一個空條目留在 `git branch` 裡；但如果這是承載了之前幾輪成果的任務分支，它一定會保留。

由於 worktree 位於執行環境的工作區目錄內，它會按正常的清理週期回收。留在你倉庫裡的有兩樣東西：分支，以及每條分支對應的一個隱藏 ref（在 `refs/multica/local-state/` 下），記錄這條分支歸誰所有、以及上次續接時你目錄裡的內容。隱藏 ref 不會出現在 `git branch` 裡，可以用 `git for-each-ref refs/multica` 查看。Multica 刪除分支時會一併刪掉它；你自己刪掉的分支所對應的 ref，會在下一次該倉庫上有執行開始時被清理 —— 也可以用 `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` 一次性清掉。

<Callout type="warn">
**自託管運維注意：** 該模式的隔離由服務端強制（儲存資源時檢查一次，執行環境每次領取執行時再檢查一次），所以無論何時降級執行環境都會被攔住。唯一攔不住的組合是：把服務端回滾到本功能之前的版本，同時還連著沒有實現該模式的執行環境 —— 舊服務端沒有這道門禁，而這樣的執行環境會忽略 `execution_mode`、直接在原目錄裡執行。只要還存在 `worktree` 資源，就不要把服務端回滾到本版本之前，除非那些機器上的執行環境全部升級到位。
</Callout>

<Callout type="info">
worktree 模式面向 git 倉庫。普通的非 git 目錄仍然串行執行 —— 這正是 `in_place` 的用途。
</Callout>

## 執行期間寫入的內容

除了 Agent 產生的程式碼改動，執行環境還可能在目錄中寫入當前 AI 編程工具所需的說明檔案，以及 `.multica/project/resources.json`。不希望它們進入版本控制時，加入 `.gitignore` 即可。

Multica 清理執行環境時不會刪除關聯的本地目錄。Agent 對該目錄的改動，與你在終端中直接執行 AI 編程工具的改動性質相同，需要同樣的審查。

## 使用 CLI 管理資源

```bash
# Link a repository when creating a project
multica project create \
 --title "Agent UX" \
 --repo https://github.com/multica-ai/multica

# View and add resources
multica project resource list <project-id>
multica project resource add <project-id> \
 --type github_repo \
 --url https://github.com/multica-ai/multica \
 --ref main

# Link a local directory on the specified daemon
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id>

# Link a local git repository and run concurrently in separate worktrees
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id> \
 --execution-mode worktree

# Change the mode for an existing local directory
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# Remove a resource
multica project resource remove <project-id> <resource-id>
```

資源變更會影響之後建立的執行，不會改寫已經結束的執行記錄。

Multica CLI 可連線至本機執行環境，也能在終端機管理工作區、任務、Agent 和自動化。本頁介紹常見操作；你安裝的版本支援哪些旗標，請一律以各命令自己的 `--help` 為準。

## 安裝

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

如果已安裝 Homebrew，也可以執行：

```bash
brew install multica-ai/tap/multica
```

</Tab>
<Tab value="Windows">

在 PowerShell 中執行：

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

</Tab>
</Tabs>

確認安裝成功：

```bash
multica version
```

## 第一次連線

按連線的服務選擇：

<Tabs items={["Multica Cloud", "自託管例項"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="自託管例項">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` 會儲存服務地址、開啟瀏覽器完成登入，並啟動 daemon。完成後檢查：

```bash
multica auth status
multica daemon status
```

如果只需要重新登入，且不想覆寫其他設定，請執行 `multica login`。若環境沒有瀏覽器，請先在 Web 設定中建立個人存取權杖，再輸入：

```bash
multica login --token
```

命令會提示你在終端機貼上權杖，避免完整權杖留在 shell 歷程記錄中。

## 選擇工作區

列出工作區並切換預設工作區：

```bash
multica workspace list
multica workspace switch <slug>
```

之後的命令都會使用這個工作區。若只想讓單一命令使用其他工作區，可用 `--workspace-id` 暫時覆寫，或設定 `MULTICA_WORKSPACE_ID`。

邀請工作區成員：

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## 常用任務操作

```bash
# 查看和搜索
multica issue list
multica issue get MUL-123
multica issue search "登录失败"

# 创建和修改
multica issue create --title "修复登录失败"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# 评论和执行记录
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "请先检查回归测试"
multica issue comment update <comment-id> --expected-revision 2 --content "请检查回归测试和发布说明"
multica issue runs MUL-123
```

長篇描述或留言可從 stdin 讀取，避免處理換行和引號：

```bash
multica issue create --title "升级说明" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

檢視某次執行的訊息、停止執行或重試：

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

把留言插話到仍在進行中的執行，而不是排隊一個後續執行（僅限支援插話的執行；你的留言能啟動哪個 Agent，就能向它插話）：

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

同一專案、同一父任務下已有標題相同（不區分大小寫，忽略多餘空格）且未關閉的任務時，`issue create` 會拒絕建立並給出那個任務。確實要再建一個，加 `--allow-duplicate`；要把一個任務標為另一個的重複，用 `multica issue status MUL-124 cancelled --duplicate-of MUL-123`。

一個任務要依次提交多個 PR 時，用 `issue create --title "..." --pr-auto-complete off` 或 `issue update <id> --pr-auto-complete off`，讓這個任務在 PR 合併後保持原狀態。用 `--pr-auto-complete on` 恢復工作區規則，從下一次 PR 事件起生效。`issue pull-requests <id>` 會顯示任務開關、工作區開關、目標狀態和判斷結果，沒有關聯 PR 時也會顯示。支援該欄位的服務端會在建立事務內儲存開關；舊服務端會補調一次 PUT，失敗時 CLI 會給出已建立的任務 ID 和重試用的 update 命令，請勿重複建立。

### 時間線

`issue get` 給出任務現在的狀態；`issue timeline` 按時間順序列出狀態、優先順序、負責人、標題、日期的改動和執行結果，並混排留言，用來回答"什麼時候進入 in_review""卡在目前狀態多久了"：

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` 去掉留言，保留全部活動記錄；`--action` 只返回指定的動作，可重複，並隱含 `--activity-only`。伺服器讀取的歷史有上限，被截斷時 stderr 會列印警告，這時不要據此推算停留時間長度。

### 讀長留言執行緒

留言多的任務，Agent 逐條讀取很費 token。先掃一遍執行緒，再展開需要的那一個：

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` 只返回頂層留言，每條附帶回複數和最近活動時間。
- `--summary` 把每條內容截成預覽。
- `--compact` 只作用於 JSON 輸出，去掉不帶資訊的欄位（例如重複的 `issue_id`、空陣列）。
- `--recent N` 返回最近活躍的 N 個執行緒，每個執行緒帶上全部回覆，回覆多時輸出可能很長。
- 已解決的執行緒預設摺疊成首條留言和結論，需要原文時加 `--full`。

列表也可以只取需要的欄位：`multica issue list --output json --fields id,identifier,title,status`。篩選在 CLI 本機完成，減少的是輸出和上下文，不是請求量。

按最近更新時間列出任務時，同時傳入 RFC3339 時間戳 `--updated-since` 和 `--updated-until`。服務端返回目前 `updated_at` 大於等於 `since`、小於 `until` 的任務，即 `[since, until)`。這兩個參數可與現有篩選、排序和分頁引陣列合使用。翻頁時保持時間範圍一致；分頁不提供快照，併發更新可能改變結果集。

```bash
multica issue list --updated-since 2026-11-05T10:00:00Z \
  --updated-until 2026-11-05T10:01:00Z \
  --sort created_at --direction asc --limit 100 --offset 0 \
  --output json --fields id,workspace_id,project_id,title
```

### 喚醒

喚醒讓 Agent 在某個事件發生、某個條件成立或到點時開始一次普通執行。完整規則見[任務喚醒](/issue-wakeups)。

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "对方回复后，按回复内容更新报价单"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "检查供应商是否回信"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

在終端機裡以成員身份建立時需要 `--agent-id`；Agent 在自己的執行中建立時預設喚醒它自己。

## Agent 和 skill

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

匯入時若遇到同名 skill，預設會停止操作，不修改現有內容。請依需求選擇：

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` 只允許 skill 的建立者使用，並保留原有 ID 和 Agent 繫結關係。

環境變數和 MCP 設定常帶有 token。命令列裡直接寫值會留在 shell 歷史和 `ps` 輸出中，用 `-file` 或 `-stdin` 形式傳入：

```bash
multica agent create --name "运营助手" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- `--custom-env` 系列只在 `agent create` 中可用。之後修改用 `agent env set`，它整體替換原有變數，值寫成 `****` 的鍵保留原值。
- `agent update --mcp-config null` 清除 MCP 設定。
- `--custom-args` 是 JSON 陣列，排在啟動參數的最後。選模型用 `--model`，部分工具會拒絕出現在自訂參數裡的 `--model`。
- 誰能呼叫 Agent 用 `--permission-mode`：`private` 只有所有者，`public_to` 配合 `--public-to-workspace` 或 `--public-to-member <user-id>`。`--visibility private|workspace` 是舊寫法，會對映到 `--permission-mode`；兩者同時給出時以 `--permission-mode` 為準。

## daemon 和runtime

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "内部 Claude 封装" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` 為目前 profile 登記開機自啟，平臺差異見[開機自啟](/daemon-runtimes#autostart)。`runtime usage` 預設統計 90 天，`--days` 最多 365。`runtime update` 讓那臺電腦上的 daemon 把 CLI 更新到指定版本，`--wait` 會一直等到更新結束。`runtime profile create` 用 `--runtime-type` 指定相容的工具（舊的 `--protocol-family` 仍可用）；固定參數目前只能在網頁端填寫。

刪除仍繫結活躍 Agent 的runtime時，命令預設拒絕。`multica runtime delete <id> --cascade` 會解綁這些 Agent、保留其設定與歷史記錄，並取消它們的活動執行。

執行方式和自訂 profile 請參閱[常駐程式與執行環境](/daemon-runtimes)。

## 環境 [#environments]

```bash
multica env start web
multica env start web --wait=false
multica env list
multica env stop web
```

`multica env`（完整寫法 `multica environment`）啟動儲存庫在 `.multica/environments.toml` 裡宣告的環境。環境由 daemon 託管，執行結束後繼續執行，顯示在任務側欄裡，TTL 到期時停止。`start` 會等環境能響應後列印它的 URL。這些命令使用目前執行的憑據，所以只能在 Agent 的執行中使用；在你自己的電腦上請用任務側欄。檔案格式和示例見[環境](/environments)。

## 專案、工作區和自動化

```bash
multica project create --title "618 活动" --lead "李雷" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "运营部" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "每周销售周报" --agent "运营助手" \
  --mode create_issue --issue-title-template "销售周报 {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Asia/Shanghai
```

- `--lead` 接受成員或 Agent 的名稱。`--default-branch-hint` 只告訴 Agent 儲存庫的預設分支，不會切換分支。
- 工作區的 `--context` 會提供給工作區裡的每個 Agent。`--slug` 建立後不能修改；`--issue-prefix` 會轉成大寫，修改它會給所有現有任務重新編號，外部引用裡的舊編號隨之失效。
- `--issue-title-template` 只替換 `{{date}}`（UTC，`YYYY-MM-DD`），其他 `{{...}}` 會被拒絕。定時觸發器的 `--timezone` 預設 UTC。

## ID 和輸出格式

任務使用 `MUL-123` 這類 key 或完整 UUID，不接受 UUID 短字首。

其他資源的 `list` 命令通常會顯示可複製的短 ID，並支援用 `--full-id` 輸出完整 UUID。若短 ID 不唯一，CLI 會要求提供更多字元或改用完整 UUID。執行記錄的短 ID 也需要透過 `--issue` 指明所屬任務。

許多命令支援結構化輸出：

```bash
multica issue list --output json
multica agent list --output json
```

指令碼應使用 JSON 輸出，不要解析面向終端機的表格。各命令支援的輸出格式和分頁旗標請以 `multica <command> --help` 為準。

## Profile 與設定

預設設定儲存在 `~/.multica/config.json`。使用 `--profile <name>` 可以隔離另一套服務地址、權杖、預設工作區和常駐程式狀態：

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

命名 profile 儲存在 `~/.multica/profiles/<name>/config.json`。檢視目前值：

```bash
multica config show
multica config show --profile staging
```

請勿在主機 shell、Compose 服務或啟動常駐程式的容器進入點中設定 `MULTICA_DAEMON_PORT`。主機常駐程式通常會依 `--profile` 推導健康檢查連線埠；若無法繫結該連線埠，便會改用可用的 loopback 連線埠，並自行將實際連線埠注入 Agent 任務。舊版啟動環境應徹底移除此變數：否則 0.4.22 和 0.4.23 會把該 shell 誤判為受管理的任務，並拒絕登入。較新版允許受保護的人工作業登入和 `daemon status` 在連線埠是唯一任務訊號時復原，但一般 API 命令和解析 profile 的命令仍會採取安全拒絕，直到移除此變數。

CLI 在常駐程式管理的 Agent 任務中執行時，不會載入或修改這些由人員管理的 profile 檔案。Multica API 命令會使用常駐程式注入、僅限該任務的憑證進行驗證。`config show` 和 `config set` 會使用任務專用的私人狀態；`login`、`logout`、`setup`、`workspace switch`、本機執行環境 profile 路徑變更、`daemon start` / `stop` / `restart`、`daemon logs` 和 `daemon probe-runtimes` 等人員／本機命令則無法使用。在此情境下，`auth status` 不會輸出權杖內容。

`daemon status` 和 `daemon disk-usage` 仍可供 Agent 檢查承載它的執行環境，且範圍僅限該執行環境：`status` 會探測常駐程式注入的健康檢查連線埠，`disk-usage` 會掃描常駐程式注入的工作區根目錄。兩者都不接受 `--profile`；`disk-usage` 也會拒絕 `--all-profiles` 和 `--workspaces-root`。由於解析狀態需要使用人員儲存的權杖，其 STATUS 欄位會留白。若要檢查此範圍以外的內容，請使用 `du` 和 `df`。

這樣可保護 Multica CLI 隱含解析 profile 的行為，同時保留其他供應商工具所需的一般 `HOME` 和 XDG 變數。這並非作業系統層級的檔案系統隔離：以相同系統使用者身分執行的程式仍可開啟已知的明確路徑。若需要更強的隔離，請使用專用使用者、容器、虛擬機器或同等方案。

<Callout type="warning">
CLI 設定檔包含可代表你存取 Multica 的權杖。請勿將其提交至儲存庫、上傳到日誌或與他人分享。
</Callout>

## 命令參考

下表列出目前所有頂層命令，並依 CLI 本身的分組排列。所有命令都接受全域旗標 `--server-url`、`--workspace-id`、`--profile` 和 `--debug`。`--output` 依命令個別註冊，預設格式也因命令而異：`list` 類命令預設輸出表格；`get`、`create` 類命令大多預設輸出 JSON。完整旗標請以 `multica <command> --help` 為準。

### 任務附件

`issue create`、`issue update` 和 `issue comment add` 的每個 `--attachment` 接受一個完整檔案路徑，保留檔名中的逗號和雙引號。多個檔案須重複 flag，例如 `--attachment 'report,final.csv' --attachment notes.txt`。省略 flag 時不新增附件；顯式傳入空路徑會報錯。所有本機路徑都透過檢查後才開始上傳。

從舊 CSV 解析方式遷移：要新增兩個檔案，將 `--attachment a,b` 改為 `--attachment a --attachment b`。前一種寫法現在只選擇名為 `a,b` 的單個檔案。舊用法 `--attachment '"report,final.csv"'` 中額外的 CSV 雙引號也須移除，改用 `--attachment 'report,final.csv'`；只有檔名本身包含雙引號時才保留。

## 從其他程式開發 Agent 操作 Multica

如果你的工作大多發生在 Codex、Claude Code 或 Cursor 裡，可以直接在那裡操作 Multica，不必切回終端機。[Multica CLI skill](https://github.com/multica-ai/multica-cli) 會教這些 Agent 安全地使用本頁的命令：讀任務和留言執行緒時少耗 token、透過檔案寫留言，以及正確處理 mention、狀態變更和指派帶來的副作用。

它完全透過你已認證的 CLI 執行，本身不授予任何權限，權限仍然只來自你的登入、所選 profile 和工作區。要求 CLI 版本不低於 v0.4.26。該儲存庫的 README 說明瞭 Claude Code 外掛市場、Codex skill 安裝器、Cursor 以及其他任何載入 Markdown 指令的工具的安裝方式。

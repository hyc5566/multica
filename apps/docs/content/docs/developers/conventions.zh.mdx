本分支的中文採台灣繁體中文；`zh-Hans` 仍是 API 與儲存使用的相容性語系 key，文件檔名仍使用 `.zh.mdx`。下列中文用語適用於本分支，不更動其他語系或內部識別字。

## 1. 程式碼命名

### 路由

工作區前置路由（使用者進入工作區之前能存取的路由）必須用單一單字，或者 `/{noun}/{verb}` 格式。

- ✅ `/login`、`/inbox`、`/workspaces/new`
- ❌ `/new-workspace`、`/create-team`、`/accept-invite`

根目錄含連字號的詞組會與使用者自選的 workspace slug 衝突，需要持續檢查保留字。保留名詞（`workspaces`）就能自動保護整個 `/workspaces/*` 子樹。

### 工作區路由

永遠用 `/{slug}/{section}` —— `/{slug}/issues`、`/{slug}/agents`、`/{slug}/settings`。共用程式碼不要複製路由邏輯，統一走 `useNavigation().push()`，不要直接用框架的 link API。

### 套件與模組

monorepo 必須遵守以下套件邊界：

| 套件 | 可依賴 | 不能依賴 |
| --- | --- | --- |
| `packages/core` | 僅平台無關基礎函式庫 | `react-dom`、`localStorage`、`process.env`、`next/*`、UI 函式庫 |
| `packages/ui` | 無業務依賴 | `@multica/core`、業務邏輯 |
| `packages/views` | `core/`、`ui/` | `next/*`、`react-router-dom`、stores |
| `apps/web/platform/` | `next/*` | 其他 app |
| `apps/desktop/.../platform/` | `react-router-dom`、electron | 其他 app |
| `apps/mobile/` | `@multica/core` 的型別和純函式 | Web/Desktop 的 React 頁面、store 和平台實作 |

Web 和 Desktop 都有的邏輯，**必須**抽到共用套件。"少量重複"也不算例外。Mobile 擁有獨立的 UI、資料層和發布流程，只共用型別與純函式。

### 檔案與元件

- 檔名：`kebab-case.tsx` / `kebab-case.ts`（如 `agent-row-actions.tsx`）
- 元件：`PascalCase`（如 `AgentRowActions`）
- Hook：`useCamelCase`（如 `useWorkspaceId`）
- 測試：與原始檔案同目錄，命名 `<file>.test.ts(x)`
- Zustand store：`<feature>-store.ts`，匯出名 `use<Feature>Store`

### 資料庫（Go + sqlc）

- 表名：`snake_case` 單數（`user`、`workspace`、`agent_runtime`）
- 欄位：`snake_case`（`workspace_id`、`created_at`、`last_seen_at`）
- 關聯欄位：`<table>_id`
- 布林值：`is_<state>` 或者 `<state>_at`（狀態變化優先用時間戳記形式）
- 遷移檔案：`NNN_descriptive_name.up.sql` + `.down.sql`，**永遠寫雙向**
- 不建立資料庫 foreign key，也不使用串聯刪除或串聯更新；關係驗證和清理由應用層完成
- 所有索引都使用 `CREATE INDEX CONCURRENTLY` 或 `CREATE UNIQUE INDEX CONCURRENTLY`，每條 concurrent index 單獨佔一個 migration 檔案

### Go

- 標準 `gofmt` + `go vet`，無例外
- Handler 檔案按域命名：`agent.go`、`auth.go`、`runtime.go`
- 測試：`<file>_test.go` 同目錄
- handler 的 UUID 解析遵守根 `AGENTS.md` 的規則：邊界輸入用 `parseUUIDOrBadRequest`，可信的資料往返用 `parseUUID`（panic 版），永遠不要直接用 `util.ParseUUID` 不查 error

### TypeScript

- 網路上 API 回應是 `snake_case`，api client 在邊界處轉成 `camelCase`。**TS 程式碼內部一律 camelCase**
- 型別：`PascalCase`（`Issue`、`AgentRuntime`），不加 `IPrefix`，不加 `_t` 後綴
- 列舉：優先用 string literal union，需要 runtime 迭代時才用 `enum`
- TanStack Query key：用 `<feature>/queries.ts` 裡的工廠函式，例如 `issueKeys.detail(id)`

### API 邊界

- 網路回應必須用 `packages/core/api/schema.ts` 中的 `parseWithFallback` 和 zod schema 解析，不能直接 `as T`
- 新增或修改 endpoint 時，同步更新 schema，並覆蓋欄位缺失或格式錯誤的測試
- 下游 UI 對可選欄位提供預設值；伺服器端列舉的 `switch` 必須有 `default` 分支
- 已安裝的 Desktop 可能連線更新的 backend，不能假設前後端永遠同版本

### Runtime 顯示名

`AgentRuntime.name` 是 daemon 的原始技術名（例如 `Codex (host)`），使用者別名在 `custom_name`。使用者可見文案不得直接渲染 `runtime.name`，要用共用 helper，保證別名和 provider 一致（MUL-5248、#5260）：

- 獨立展示 runtime（列表、標籤、確認對話框、視窗標題）：`runtimeDisplayLabel(runtime)` → 別名 + provider，無別名時回退 daemon 名。
- 旁邊已經單獨顯示 provider 圖示/文字時：`runtimeDisplayName(runtime)` → 只顯示別名，避免重複 provider。
- 在機器分組內：機器標題用 `machine.title`，子行用 `runtimeRowLabel(runtime, machine.title)`。
- runtime 選擇器用 `buildRuntimeMachines` 按機器分組，不要自己拼扁平的原始名列表。

原始 `runtime.name` 只允許用於內部識別——hostname 解析、分組、搜尋 haystack、協議 payload——絕不能進入 JSX 文字、i18n 參數、`<Select>` label 或視窗標題。

### Issue 編號

每個 issue 有人類可讀的編號，比如 `MUL-123`：工作區 `issue_prefix`（大寫字母和數字，通常 3 個字元，最長 10 個）+ 流水號。工作區管理員可以在**設定 → 一般**中修改前綴；修改會讓所有現有 issue 重新編號，外部引用——PR 標題、分支名、文件與聊天裡的連結——裡的舊前綴會失效。

### 程式碼註解

**只允許英文**。Go 和 TypeScript 都強制。如果在程式碼裡看到中文註解，那就是 bug，替換掉。

### Commit message

Conventional 格式：`feat(scope)`、`fix(scope)`、`refactor(scope)`、`docs`、`test(scope)`、`chore(scope)`。按意圖原子化分組。

## 2. i18n 翻譯術語表

這是每個翻譯 PR 都必須遵守的術語表。原本在 `packages/views/locales/glossary.md`，那個文件已刪除，由這一頁取代。

### 核心區分：日常詞 vs Multica 專有詞

Multica 的產品名詞分兩類：

- **日常詞** —— 使用者會直接說出口的詞。**完整翻譯成中文**，是不是資料庫實體都一樣：`issue` → 任務、`workspace` → 工作區、`project` → 專案。
- **Multica 專有詞** —— 中文裡沒有對應詞的概念（`skill`），或使用者可能要照著敲、照著比對的 schema 識別字（`todo`、`in_progress`、`task_id`）。**用小寫英文**呈現，讀起來像型別名。

其他文案參考 `apps/docs/content/docs/*.zh.mdx`。各語系文件依照下表區分任務與執行；本分支的中文使用台灣用語。

### `issue` 就是產品中的"任務"，必須翻譯

`issue` 是這個"使用者提出、Agent 去做的事"的英文產品名。在英文之外的每種語言裡，它就是當地最日常的那個"任務"詞：

| 實體 | en | zh-Hans | ja | ko | fr |
| --- | --- | --- | --- | --- | --- |
| 提交出來的一件事（`issue`） | Issue | **任務** | **タスク** | **태스크** | **Tâche** |
| Agent 的一次執行記錄（API / DB 中為 `task`） | **Run** | **執行** | **実行** | **실행** | **Exécution** |

這兩個概念使用者都看得到，而且**不是一回事** —— 一個任務下面可以有多次執行。任何一種語言都不能把兩者寫成同一個詞。`Task` 不再是 Agent 單次執行的使用者側產品名，只保留為已經穩定的內部識別字。

不跟著改的部分：

- **API / DB 欄位**永遠是 `issue` / `task` / `skill`：`issue_status`、`task_id`、`skill_uuid`。開發者內文稱產品物件為 Run；需要對照協議時可寫成"Run（API 中為 `task_id`）"。
- **程式碼引用和字面命令**保持英文：`multica issue ...`、Slack 與飛書的 `/issue` 斜線指令。
- **`skill`** 在中文裡仍用小寫英文 —— Multica 特有概念，沒有公認中文譯法；標題可大寫為 `Skills`。
- **表示"問題"的 issue** 不是這個實體：機器卡片上的 `{{count}} issues` 是 `{{count}} 個異常` / `問題 {{count}} 件` / `문제 {{count}}개`，不要用實體那個詞。

**為什麼 `issue` 要譯，而 `skill` 不譯**：使用者每天都在提任務、看任務，而 "issue" 這個詞在中文、日文、韓文裡除了開發圈術語之外沒有含義，當地人本來就用"任務"在說這件事。`skill` 則是 Multica 特有概念，沒有哪個中文詞能承載它的意思。

其他產品名詞同樣以"是否有通用的當地用語"判斷：

- **`project` 翻成"專案"**：使用台灣常見的工作管理用語，不在中文產品文案中保留英文 `project`。
- **`autopilot` 翻成"自動化"**：這項功能依排程啟動 Agent 執行，使用"自動化"能直接表達用途，避免讓人聯想到車輛的自動駕駛。

### 角色名 + 狀態名（小寫英文，不翻）

這些是 schema-level 識別字，中文環境也保持小寫英文：

- 角色：`owner` / `admin` / `member`
- Issue 狀態：`backlog` / `todo` / `in_progress` / `in_review` / `done` / `blocked` / `cancelled`
- Issue 狀態分類：`unstarted` / `started` / `done` / `closed`

UI 裡顯示這些值時保持英文（必要時用 code-style 包起來）：

- "你需要 owner 權限"
- "已切換到 in_progress"

### 詞組組合規則

英文詞（實體名 + 品牌名 + 縮寫）與中文之間**加單空格**：

- "Create new issue" → "新建任務"（`任務` 是中文，不加空格）
- "Assign to agent" → "分配給 Agent"
- "Configure runtime" → "設定執行環境"
- "Stop daemon" → "停止常駐程式"

### 複數與計數

i18next 用 `_one` / `_other`；中文不區分語法單複數，只填 `_other`。

```json
// en/issues.json
{
  "issue_count_one": "{{count}} issue",
  "issue_count_other": "{{count}} issues"
}

// zh-Hans/issues.json
{
  "issue_count_other": "{{count}} 項任務"
}
```

常見計數格式：

- `{{count}} issues` → `{{count}} 項任務`
- `{{count}} agents` → `{{count}} 個 Agent`
- `{{count}} workspaces` → `{{count}} 個工作區`
- `{{count}} comments` → `{{count}} 則留言`
- `{{count}} members` → `{{count}} 位成員`
- `{{count}} skills` → `{{count}} 個 skill`

### 插值

用 `{{var}}` 形式。中文翻譯可以調整位置以符合中文語序。

```json
// en
{ "welcome_message": "Welcome back, {{name}}!" }

// zh-Hans
{ "welcome_message": "歡迎回來，{{name}}！" }
```

### Key 命名約定

3 層嵌套：`feature.component.action`。

```json
{
  "feature_or_component": {
    "subcomponent_or_section": {
      "action_or_label": "..."
    }
  }
}
```

實例：

- `issues.toolbar.batch_update_success`
- `issues.detail.comment_form.placeholder`
- `inbox.empty.title`
- `settings.preferences.language.title`

### Web-only / Desktop-only 文案位置

- 共用文案：放 namespace JSON 頂層
- Web-only：放 `web` 段
- Desktop-only：放 `desktop` 段

參考 `auth.json`（`web` 段含 `prefer_desktop` / `desktop_handoff.*`）。

## 3. 中文風格

### 標點

- 中文用全角標點：`，。：；！？`
- 引號：用 `"..."`（直引號），與英文 source 保持一致。**不要**用 `「」` 或彎引號
- 省略號：用 `...`（三點）而非 `…`（單字元），與英文 source 保持一致
- 中英混排：英文詞左右各加 1 個空格（詳見詞組組合規則）

### 風格原則

- **簡潔直白**：避免翻譯腔，"對於 X 來說"、"作為 X"、"我們的"
- **錯誤資訊**：溫和但明確，"無法儲存修改" 優於 "儲存修改失敗了！"
- **按鈕**：動詞開頭，2-4 字最佳。"取消"、"儲存修改"、"立即同步"
- **Tooltip**：完整短句。"複製連結到剪貼簿"
- **placeholder**：示例性提示。"輸入任務標題..."

### UI 描述性文案

description 預設省略。新增前先問：**沒有這句話，使用者會誤解什麼或做錯什麼？** 如果標題、標籤、控制項、目前值或按鈕已經表達清楚，就不新增。

- 同一事實只說一次，放在最相關的控制項旁，不在頁頭、分組、欄位、空狀態和對話框中反覆解釋。
- 優先用準確的標籤或具體示例，避免用一段話講解顯然的操作。除非能消除實際歧義，不寫"建立一個開始使用""點選下方""之後可以修改"等通用提示。
- 權限、費用、不可撤銷後果、執行前提、輸入限制和錯誤恢復資訊應在相關狀態下直接可見，不藏進只能懸停查看的說明中。
- 首次使用說明只在需要的位置展示；進階用法與診斷細節放入可明確開啟、支援鍵盤操作的說明中。
- 保留輸入標籤、無障礙名稱和必要的描述關聯。不要把刪掉的重複的可見文案全部轉成螢幕閱讀器專用文字。
- 同時檢查英文、各語言翻譯和行動版獨立文案。PR 評審檢查新增資訊、同一畫面上的重複資訊、顯示條件和保留的約束；字數只是複查信號，不是自動刪除標準。

共用設定元件已經支援可選 description。示例與新增呼叫預設省略，不增加強制填寫描述的元件屬性，也不另建一份文案規範。

### 不確定的時候去哪查

術語表沒覆蓋的詞，按這個順序查：

1. `apps/docs/content/docs/*.zh.mdx` —— 本分支的台灣繁體中文文件
2. `packages/views/locales/zh-Hans/auth.json` 和 `editor.json` —— JSON 結構 + selector API 用法參考
3. `packages/views/auth/login-page.tsx` —— 元件層 selector API 呼叫參考
4. `packages/views/settings/components/preferences-tab.tsx` —— 語言切換器參考

## 修改本頁時

改本頁規則的同時還要：

1. 把規則在相關 locale JSON / AGENTS.md / docs 頁面裡同步落地
2. PR 描述裡寫明改了什麼，方便 reviewer 檢查下游是否跟著改了

本頁定義儲存庫的文案契約。

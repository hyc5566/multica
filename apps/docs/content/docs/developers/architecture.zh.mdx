Multica 由一個 Go backend、多種用戶端和在執行主機上運作的常駐程式組成。PostgreSQL 儲存協作資料；常駐程式領取 task，並呼叫本機的 AI 程式開發工具。

本頁聚焦實作，因此內文中的 **task** 指產品 **Run**（執行）背後的內部排程、API 和資料庫實體。介面與產品文件統一稱為 Run；`TaskService`、`task_id` 等識別字為相容性保持不變。

```text
Web / Desktop / Mobile / CLI
 │
 HTTP + WebSocket
 │
 Go API ───────── PostgreSQL
 │
 daemon WebSocket
 │
 本機常駐程式 ─── AI 程式開發工具
```

面向產品使用者的解釋見 [Multica 的工作方式](/how-multica-works)。本頁關注程式碼如何分層。

## 儲存庫結構

| 目錄 | 職責 | 主要技術 |
| --- | --- | --- |
| `server/` | API、認證、task 排程、整合、CLI 和常駐程式 | Go、Chi、sqlc、gorilla/websocket |
| `apps/web/` | 瀏覽器用戶端和 landing page | Next.js App Router |
| `apps/desktop/` | 桌面用戶端和本機程序管理 | Electron、electron-vite |
| `apps/mobile/` | 獨立的 iOS 用戶端 | Expo、React Native |
| `apps/docs/` | 多語言文件站 | Next.js、Fumadocs |
| `packages/core/` | API client、型別、查詢、mutation 和平台無關業務邏輯 | TanStack Query、Zustand |
| `packages/ui/` | 不包含業務邏輯的基礎 UI | shadcn、Base UI |
| `packages/views/` | Web 與 Desktop 共用的業務頁面和元件 | React |
| `packages/tsconfig/`、`packages/eslint-config/` | 共用工具設定 | TypeScript、ESLint |

共用套件直接匯出 `.ts` 和 `.tsx` 原始檔案，由使用它們的應用編譯。依賴方向是 `views → core + ui`；`core` 和 `ui` 互不依賴。

## Web 與 Desktop 的程式碼共用

Web 和 Desktop 共用三層：

1. `packages/core` 處理 API、快取、權限和平台無關狀態；
2. `packages/ui` 提供基礎元件；
3. `packages/views` 組合業務頁面。

路由、cookie 和 Electron IPC 等平台能力留在應用層。共用頁面透過 `NavigationAdapter` 導覽，不直接匯入 `next/*` 或 `react-router-dom`。

例如，一項 Web 與 Desktop 都需要的任務功能通常會涉及：

```text
packages/core/issues/ 查詢、mutation、快取更新
packages/views/issues/ 頁面和業務元件
apps/web/platform/ Next.js 路由轉接
apps/desktop/.../platform/ Electron 路由轉接
```

Mobile 不重用這些 React 頁面。它可以匯入 `@multica/core` 的型別和純函式，但擁有自己的 UI、query key、狀態、即時訂閱和發布流程。

## 前端狀態

伺服器端資料和用戶端狀態分開管理：

- **TanStack Query** 儲存任務、Agent、成員、收件匣等伺服器端資料；
- **Zustand** 儲存篩選條件、草稿、對話框和版面配置等用戶端狀態；
- 目前工作區由路由決定，只在平台層為請求、持久化命名空間和重連做必要鏡像；
- React Context 只傳遞工作區 ID、導覽轉接器等平台基礎設施。

WebSocket 事件應更新 TanStack Query 快取，或將其標記為失效，不能把伺服器端物件複製進 Zustand。建立、刪除或離開工作區這類會導向其他頁面的 mutation，需要等待伺服器端確認後再清理本機狀態。

API 回傳值在 `packages/core/api/` 邊界透過 zod schema 解析。已安裝的 Desktop 可能連線更新的 backend，因此不能直接把網路 JSON 強制轉換成 TypeScript 型別。

## Backend 分層

主要入口位於 `server/cmd/`：

| 入口 | 作用 |
| --- | --- |
| `server` | 啟動 HTTP API、WebSocket、排程器和整合 worker |
| `multica` | CLI 與本機常駐程式 |
| `migrate` | 執行資料庫 migration |
| `backfill_*` | 特定版本的資料回填工具 |

請求通常按以下方向流動：

```text
router → middleware → handler → service → sqlc query → PostgreSQL
```

- `internal/middleware/` 處理認證、工作區和請求邊界；
- `internal/handler/` 解析 HTTP 輸入並產生回應；
- `internal/service/` 負責跨查詢的業務流程和交易；
- `pkg/db/queries/` 儲存手寫 SQL；
- `pkg/db/generated/` 由 sqlc 產生，不能直接編輯；
- `internal/integrations/` 處理 GitHub、Slack、飛書等外部事件；
- `internal/storage/` 處理本機或 S3 附件。

PostgreSQL 是業務資料的權威來源。Redis 是可選元件，用於跨實例即時事件、快取或暫時協調；沒有設定時，單實例開發環境使用程序內實作。

## 即時連線

Multica 有兩條不同的 WebSocket 路徑：

- `internal/realtime/` 把任務、留言、收件匣等變化推送給使用者的用戶端；
- `internal/daemonws/` 連線常駐程式，用於喚醒執行環境和執行 daemon RPC。

WebSocket 負責降低延遲，資料庫仍然是最終狀態。用戶端重連後需要透過查詢重新校正；常駐程式也保留輪詢路徑，避免一次斷線讓 queued task 永久停住。

## 一次執行的程式碼路徑

1. 使用者分配任務、提及 Agent，或由自動化觸發；
2. `TaskService` 建立 queued task，並通知對應執行環境；
3. 常駐程式透過 daemon API 領取 task；
4. 伺服器端簽發綁定 task 和 Agent 的暫時憑證；
5. 常駐程式準備本機目錄，呼叫 `pkg/agent` 中對應的 provider backend；
6. 工具在本機執行，常駐程式上傳進度、訊息和最終狀態；
7. 伺服器端更新 task 與任務，並透過即時事件更新用戶端。

provider 轉接層統一了不同 AI 程式開發工具的啟動、串流事件、取消和用量資料，但本機目錄與工作階段仍由常駐程式管理。

## 多工作區邊界

業務查詢必須限定 `workspace_id`，請求進入工作區路由前會檢查成員身份。`X-Workspace-ID` 選擇目前工作區，但不能替代權限檢查。

任務的負責人是多態關係，可以指向成員、Agent 或小隊。新增查詢、快取 key 或即時事件時，都要保留工作區與負責人型別，不能只按資源 ID 假設全域唯一上下文。

聊天整合讓團隊不用開啟 Multica，也能直接向 Agent 提問、在群聊中 @它，或從聊天窗口建立任務。

目前支援飛書/Lark、Slack、釘釘、企業微信和 Telegram。它們使用相同的會話、身份和執行機制，但安裝方式不同。

## 選擇平臺

| | 飛書 / Lark | Slack | 釘釘 | 企業微信 | Telegram |
|---|---|---|---|---|---|
| 安裝方式 | 在 Multica 中生成二維碼，用飛書掃碼授權 | 在 Slack 建立 app，再把兩個 token 填入 Multica | 建立企業內部應用和 Stream 模式機器人，再把 AppKey 與 AppSecret 填入 Multica | 在企業微信管理後臺建立智能機器人並開啟長連接，再把 Bot ID 與 Secret 填入 Multica | 用 @BotFather 建立 Bot，再把 token 填入 Multica |
| 私聊 Agent | 支援 | 支援 | 支援 | 支援 | 支援 |
| 群聊或頻道 | @ Bot 後觸發 | @ Bot 後觸發 | @ Bot 後觸發 | @ Bot 後觸發 | @ Bot 或回覆 Bot 後觸發 |
| 建立任務 | `/issue` 消息命令，按輸入直接建立 | `/issue` slash 命令，Agent 整理描述後建立 | `/issue` 消息命令，按輸入直接建立 | `/issue` 消息命令，按輸入直接建立 | `/issue` 消息命令，按輸入直接建立 |
| 新建 Chat | `/new [消息]` | 私聊：`/new [消息]`；頻道/thread：`@Multica /new [消息]` | `/new [消息]` | `/new [消息]` | `/new [消息]` |
| 清空當前 Chat 上下文 | `/clear [消息]` | 私聊：`/clear [消息]`；頻道/thread：`@Multica /clear [消息]` | `/clear [消息]` | `/clear [消息]` | `/clear [消息]` |
| 連接方式 | 平臺長連接 | Socket Mode | Stream 模式 | 平臺長連接 | `getUpdates` 長輪詢 |

新連接目前只開放中國大陸版飛書；已有的國際版 Lark 連接仍可繼續使用和管理。

每個 Bot 綁定一個 Multica Agent。需要在同一個聊天平臺中使用多個 Agent 時，要分別連接多個 Bot。

釘釘、企業微信和 Telegram [由社區維護](/community-maintained)：隨每個版本發佈，但沒有官方支援 SLA。遇到問題請提交 [GitHub 任務](https://github.com/multica-ai/multica/issues)。

企業微信目前只處理文字消息。語音、圖片和檔案消息會收到一句說明，不會轉交給 Agent。

Telegram 會將圖片、檔案、影片和音訊以附件形式轉交給 Agent，也會把 Agent 產生的檔案傳回聊天。這兩個方向都需要在伺服器設定物件儲存；未設定時，媒體訊息仍會顯示不支援提示。貼圖等非檔案訊息也會收到相同提示，不會轉交給 Agent。

## 消息的執行流程

1. Multica 根據 Bot 找到對應的工作區和 Agent。
2. 在群聊或頻道中，只有明確 @ Bot 的消息會繼續處理；私聊不需要 @。
3. Multica 校驗傳送者的帳戶綁定和工作區成員身份。
4. 消息進入一段[Agent 對話](/chat)，並建立一次執行。
5. Agent 的回覆回到原來的私聊或討論串。

沒有 @ Bot 的頻道消息不會觸發 Agent，也不會被加入它的對話上下文。

普通消息按上述流程處理。`/issue` 是命令，不是對話輪次：Multica 會在原平臺返回處理結果，但不會把命令加入 Multica Chat。Slack 原生 slash 命令仍按獨立的異步建立任務流程處理。

## 控制對話上下文

`/new` 會建立一個新的 Multica Chat，並把這條外部會話的後續消息路由到新 Chat。`/new <消息>` 會同時把消息作為第一輪。舊 Chat 仍儲存在 Multica 中，可以繼續使用。

`/clear` 不會新建 Chat，只會在當前 Multica Chat 中開啟一段新的 Agent 可見上下文。完整 Chat 歷史仍儲存在 Multica 中，但 Agent 無法讀取邊界之前的消息。`/clear <消息>` 會把消息作為新上下文的第一輪；裸 `/clear` 會把邊界應用到下一條真實消息。

在 Slack 私聊中，`/new` 和 `/clear` 都是原生 slash 命令。原生 slash command payload 無法標識頻道里的目標 thread，因此需要在目標 thread 中傳送 `@Multica /new [消息]` 或 `@Multica /clear [消息]`。

## 會話隔離

- 飛書/Lark 按聊天區分會話；同一個聊天中的後續消息會繼續原會話。
- Slack 私聊按頻道區分；頻道中的每個 thread 分別儲存一段會話。
- 釘釘按 conversation 區分會話；每個單聊或群聊分別延續自己的會話。
- 企業微信按聊天區分會話；每個單聊或群聊分別延續自己的會話。
- Telegram 按聊天區分會話；forum 的每個 topic 分別隔離。

在頻道中繼續追問時仍需再次 @ Bot。Agent 只收到發給自己的消息，不會自動讀取整個頻道的歷史。

## 帳戶綁定

成員第一次向 Bot 發消息時，會收到一個帳戶綁定連結。登入 Multica 後，平臺帳戶與當前工作區成員關聯。

綁定完成後，Multica 才會執行 Agent。每條消息都會重新檢查帳戶綁定和工作區成員身份；離開工作區後，不能繼續通過 Bot 使用它。

<Callout type="info">
帳戶綁定只用於確認傳送者身份。聊天平臺中的其他成員不會因此自動加入 Multica 工作區。
</Callout>

## 管理連接

工作區 owner 和 admin 可以連接或斷開 Bot；飛書/Lark Bot 的連接和斷開還對 Agent 所有者開放。普通成員可以查看已經連接的整合並使用自己有權調用的 Agent。

斷開後，Bot 不再接收新消息。已有的 Multica 對話和執行記錄仍然保留。

## 自託管

自託管部署需要先為對應平臺設定一個 32 字節加密密鑰，Multica 才會開放連接入口：

```dotenv
MULTICA_LARK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_SLACK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_DINGTALK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_WECOM_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_TELEGRAM_SECRET_KEY=<base64 編碼的 32 字節密鑰>
```

這些密鑰用於加密儲存 Bot 憑據。生成、儲存和輪換方法見[環境變數](/environment-variables)。Multica Cloud 已完成這項設定。

企業微信的出站只有一條路徑——某個程序持有的 WebSocket。回覆產生在**其他副本**上時會發生什麼，取決於實時中繼（realtime relay）的模式：

- **分片或雙寫中繼模式**（設定了 `REDIS_URL`，有 Redis 時的預設）：回覆會轉發給持有連接的副本並送達，**支援多副本部署**。
- **legacy 中繼模式，或沒有 Redis**：回覆會被丟棄。這種設定下請把啟用企業微信的後端保持單副本。

任何模式下都有一個殘留窗口：回覆產生時**沒有任何副本**持有活連接（全部在重連中），這條回覆不會送達。但它會被記錄下來——轉發它的副本事後會去確認有沒有副本認領過這次投遞，沒有就給 `multica_wecom_outbound_dropped_total{reason="no_live_connection"}` 加一，所以這個窗口有多大是能實測出來的。如果這種丟失不可接受，單副本仍是最保守的部署方式。

聊天整合讓團隊不必開啟 Multica，也能直接向 Agent 提問、在群組中 @提及 Agent，或從聊天視窗建立任務。

目前支援飛書/Lark、Slack、釘釘、企業微信和 Telegram。這些整合使用相同的對話、身分和執行機制，但安裝方式各不相同。

## 選擇平台

目前只開放連接中國大陸版飛書；既有的國際版 Lark 連線仍可繼續使用和管理。

每個 Bot 都會綁定一個 Multica Agent。若要在同一聊天平台使用多個 Agent，請分別連接不同的 Bot。

釘釘、企業微信和 Telegram [由社群維護](/community-maintained)：會隨每個版本一併發布，但不提供官方服務水準協議（SLA）。遇到問題請至 [GitHub 回報](https://github.com/multica-ai/multica/issues)。

企業微信目前只處理文字訊息。語音、圖片和檔案訊息會收到簡短說明，不會轉交給 Agent。

若伺服器已設定物件儲存，Telegram 會將照片、檔案、影片和音訊作為附件交給 Agent，也會把 Agent 產生的檔案傳回聊天。未設定物件儲存時，媒體訊息會收到原有的簡短不支援提示。貼圖等非檔案訊息也會收到該提示，不會轉交給 Agent。

## 訊息處理流程

1. Multica 依 Bot 找到對應的工作區和 Agent。
2. 在群組或頻道中，只有明確 @提及 Bot 的訊息會繼續處理；私訊不需要 @提及。
3. Multica 會確認傳送者的帳號綁定和工作區成員身分。
4. 訊息會進入一段 [Agent 聊天](/chat)，並建立一次執行。
5. Agent 的回覆會送回原本的私訊或討論串。

未 @提及 Bot 的頻道訊息不會觸發 Agent，也不會加入它的對話脈絡。

一般訊息依上述流程處理。`/issue` 是命令，不是聊天回合：Multica 會在原平台回覆處理結果，但不會把命令加入 Multica Chat。Slack 原生斜線命令仍使用獨立的非同步任務建立流程。

## 控制聊天脈絡

`/new` 會建立新的 Multica Chat，並將這段外部聊天之後的訊息導向新 Chat。`/new <訊息>` 會直接以該訊息作為第一則內容。舊 Chat 仍保留在 Multica 中，也可以繼續使用。

`/clear` 不會建立新的 Chat，只會在目前的 Multica Chat 中開啟新的 Agent 可見脈絡。完整聊天紀錄仍保存在 Multica 中，但 Agent 無法讀取界線之前的訊息。`/clear <訊息>` 會以該訊息作為新脈絡的第一則內容；單獨使用 `/clear` 時，新界線會套用到下一則一般訊息。

在 Slack 私訊中，`/new` 和 `/clear` 都是原生斜線命令。原生斜線命令的 payload 無法識別頻道中的目標討論串，因此請在目標討論串中傳送 `@Multica /new [訊息]` 或 `@Multica /clear [訊息]`。

## 工作階段隔離

- 飛書/Lark 依聊天區分工作階段；同一個聊天的後續訊息會延續原工作階段。
- Slack 的私訊依頻道區分；頻道中的每個討論串各自保存工作階段。
- 釘釘依 conversation 區分工作階段；每個單聊或群聊都有自己的工作階段。
- 企業微信依聊天區分工作階段；每個單聊或群聊都有自己的工作階段。
- Telegram 依聊天區分工作階段；forum 中的每個 topic 都彼此隔離。

在頻道中追問時，仍須再次 @提及 Bot。Agent 只會收到傳給自己的訊息，不會自動讀取整個頻道的歷史紀錄。

## 帳號綁定

成員第一次傳訊息給 Bot 時，會收到帳號綁定連結。登入 Multica 後，聊天平台帳號就會連結到目前工作區的成員身分。

完成綁定後，Multica 才會執行 Agent。每則訊息都會重新確認帳號綁定和工作區成員身分；離開工作區後，就不能再透過 Bot 使用該工作區。

<Callout type="info">
帳號綁定只用來確認傳送者身分，不會讓聊天平台上的其他成員自動加入 Multica 工作區。
</Callout>

## 管理連接

工作區 `owner` 和 `admin` 可以連線或中斷 Bot；飛書/Lark Bot 也允許 Agent 擁有者連線或中斷。一般成員可以查看已連線的整合，並使用自己有權執行的 Agent。

中斷連線後，Bot 不會再接收新訊息。既有的 Multica Chat 和執行紀錄仍會保留。

## 自行託管

自行託管的部署必須先為各平台設定 32 位元組的加密金鑰，Multica 才會開放連線入口：

```dotenv
MULTICA_LARK_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
MULTICA_SLACK_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
MULTICA_DINGTALK_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
MULTICA_WECOM_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
MULTICA_TELEGRAM_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
```

這些金鑰用來加密儲存 Bot 憑證。產生、儲存和輪替方式請參閱[環境變數](/environment-variables)。Multica Cloud 已完成設定。

企業微信只有一條訊息送出管道：由單一程序持有的 WebSocket。若回覆是在**其他副本**上產生，能否送達取決於即時中繼（realtime relay）模式：

- **分片或雙中繼模式**（設定了 `REDIS_URL`，也是預設的 Redis 模式）：回覆會轉送給持有連線的副本並送達，**支援多副本部署**。
- **舊版中繼模式或未設定 Redis**：回覆會遭丟棄。此設定下，請讓啟用企業微信的後端維持單一副本。

無論哪種模式，都可能遇到一段所有副本都在重新連線、**沒有副本持有有效連線**的時間；此時產生的回覆不會送達，但會留下紀錄。負責轉送的副本會確認是否有副本接手該筆傳送；若沒有，就會增加 `multica_wecom_outbound_dropped_total{reason="no_live_connection"}` 計數，因此可以量測這段期間的影響。若無法接受這類訊息遺失，最保守的部署方式仍是使用單一副本。

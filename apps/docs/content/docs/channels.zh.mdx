接入聊天工具後，團隊不用開啟 Multica，就能在私聊裡向Agent提問、在群聊中 @ 它，或者直接在聊天視窗建立任務。

目前支援飛書/Lark、Slack、釘釘、企業微信、Telegram 和微信。微信只接收掃碼連接賬號的私聊訊息。它們使用相同的會話、身份和執行機制，但安裝方式不同。

目前只開放連接中國大陸版飛書；既有的國際版 Lark 連線仍可繼續使用和管理。

每個 Bot 都會綁定一個 Multica Agent。若要在同一聊天平台使用多個 Agent，請分別連接不同的 Bot。

釘釘、企業微信和 Telegram [由社群維護](/community-maintained)：會隨每個版本一併發布，但不提供官方服務水準協議（SLA）。遇到問題請至 [GitHub 回報](https://github.com/multica-ai/multica/issues)。

企業微信目前只處理文字訊息。語音、圖片和檔案訊息會收到簡短說明，不會轉交給 Agent。

若伺服器已設定物件儲存，Telegram 會將照片、檔案、影片和音訊作為附件交給 Agent，也會把 Agent 產生的檔案傳回聊天。未設定物件儲存時，媒體訊息會收到原有的簡短不支援提示。貼圖等非檔案訊息也會收到該提示，不會轉交給 Agent。

## 訊息處理流程

1. Multica 依 Bot 找到對應的工作區和 Agent。
2. 在群組或頻道中，只有明確 @提及 Bot 的訊息會繼續處理；私訊不需要 @提及。
3. Multica 會確認傳送者的帳號綁定和工作區成員身分。
4. 訊息會進入一段 [Agent 聊天](/chat)，並建立一次執行。
5. Agent 的回覆會送回原本的私訊或討論串。

沒有 @ Bot 的頻道訊息不會觸發Agent，也不會單獨成為對話的一輪。飛書和 Telegram 會在有人向 Bot 發出指令時，把群裡最近的幾條訊息作為只讀上下文附在這一輪前面，細節見各平臺頁面。

`/issue` 是命令，不算對話的一輪：Multica 按訊息建立任務，負責人是這個 Bot 繫結的Agent，結果回到原來的聊天，命令本身不會出現在 Multica Chat 中。Slack 原生 slash 命令另走一條非同步建立任務的流程。

## 控制聊天脈絡

在私聊中發送 `/help`（Slack 使用 `@Multica /help`），或在群聊、頻道中 @ Bot 併發送 `/help`，即可查看可用命令：`/help`、`/new [訊息]`、`/clear [訊息]` 和 `/issue <標題>`（後續行作為描述）。企業微信和微信（僅私聊）同樣支援。Multica 會直接回復，不建立 Chat 或運行，也不改變當前 Chat。在 Slack 中，`@Multica /help` 列出訊息命令。原生 `/issue <描述>` 走獨立流程，由Agent根據描述建立任務。

`/new` 會建立一個新的 Multica Chat，並把這條外部會話的後續訊息路由到新 Chat。`/new <訊息>` 會同時把訊息作為第一輪。舊 Chat 仍保存在 Multica 中，可以繼續使用。

`/clear` 不會建立新的 Chat，只會在目前的 Multica Chat 中開啟新的 Agent 可見脈絡。完整聊天紀錄仍保存在 Multica 中，但 Agent 無法讀取界線之前的訊息。`/clear <訊息>` 會以該訊息作為新脈絡的第一則內容；單獨使用 `/clear` 時，新界線會套用到下一則一般訊息。

在 Slack 私訊中，`/new` 和 `/clear` 都是原生斜線命令。原生斜線命令的 payload 無法識別頻道中的目標討論串，因此請在目標討論串中傳送 `@Multica /new [訊息]` 或 `@Multica /clear [訊息]`。

## 工作階段隔離

- 飛書/Lark 按聊天區分會話；同一個聊天中的後續訊息會繼續原會話。
- Slack 私聊按頻道區分；頻道中的每個 thread 分別保存一段會話。
- 釘釘按 conversation 區分會話；每個單聊或群聊分別延續自己的會話。
- 企業微信按聊天區分會話；每個單聊或群聊分別延續自己的會話。
- Telegram 按聊天區分會話；forum 的每個 topic 分別隔離。
- 微信按已連接的 Bot 和掃碼賬號保存會話。

在頻道中繼續追問時仍需再次 @ Bot。除了上面提到的近期上下文，Agent不會自動讀取整個頻道的歷史。

## 帳號綁定

微信在掃碼時將微信賬號綁定到發起連接的 Multica 使用者，訊息按該使用者的工作區權限執行。請用自己的賬號掃碼，不要分享二維碼；其他賬號和群聊訊息不會被接收。

對于飛書/Lark、Slack、釘釘、企業微信和 Telegram，成員第一次向 Bot 發訊息時，會收到一個賬號綁定連結。登錄 Multica 後，平台賬號與當前工作區成員關聯。

完成綁定後，Multica 才會執行 Agent。每則訊息都會重新確認帳號綁定和工作區成員身分；離開工作區後，就不能再透過 Bot 使用該工作區。

<Callout type="info">
帳號綁定只用來確認傳送者身分，不會讓聊天平台上的其他成員自動加入 Multica 工作區。
</Callout>

## 管理連接

工作區 owner 和 admin 可以連接或斷開 Bot；飛書/Lark、釘釘和微信的連接和斷開還對Agent所有者開放。普通成員可以查看已經連接的整合並使用自己有權調用的Agent。

中斷連線後，Bot 不會再接收新訊息。既有的 Multica Chat 和執行紀錄仍會保留。

## 自行託管

自行託管的部署必須先為各平台設定 32 位元組的加密金鑰，Multica 才會開放連線入口：

```dotenv
MULTICA_LARK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_SLACK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_DINGTALK_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_WECOM_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_TELEGRAM_SECRET_KEY=<base64 編碼的 32 字節密鑰>
MULTICA_WEIXIN_SECRET_KEY=<base64 編碼的 32 字節密鑰>
```

這些金鑰用來加密儲存 Bot 憑證。產生、儲存和輪替方式請參閱[環境變數](/environment-variables)。Multica Cloud 已完成設定。

企業微信的回覆只能經由某個程序持有的 WebSocket 發出。回覆產生在其他副本上時，結果取決於即時中繼（realtime relay）的模式：

- **分片或雙寫中繼模式**（配置了 `REDIS_URL`，有 Redis 時的預設）：回覆會轉發給持有連線的副本並送達，可以多副本部署。
- **legacy 中繼模式，或沒有 Redis**：回覆會被丟棄。這種配置下請把啟用企業微信的後端保持單副本。

任何模式下都有一個殘留視窗：回覆產生時沒有任何副本持有活連線（全部在重連中），這條回覆不會送達。轉發它的副本事後會確認有沒有副本認領過這次投遞，沒有就給 `multica_wecom_outbound_dropped_total{reason="no_live_connection"}` 加一，所以丟失的頻率可以從這個指標看出來。不能接受這種丟失時，單副本仍是最保守的部署方式。

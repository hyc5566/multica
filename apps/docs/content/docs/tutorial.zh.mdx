Multica 是人和 AI Agent一起工作的平臺。這篇教程從零開始，帶你完整走一遍端到端的工作流：

- 搭建自己的工作區，熟悉 **工作**、**團隊**、**聊天** 與 **自動化** 四個空間
- 連線本機執行時，手動和透過對話建立Agent
- 用任務交付程式碼、檢視實時執行日誌，並用 **環境（Environments）** 一鍵預覽本地頁面
- 把審查反饋寫進指令，讓 **Engineer** 與只讀 **Reviewer** 在同一條時間線上協作
- 把協調工作交給 **小隊（Squad）**，把通用方法沉澱為 **Skills**，把週期檢查交給 **自動化（Autopilot）**

教程以一個攝影師個人作品集網站為示例專案，把 Multica 的核心能力串成一條真實的交付鏈路。

**開始前準備：**

- 一個 Multica 賬號（在 [multica.ai](https://multica.ai) 註冊）
- 一臺安裝並登入了至少一款 AI 程式設計工具的電腦，例如 Claude Code 或 Codex；全部支援的工具見[安裝 AI 程式設計工具](/install-agent-runtime)

## 建立工作區

工作區是團隊工作的地方：任務、專案、Agent和執行記錄都屬於某個工作區。註冊後的引導會帶你建立第一個工作區；如果你是被邀請加入團隊，登入後會直接進入團隊的工作區。

這篇教程新建一個空白工作區來演示。

<Steps>
<Step>

點選最左側應用導航欄頂部的工作區圖示，選擇 **建立工作區**：

![在左側應用導航欄開啟工作區選單並選擇建立工作區](/images/docs/tutorial-create-workspace-menu.webp)

</Step>
<Step>

填寫三項資訊：

- **工作區名稱**：展示給成員，之後可以隨時修改。
- **URL**：工作區地址中的 slug，例如 `multica.ai/personal-site` 中的 `personal-site`，建立後不可修改。
- **任務編號字首**：預設根據 URL 自動生成，建立前可直接修改；設為 `SITE` 後，任務編號會依次為 `SITE-1`、`SITE-2`（之後也可以在設定中修改）。

![建立工作區頁面，填寫名稱、URL 和任務編號字首](/images/docs/tutorial-create-workspace-form.webp)

</Step>
<Step>

建立完成後即進入新工作區。先認識一下介面結構：

- **最左側應用導航欄**：頂部是工作區切換、**新建任務**（`C`）和 **搜尋**（`⌘K`）；中間是四個核心空間——**工作**、**團隊**、**聊天**、**自動化**；底部是幫助、**設定**和個人賬號。
- **工作面板**（緊鄰導航欄）：頂部就是 **收件匣**，往下依次是內建與自定義 **檢視** 以及 **專案**。
- **底部狀態列**：左側顯示正在工作的Agent數量，右側是 **Ask Multica** 快捷聊天入口（快捷鍵 `⌘J`）。

中間的任務列表目前還是空的，接下來幾步我們會讓Agent把它填起來。

![剛建立好的空工作區](/images/docs/tutorial-empty-workspace.webp)

</Step>
</Steps>

## 連線你的電腦

Agent在你連線的電腦上執行工作，呼叫的正是這臺電腦上安裝的 AI 程式設計工具。

教程使用 [Multica Desktop](https://multica.ai/download) 演示：下載並登入後，桌面端會自動啟動daemon、把這臺電腦註冊為執行時，並檢測已安裝的 AI 程式設計工具。在應用導航欄切到 **團隊**，開啟 **資源** 下的 **執行時**，確認電腦已顯示為 **線上**：

![團隊空間下的執行時列表，本機顯示線上](/images/docs/tutorial-runtimes-list.webp)

點進這臺電腦，可以看到檢測出的每一款 AI 程式設計工具及其狀態：

![機器詳情頁，顯示 Claude Code 和 Codex 線上](/images/docs/tutorial-runtime-detail.webp)

不使用桌面端也可以：在 **執行時** 頁面點選右上角 **+**，選擇 **其他機器或伺服器**，按提示在終端執行安裝命令即可；daemon會在後臺常駐執行，詳見[daemon與執行時](/daemon-runtimes)。

## 建立第一個 Agent

Agent是工作區的正式協作者：可以被分配任務、在評論執行緒中回覆，也可以與你一對一對話。我們先建立一個負責日常事務的 helper，後續教程裡的不少配置工作都可以直接交給它。

在 **團隊** 空間點選面板頂部的 **+**（或進入 **全部Agent** 後點選 **新建Agent**）：

<Steps>
<Step>

**選擇執行時**：挑選上一步連線的電腦上處於線上狀態的 AI 程式設計工具，教程使用 **Claude Code**。

</Step>
<Step>

**配置Agent**：填寫核心欄位（也可以點選右上角的 **讓 AI 來寫**，透過 Agent Builder 對話直接生成配置）：

- **名稱**：`Multica helper`
- **描述**：`Handles workspace chores, agent setup, and status updates.`
- **指令**：每次執行時都會提供給Agent，寫清它的職責與邊界：

```text
You are the helper of this workspace.

You handle what members ask for in issues and chat: create or update
issues, adjust statuses, configure agents, squads, skills, and autopilots,
and answer questions about what is going on in the workspace.

Keep replies short. After finishing something, reply with a one-line
summary of what you did. Do not touch code or repositories. If a
request is ambiguous, ask before acting.
```

選擇模型（教程選用 Claude Sonnet），**訪問許可權** 保持預設的 **僅自己可用**。

![建立Agent配置頁，已填寫 Multica helper 的名稱、描述和指令](/images/docs/tutorial-create-agent-form.webp)

</Step>
<Step>

點選 **建立Agent**。進入詳情頁後，**Multica helper** 已顯示為 **線上 · 空閒**，隨時可以接活：

![Agent詳情頁，Multica helper 線上待命](/images/docs/tutorial-agent-detail.webp)

</Step>
</Steps>

## 第二個Agent：透過對話建立

建網站需要一名能寫程式碼的工程師。這次不用再填表單：工作區裡已經有了一名Agent，建立新Agent的操作可以直接在聊天裡交給它透過 CLI 完成。

在应用导航栏切换到 **聊天**，选择 **Multica helper**，让它在同一个 Claude Code 运行时上创建一名叫 **Engineer** 的智能体，模型使用 **Claude Opus 5**，负责建设和维护摄影师个人作品集网站。Multica helper 会在这台电脑上执行创建并回复结果：

![在聊天中让 Multica helper 创建 Engineer 智能体](/images/docs/tutorial-chat-create-engineer.webp)

打开 **团队 → 全部智能体 → Engineer** 确认结果：模型为 `claude-opus-5`，权限为仅所有者可用，指令由 Multica helper 自动生成，后续随时可以调整：

![Engineer 详情页与生成的指令](/images/docs/tutorial-engineer-instructions.webp)

## 準備網站儲存庫

網站程式碼託管在 GitHub 倉庫裡。只要這臺電腦安裝並登入了 [GitHub CLI](https://cli.github.com)（`gh`），建立和註冊倉庫同樣可以交給Agent。

在 **聊天** 中選擇 **Engineer**，讓它用 `gh` 在你的 GitHub 賬號下建立一個名為 `personal-website` 的空倉庫，再透過 `multica repo add` 註冊到當前工作區。Engineer 執行完成後會回覆倉庫地址：

![Engineer 回覆已建立並註冊 personal-website 倉庫](/images/docs/tutorial-chat-create-repo.webp)

點選應用導航欄底部的 **設定** 圖示，開啟 **連線與擴充套件** 下的 **程式碼**。確認 `personal-website` 已出現在 **程式碼倉庫** 列表中，並點選 **連線 GitHub** 完成授權。連線之後：

- 分支名或標題中帶有任務編號（如 `SITE-1`）的 Pull Request 會自動關聯到對應任務；
- PR 的改動行數與 CI 檢查狀態會直接顯示在任務右側欄；
- 關聯 PR 全部合併後，系統可自動把任務移至 **已完成**。

![設定 -> 內碼表面，GitHub 已連線且 personal-website 已註冊](/images/docs/tutorial-repo-settings.webp)

如果沒有安裝 GitHub CLI，也可以自己在 GitHub 建好倉庫後，在同一頁面點 **+ 新增倉庫** 手動繫結。

## 第一項任務：建站

前期準備全部就緒。接下來進入 Multica 的日常協作節奏：把需求寫成 **任務**，交給Agent執行，所有討論、執行記錄和 PR 都沉澱在同一條時間線上。

網站從 shadcn 的 Next.js 官方模板起步，讓 Engineer 在乾淨的技術棧上專注內容與設計。

<Steps>
<Step>

點選應用導航欄頂部的 **新建任務**（快捷鍵 `C`）。預設的 **透過Agent建立** 模式不需要手寫標題：在 **建立者** 裡選擇 **Engineer**，直接把需求寫進輸入框（底部隨時可以 **切換為手動建立**）：

```text
Work in the personal-website repository registered in this workspace.

Start from a template instead of scaffolding from scratch:

pnpm dlx shadcn@latest init --preset b5rR41Mtnc --template next --pointer

Run the command, commit the template as-is, then build on top of it.

The site is for a photographer. It needs:

- Introduction — who I am and what I shoot
- My work — a selection of photos
- Contact — an email link that is easy to find
- Pricing — decide where a pricing table fits and how to present it
- Use placeholder images wherever a photo belongs, and list where I
  should replace them with my own work

Design:

- Pick a style that fits a photography portfolio. It should feel
  refined and understated; express that through layout, typography,
  and spacing, and never use words like "premium" or "high-end"
  in the copy.
- Choose the fonts.

Open a pull request when it is ready.
```

這條需求包含三類關鍵資訊：明確約束（基於指定模板起步）、具體內容清單、以及有意識的留白（版式與字型交給 Engineer 決策）。寫清意圖與邊界，把實現交給Agent。

![新建任務對話方塊的Agent模式，建立者已選 Engineer](/images/docs/tutorial-new-issue-agent-mode.webp)

</Step>
<Step>

提交後，Multica 自動生成標題並建立 `SITE-1`，把負責人設為 **Engineer** 並立刻開始執行，任務狀態變為 **進行中**。任務右側欄集中展示了 **屬性**、**喚醒**、**Pull requests**、**環境** 和 **執行日誌**。

執行期間，可以透過頂部標題旁的 **Engineer is working** 徽章或右側的 **執行日誌** 隨時檢視進展。如果中途發現Agent跑偏了，也不必中斷重來——直接在評論框傳送糾正並選擇 **加入當前執行**，即可在下一步安全邊界[給執行中的Agent插話糾偏](/mentioning-agents#給正在執行的Agent插話)。

![SITE-1 執行中，顯示工作狀態徽章和右側執行日誌](/images/docs/tutorial-issue-engineer-working.webp)

</Step>
<Step>

將滑鼠懸停在 **執行日誌** 中的當前執行上，點選 **檢視完整記錄**，即可看到Agent的每一步操作：文字說明、**Bash** 命令、**Read / Edit** 檔案改動以及耗時。點選右上角的 **ⓘ**，可以檢視本次執行使用的機器、AI 程式設計工具、已下發的 Skills 與工作目錄：

![執行日誌詳情，完整呈現 Engineer 的每一步命令與編輯](/images/docs/tutorial-execution-log.webp)

</Step>
</Steps>

## 驗收與預覽：快捷聊天與本地環境

執行結束後，Engineer 自動將 `SITE-1` 改為 **稽核中**，在任務下發表結構化的完成總結（列出每個佔點陣圖的替換路徑），同時你的 **工作** 面板頂部 **收件匣** 收到新通知：

![SITE-1 稽核中，展示 Engineer 的完成評論與左側收件匣通知](/images/docs/tutorial-issue-review-comment.webp)

驗收時有兩件事要確認：在瀏覽器裡開啟實時頁面看看效果，以及右側欄的 **Pull requests** 為什麼還是空的。不用在任務評論區刷屏，直接用底部狀態列的 **快捷聊天**：

<Steps>
<Step>

點選底部狀態列最右側的 **Ask Multica**（或按 `⌘J` / `⇧⌘J`），選擇 **Engineer**，輸入 `@SITE-1` 帶入當前任務上下文，把兩件事一併問它。

Engineer 直接在浮窗裡回覆：它已經透過 `multica env start web` 啟動了本地預覽服務；至於 PR #1，因為分支名和標題裡漏掉了 `SITE-1` 沒能觸發自動關聯，它已經把編號補進了 PR 標題。

![在 SITE-1 頁面開啟底部狀態列的快捷聊天浮窗與 Engineer 對話](/images/docs/tutorial-chat-ask-in-issue.webp)

</Step>
<Step>

收起浮窗，看 `SITE-1` 的右側欄，兩張新卡片都已經就位：

- **Pull requests**：`#1 Build photographer portfolio website`，顯示 `+648 -14` 改動量以及合併後自動流轉提示（`Moves to Done when #1 merges`）。
- **環境（Environments）**：`Maya's MacBook Pro` 下的 `Web app · Running · localhost:41000`。點選即可在瀏覽器一鍵開啟，也可以在選單裡重啟、停止或檢視實時日誌——詳見[環境文件](/environments)。

![SITE-1 右側欄同時展示關聯 PR 卡片與執行中的本地環境](/images/docs/tutorial-issue-pr-and-env.webp)

</Step>
<Step>

點選 **環境** 裡的 **Web app** 開啟 `http://localhost:41000`，在瀏覽器裡驗收做好的作品集網站：

![本地執行在 localhost:41000 的攝影師作品集首頁](/images/docs/tutorial-site-localhost.webp)

</Step>
</Steps>

## 把反饋寫進指令

這輪驗收暴露出兩個會反覆出現的習慣：提交 PR 時漏帶任務編號導致無法自動關聯；完成後反覆截圖自查拉長了執行時間，而我們更習慣直接透過 **環境** 在瀏覽器裡看效果。

這兩條規則對以後每條任務都適用，最省事的做法是直接固化進 Engineer 的指令。Agent支援用 `multica agent update` 更新自己的配置，在剛才的對話裡直接讓它寫進去即可：

![在聊天中讓 Engineer 用 multica agent update 把兩條規則寫入自身指令](/images/docs/tutorial-chat-update-instructions.webp)

Engineer 完成更新，並坦誠提示了代價：取消截圖自查後，頁面視覺細節需要靠你的瀏覽器驗收把關。開啟 **團隊 → 全部Agent → Engineer**，可以看到新增的 **Working rules** 小節已經生效：

![Engineer 更新後的指令，已包含新增的工作規則](/images/docs/tutorial-engineer-updated-instructions.webp)

調優Agent的核心方法就是如此：只要某個問題會跨任務重複出現，就把它沉澱成一條指令規則。

## 第三個 Agent：Reviewer

Engineer 交付了第一版，但作者自己往往很難發現全部盲區。引入一名獨立上下文、使用不同工具和模型的 **Reviewer** Agent來做程式碼審查。

<Steps>
<Step>

在聊天裡讓 **Multica helper** 建立 **Reviewer**，執行時選 **Codex**、模型選 `gpt-5.6-sol`，指令限定為只讀審查：對照任務需求與程式碼規範檢查 PR diff、按類別輸出帶檔案路徑和行號的發現、執行只讀檢查命令，絕不修改程式碼。開啟 **團隊 → 全部Agent → Reviewer** 確認配置：

![Reviewer 詳情頁，執行在 Codex 與 gpt-5.6-sol 上的只讀審查Agent](/images/docs/tutorial-reviewer-detail.webp)

</Step>
<Step>

審查不需要新建任務，也不用變更負責人。回到 `SITE-1` 的評論框，輸入 `@Reviewer` 請它審查 PR #1。傳送前，輸入框下方會出現觸發預覽（`Reviewer · Will start when sent`），清楚提示傳送後將啟動哪名Agent：

![在 SITE-1 評論框中 @Reviewer，底部顯示實時觸發預覽](/images/docs/tutorial-comment-mention-reviewer.webp)

</Step>
<Step>

Reviewer 返回 **合併前需要修改**，列出兩組共五條具體發現——既包含兩條 Engineer 自己沒注意到的需求偏差（定價表缺少佔位標註、頁尾塞了未核實的 Instagram 連結），也包含三條程式碼規範建議，全部附帶檔案與行號。

在同一條討論執行緒裡 `@Engineer` 讓它逐條修復；Engineer 推送新提交到 PR #1 後，在時間線裡逐項彙報修復結果：

![Reviewer 的結構化審查結論與 @Engineer 接手修復](/images/docs/tutorial-reviewer-findings.webp)

</Step>
<Step>

再次 `@Reviewer` 複查一輪：五條問題全部驗證修復、本地檢查全綠，Reviewer 給出 **Ready to merge** 結論並附帶兩條非阻塞後續建議：

![Reviewer 複查透過，確認可以合併](/images/docs/tutorial-reviewer-recheck.webp)

</Step>
</Steps>

一條任務上現在有兩名專業分工的Agent——Engineer 負責實現與修復，Reviewer 負責把關——在同一條討論執行緒裡高效往復。

## 合併收尾

在評論裡 `@Engineer` 合併 PR #1 並收尾。Engineer 合併至 `main`、清理分支、在主分支重跑構建並彙報結果。右側 PR 卡片變為 **Merged**，本地預覽環境自動停止，`SITE-1` 狀態更新為 **已完成**：

![SITE-1 狀態轉為已完成，PR #1 已合併](/images/docs/tutorial-issue-done.webp)

從需求描述、執行日誌、實時預覽、程式碼審查、修復複查到最終合併，全過程完整沉澱在一條時間線裡。

## 組建小隊

`SITE-1` 的開發審查閉環跑通了，但每次銜接都得由你手動發起：建完 `@Reviewer`、審完 `@Engineer`、修完再 `@Reviewer`。這層協調工作同樣可以交給 **小隊（Squad）**：由一名隊長Agent統籌多名Agent與人類成員。

任務分配給小隊後，隊長負責接管：閱讀需求、用 `@` 提及把活派給合適成員、在成員回覆後自動喚醒並推進下一步，直到全部完成再向你彙報驗收。

把現有分工加一名隊長，組成 **Website Team**：

- **Lead**（新建，Claude Sonnet）：隊長，負責拆解約束、派活給 Engineer 與 Reviewer、推進狀態並彙總交付簡報，自己不改程式碼。
- **Engineer**（已有）：開發實現、修復審查意見、獲批後合併 PR。
- **Reviewer**（已有）：審查每個 PR（只讀）。
- **Maya Lin（你）**：最終產品驗收與合入拍板。

在聊天裡把這套結構連同兩個 Skill（`tdd` 掛給 Engineer、`delivery-brief` 掛給 Lead，下一節展開）和小隊工作流一次性說給 **Multica helper**，它透過 CLI 一步配置完畢：

![Multica helper 一次完成 Website Team 小隊、Lead 與 Skill 繫結](/images/docs/tutorial-helper-create-squad.webp)

開啟 **團隊 → 小隊 → Website Team** 檢查成員名單、角色描述與交付工作流（也可以直接在這個頁面用表單新建或編輯小隊，詳見[小隊文件](/squads)）：

![Website Team 小隊詳情頁，展示隊長、成員、角色與工作流指令](/images/docs/tutorial-squad-detail.webp)

## Skill：可重用的方法

前面把反饋寫進指令，解決的是單個Agent的專屬規則。如果一套方法需要讓多個Agent共享，或者直接複用社群現成經驗，就沉澱為 **Skill**。

Skill 遵循開放的 Agent Skills 規範：以一份 `SKILL.md` 為核心，可附帶參考文件、模板或指令碼。掛載給Agent後，Multica 會在每次執行時自動同步到執行時。開啟 **團隊 → 資源 → Skills**，剛才配置的兩個 Skill 及掛載物件一目瞭然：

![團隊 -> Skills 列表，顯示 delivery-brief 與 tdd 及各自掛載的Agent](/images/docs/tutorial-skills-list.webp)

點進 `tdd`，可以檢視 `SKILL.md` 正文、附帶檔案（`examples/test-first.md`、`references/checklist.md`）、版本記錄與使用它的Agent：

![tdd Skill 詳情頁，展示 SKILL.md、附帶檔案與已掛載的 Engineer](/images/docs/tutorial-skill-detail.webp)

這兩個 Skill 分別規範了“怎麼做”和“怎麼彙報”：

- **tdd**（掛給 Engineer）：先寫失敗測試，再用最小改動讓測試透過，最後整理重構。
- **delivery-brief**（掛給 Lead）：每次驗收匯報第一行直接給結論與下一步動作，緊跟 PR 摘要與需要你拍板的點，未獲批准絕不合並。

點選 **Skills** 頁面右上角的 **+**，可以看到新增 Skill 的四種入口——**手動建立**、**從本地匯入**、**從 URL 匯入**（GitHub、ClawHub、Skills.sh）以及 **從執行時複製**（詳見 [Skills 文件](/skills)）：

![Skills 頁面右上角 + 選單中的四種建立與匯入方式](/images/docs/tutorial-skill-new-modal.webp)

匯入第三方 Skill 前請先審閱其中的檔案：Multica 不對 Skill 做沙盒隔離，內容會原樣交給 AI 程式設計工具執行。

## 第二項任務：交給小隊

現在把一件完整需求交給 **Website Team**：把個人作品集改造成可複用模板——將個人姓名替換為佔位身份 `Alex Rivera`，郵箱替換為 `hello@example.com`，保持原有排版、字型與畫廊結構不變。

按 `C` 開啟 **新建任務**，保持 **透過Agent建立** 模式，在 **建立者** 中選擇 **Website Team**，輸入需求提交。小隊和個人、單個Agent一樣，可以出現在任何負責人位置。

Multica 建立 `SITE-2` 並分配給 **Website Team**。接下來整條鏈路完全由 **Lead** 自動串聯：

1. **Lead** 主動補齊約束（全站 `<title>`、Open Graph 後設資料和 `README.md` 統一替換，並按 `tdd` 補單元測試），然後 `@Engineer` 派活。
2. **Engineer** 先寫測試再實現，提交 PR #2（`SITE-2: Convert portfolio into reusable template`）並回報。
3. **Lead** 自動喚醒，將 PR #2 轉給 `@Reviewer` 審查。
4. **Reviewer** 校驗 diff 與測試全部透過，零發現返回 **Ready to merge**。

![SITE-2 時間線：Lead 派活給 Engineer、Engineer 回報 PR #2、Lead 轉交 Reviewer 並審查透過](/images/docs/tutorial-squad-dispatch.webp)

審查透過後，**Lead** 自動把 `SITE-2` 推進至 **稽核中**，按 `delivery-brief` Skill 的格式向你發出簡潔驗收簡報：首行給出結論並 `@` 提及你，列出 PR 摘要與兩個待確認點，並明確表示未經同意不會合並：

![Lead 在 SITE-2 發出的簡潔交付簡報，@ 提及 Maya 驗收](/images/docs/tutorial-squad-delivery.webp)

從補齊約束、測試驅動開發、PR 審查到驗收簡報，全程無需你手動穿針引線。

## 自動化：Autopilot

前面的每次執行都由你主動觸發：分配任務、評論提及或發起聊天。**自動化（Autopilot）** 補上了定時與 Webhook 觸發能力，讓週期性維護工作自動運轉。

<Steps>
<Step>

在聊天裡讓 **Multica helper** 建立一條每週一早上 9:00 執行的自動化規則，指派給 **Reviewer**，採用 **建立任務** 模式：檢出 `personal-website` 倉庫，只讀巡檢死程式碼、未使用的匯出、過時依賴和型別隱患，並將結果寫進任務評論。

在應用導航欄切換到 **自動化**，點開規則即可看到完整配置——**執行手冊（Runbook）**、定時規則（`0 9 * * 1`、時區與下次執行時間）、執行模式（**建立任務** 或 **僅執行**）；面板左側還提供 **任務喚醒（Issue wakeups）** 檢視，用來管理單條已有任務的定時或事件回撥。

不用等到週一，點選右上角 **立即執行** 馬上試跑一次：

![自動化詳情頁，展示執行手冊、每週一 9:00 定時觸發器與立即執行按鈕](/images/docs/tutorial-autopilot-detail.webp)

</Step>
<Step>

Multica 立刻建立出 `SITE-3` 並喚醒 **Reviewer** 開始只讀巡檢。此後每週一早上九點，同樣的檢查都會自動建單執行：

![自動化建立的 SITE-3 任務，Reviewer 正在執行檢查](/images/docs/tutorial-autopilot-issue.webp)

</Step>
</Steps>

除了定時觸發，自動化同樣支援 GitHub、GitLab 與通用 **Webhook**，執行者也可以直接指向 **小隊**；詳見[自動化文件](/autopilots)和[任務喚醒](/issue-wakeups)。

## 多人協作

到目前為止，工作區裡的人類成員只有你一個。點選 **團隊** 面板頂部的 **邀請成員** 圖示，或開啟 **設定 → 成員**，即可透過郵箱邀請協作者。支援選擇 **成員**、**管理員**，或僅限特定共享專案的免費 **訪客（Guest）** 角色：

![設定 -> 成員中的邀請成員彈窗，支援成員、管理員與訪客角色](/images/docs/tutorial-invite-member.webp)

加入後的同事和你一樣可以建立任務、`@` 提及共享Agent、開啟預覽環境並加入小隊，實現多人與多Agent的協同交付。

## 結語

當任務和專案逐漸增多時，Multica 已經為你準備好了順滑擴充套件這套工作流的結構：

- **四個空間**讓日常關注點清晰分離：**工作**（收件匣、檢視、專案）、**團隊**（Agent、小隊、Skills、執行時、統計）、**聊天** 與 **自動化**。
- **專案（Projects）** 把關聯任務聚合在一起，提供共享背景說明、程式碼倉庫與目錄資源、資料夾歸類、進度預測，以及可按階段自動交接的自定義[工作流（Workflows）](/workflows)。

回頭看走過的完整路徑：從空白工作區起步，連上本機電腦，建起四名分工明確的Agent，用本地環境完成首次 PR 預覽與交付，把經驗固化成指令和可複用 Skill，再把協調交給小隊、把週期巡檢交給自動化。到最後，你需要投入精力的，只剩定方向和做驗收。

Multica 是人和 AI Agent 一起工作的平臺。這篇教程從零開始，帶你：

- 搭建一個自己的工作區
- 實現人與 Agent 的協作，以及 Agent 之間的自動協作
- 把重複的工作交給自動化
- 把有效的做法沉澱為 skill，持續迭代你的 Agent

教程以一個個人網站為示例專案，把 Multica 的整體流程和核心功能完整過一遍。

**開始前準備：**

- 一個 Multica 帳戶（[multica.ai](https://multica.ai) 註冊）
- 一臺安裝並登入了至少一款 AI 編程工具的電腦，例如 Claude Code 或 Codex；全部支援的工具見[安裝 AI 編程工具](/install-agent-runtime)

## 建立工作區

工作區是團隊工作的地方：任務、專案、Agent 都屬於某個工作區。註冊後的引導會帶你建立第一個工作區；如果你是被邀請加入團隊，登入後會直接進入團隊的工作區。

這篇教程新建一個工作區來演示。點擊側邊欄頂部的工作區名稱，選擇 **建立工作區**：

![建立工作區入口](/images/docs/tutorial-create-workspace-menu.webp)

建立時填兩項：

- **名稱**：展示給成員，之後可以修改。
- **工作區 URL**：地址中的 slug，例如 `multica.ai/my-team` 裡的 `my-team`，建立後不可修改。

![建立工作區頁面](/images/docs/tutorial-create-workspace-form.webp)

建立完成後會進入新工作區。左側是側邊欄，之後的操作都從這裡進入；中間的任務列表現在還是空的，接下來幾步就是讓 Agent 來填滿它。

![剛建立好的空工作區](/images/docs/tutorial-empty-workspace.webp)

## 連接你的電腦

Agent 在你連接的電腦上執行工作，用的就是這臺電腦上安裝的 AI 編程工具。

教程用 [Multica Desktop](https://multica.ai/download) 演示：下載並登入後，它會自動把這臺電腦註冊為執行環境，並檢測已安裝的 AI 編程工具。開啟側邊欄底部的 **設定 → 執行環境**，確認這臺電腦已經在線：

![執行環境列表，這臺電腦在線](/images/docs/tutorial-runtimes-list.webp)

點進這臺電腦，可以看到檢測出的每一款工具：

![執行環境詳情，檢測出的 AI 編程工具](/images/docs/tutorial-runtime-detail.webp)

不用 Desktop 也可以：在執行環境頁面點 **新增電腦**，按提示用命令列安裝，守護程序會常駐後臺執行；詳見[守護程序與執行環境](/daemon-runtimes)。

## 建立第一個 Agent

Agent 是工作區的正式成員：可以被分配任務、發表留言、和你對話。第一個 Agent 我們建立一名 helper，負責工作區裡的日常事務，之後教程裡的不少操作都會交給它。

開啟側邊欄的 **Agent**，點 **新建 Agent**，選擇 **從空白開始**，填三項：

- **名稱**：`Multica helper`。
- **執行環境**和**模型**：選擇上一步連接的電腦和一款 AI 編程工具，再從該工具支援的模型裡選一個。教程用 Claude 和 Sonnet。
- **指令**：每次執行時提供給 Agent 的提示詞，寫清它負責什麼、不負責什麼：

```text
You are the helper of this workspace.

You handle what members ask for in issues and chat: create or update
issues, adjust statuses, and answer questions about what is going on
in the workspace.

Keep replies short. After finishing something, reply with a one-line
summary of what you did. Do not touch code or repositories. If a
request is ambiguous, ask before acting.
```

![建立 Agent 頁面](/images/docs/tutorial-create-agent-form.webp)

其餘欄位保持預設，點建立。回到**Agent**頁面，Multica helper 已經在線，可以接受工作了：

![Agent 詳情，Multica helper 在線](/images/docs/tutorial-agent-detail.webp)

## 第二個 Agent：用對話建立

建網站需要一名能寫程式碼的工程師。這次不填表單——工作區裡已經有一個 Agent，建立的事可以直接交給它。

開啟側邊欄的**聊天**，選擇 Multica helper，告訴它：在同一個執行環境上建立一名叫 Engineer 的 Agent，模型用 Opus，負責建設和維護個人網站。Multica helper 會在這臺電腦上執行建立，並回覆新 Agent 的名稱和模型。新 Agent 預設只有建立者可以執行，教程裡保持預設即可。

![聊天中讓 helper 建立 Engineer](/images/docs/tutorial-chat-create-engineer.webp)

開啟**Agent → Engineer** 確認結果：模型是 Opus，指令由 Multica helper 生成——職責範圍、取用倉庫程式碼的方式、提交改動的要求，之後隨時可以修改。

![Engineer 的指令](/images/docs/tutorial-engineer-instructions.webp)

## 準備網站倉庫

網站的程式碼放在 GitHub 倉庫裡。倉庫的建立和綁定同樣交給 Agent——前提是這臺電腦安裝並登入了 [GitHub CLI](https://cli.github.com)。

在**聊天**中選擇 Engineer，告訴它：在我的 GitHub 帳戶下建立一個名為 `personal-website` 的空倉庫（這臺電腦上有 GitHub CLI），然後用 `multica repo add` 註冊進這個工作區。Engineer 會在本地建立倉庫、把它註冊進工作區，並回覆倉庫地址。消息裡沒有指定可見性，它會按預設建立並在回覆裡說明；公開或私有都不影響後續步驟。

![聊天，Engineer 回覆倉庫已建立並註冊](/images/docs/tutorial-chat-create-repo.webp)

開啟**設定 → 程式碼**確認 `personal-website` 已列出。之後 Agent 執行時，從這裡選擇儲存庫。

![設定中的程式碼倉庫列表](/images/docs/tutorial-repo-settings.webp)

不用 GitHub CLI 的話，也可以自己在 GitHub 建立倉庫，在同一頁面手動新增，效果相同。

最後在同一頁面點**連接 GitHub**，按提示授權這個倉庫。連接後，引用了任務編號的 pull request 會自動關聯到對應任務，PR 狀態和 CI 結果直接顯示在任務裡。

## 第一條任務：建站

設定到此全部完成。從這裡開始是 Multica 的日常工作方式：需求寫成任務，交給 Agent 執行。

網站從 shadcn 的官方模板起步，而不是從零搭建：模板已經帶好技術棧和基礎設定，Engineer 在它之上做內容和設計。

點側邊欄頂部的**新建任務**（快捷鍵 `C`）。預設的 Agent 模式下不用填標題——在**建立者**中選擇 Engineer，把需求直接寫進描述，標題在建立時自動生成；也可以切換到手動模式，自行填寫標題和內容。描述：

```text
Work in the personal-website repository registered in this workspace.

Start from a template instead of scaffolding from scratch:

pnpm dlx shadcn@latest init --preset b5rR41Mtnc --template next --pointer

Run the command, commit the template as-is, then build on top of it.

The site is for a photographer. It needs:

- Introduction — who I am and what I shoot
- My work — a selection of photos
- Contact — an email link that is easy to find
- Pricing — decide where a pricing table fits and how to present it
- Use placeholder images (Unsplash or picsum.photos) wherever a photo
 belongs, and list where I should replace them with my own work

Design:

- Pick a style that fits a photography portfolio. It should feel
 refined and understated; express that through layout, typography
 and spacing, and never use words like "premium" or "high-end"
 in the copy.
- Choose the fonts.

Open a pull request when it is ready.
```

這條描述裡有三類資訊：約束（從指定模板開始）、內容要求（逐條列出）、留白（風格交給 Engineer 分析）。要求寫意圖和邊界，實現方式留給 Agent。

![新建任務的 Agent 模式，建立者已選 Engineer](/images/docs/tutorial-new-issue-agent-mode.webp)

提交後，Multica 建立任務（編號 `MUL-1`，標題自動生成），把 Engineer 設為負責人；Engineer 隨即開始執行，狀態轉為「進行中」。任務右側是它的全部動態：狀態、負責人、關聯的 pull request 和執行記錄。

執行需要幾分鐘，進展有兩個入口：標題旁的工作狀態徽章，和右側的**執行日誌**——點開當前這次執行：

![查看進展的兩個入口](/images/docs/tutorial-issue-engineer-working.webp)

執行記錄裡是這次執行的每一步：**Agent** 行是它的說明，**Bash**、**Read**、**Edit** 是它執行的命令和讀寫的檔案。截圖這一刻，它正在給建好的頁面截圖自查，剛發現定價表的分隔線沒有對齊。點右上角的 ⓘ，可以看到這次執行用的電腦、AI 編程工具和工作目錄。

![執行記錄，Engineer 的每一步](/images/docs/tutorial-execution-log.webp)

## 驗收：在任務裡對話

執行結束後，Engineer 把狀態改為「審核中」，通知進入你的收件箱。它在任務裡發表了完成留言，附上做好的頁面截圖：

![Engineer 的完成留言，附頁面截圖](/images/docs/tutorial-issue-review-comment.webp)

截圖能看出大概，驗收還是要在瀏覽器裡點開。網站在你的電腦上構建，讓 Engineer 啟動本地服務就能訪問。另外，右側的 **Pull Request** 區域還是空的——任務裡明確要求了提交 PR，這件事也直接問它。

這次不用留言區。頁面右下角有一個聊天按鈕，工作區的任何頁面都能開啟，和側邊欄的**聊天**是同一個功能：

![右下角的聊天按鈕](/images/docs/tutorial-chat-fab.webp)

點開後選擇 Engineer，輸入 `@` 引用當前任務——對話會帶上這條任務的上下文，把上面兩件事發給它：

![在聊天中引用任務提問](/images/docs/tutorial-chat-ask-in-issue.webp)

Engineer 的回覆分兩部分：本地服務已經啟動，給出訪問地址；PR 其實已經提交了，只是標題、分支名和正文裡都沒有 `MUL-1`，自動關聯匹配不上——它隨後把編號補進了 PR 標題。

![Engineer 的回覆：本地地址和 PR 未關聯的原因](/images/docs/tutorial-chat-engineer-reply.webp)

在瀏覽器開啟它給的地址，看到網站：

![本地執行的網站首頁](/images/docs/tutorial-site-localhost.webp)

回到任務，右側的 **Pull Request** 區域也出現了 PR 卡片，顯示狀態和改動規模，點擊直接開啟 GitHub 上的 PR；設定了 CI 的倉庫還會顯示 check 結果：

![任務右側出現 PR 卡片](/images/docs/tutorial-issue-pr-linked.webp)

## 把反饋寫進指令

這輪驗收暴露了 Engineer 的兩個工作習慣：完成後靠反覆截圖自查，佔掉不少執行時間；提交 PR 時不帶任務編號，關聯不上。兩個都不是這一次的偶然失誤，而是它每次都會重複的做法——要改的不是這條任務，而是它的指令。

指令不用你自己動手改：Agent 可以用 multica CLI 更新自己的設定。繼續在剛才的對話裡告訴 Engineer 這兩條規則——完成後不用截圖自查，驗收在瀏覽器裡進行；PR 的分支名或標題裡必須帶任務編號——並讓它寫進自己的指令：

![讓 Engineer 把規則寫進自己的指令](/images/docs/tutorial-chat-update-instructions.webp)

Engineer 用 `multica agent update` 完成更新，在指令裡新增一節工作規則，並指出第一條的代價：不再截圖自查，頁面上的視覺問題要靠你在瀏覽器裡發現。

開啟**Agent → Engineer**，指令裡已經多出這兩條：

![Engineer 更新後的指令](/images/docs/tutorial-engineer-updated-instructions.webp)

之後每次執行，這兩條規則都會隨指令生效。這也是調優 Agent 的基本方式：發現重複出現的問題，把糾正寫進指令，而不是每次口頭提醒。

## 第三個 Agent：Reviewer

Engineer 交付了第一版，但有些問題它自己意識不到。審查交給一名新的 Agent：全新的上下文，專門對照任務的要求檢查程式碼質量。

建立還是交給 Multica helper：一名叫 Reviewer 的 Agent，這次選 Codex 和 GPT-5.6 Sol 模型，和 Engineer 用的工具、模型都不同；只審查、不改程式碼，結論寫成任務留言。指令依然由 helper 生成——讀取 PR 的真實狀態再審查、發現寫成帶檔案位置的留言、絕不修改程式碼：

![Reviewer 的設定](/images/docs/tutorial-reviewer-detail.webp)

審查不用新開任務，也不用換負責人。回到 MUL-1 的留言框，輸入 `@Reviewer` 提及它，寫上要做的事再傳送——留言框下方會提示：傳送後 Reviewer 就開始執行：

![在留言中 @Reviewer 發起審查](/images/docs/tutorial-comment-mention-reviewer.webp)

幾分鐘後，審查留言回來了，結論是：合併前需要修改。五條發現分成兩組——程式碼規範三條、需求符合度兩條，每條都帶檔案和行號。需求符合度的兩條正是 Engineer 自己意識不到的問題：定價表把虛構的價格、訂金和稅務條款當成正式內容展示，沒有任何待定標註；聯繫方式裡放了一個沒核實過的 Instagram 連結。留言末尾它說明了自己驗證過的部分：typecheck、lint 和 build 都通過。

修復不用新流程：在留言區 @Engineer，讓它把發現的問題都修掉。傳送後 Engineer 隨即開始執行，標題旁的徽章和右側執行記錄裡都能看到：

![Reviewer 的審查結論，@Engineer 繼續修復](/images/docs/tutorial-reviewer-findings.webp)

幾分鐘後 Engineer 回報：五條全部修復，推進同一個 PR。雙方共享同一條時間線，報告只需對著發現逐條說結果，不用重述背景：

![Engineer 的修復報告](/images/docs/tutorial-engineer-fixed.webp)

再提及 Reviewer 複查一輪，結論：五條發現全部解決，可以合併，剩兩條低優先順序的後續建議：

![Reviewer 複查通過](/images/docs/tutorial-reviewer-recheck.webp)

開發和審查就這樣往復：發現問題，修復問題，每一輪都讓網站的定義更確定一點。一條任務上現在有兩名 Agent：Engineer 實現，Reviewer 審查，你用幾條短留言驅動整個循環。

## 合併收尾

合併同樣用一條留言下達：讓 Engineer 合併 PR，並確保任務轉到「已完成」。它合併、刪除分支、在合併後的 main 上重跑檢查，然後回報。任務狀態變成「已完成」，收件箱裡收到完成通知：

![合併完成，任務轉為「已完成」](/images/docs/tutorial-issue-done.webp)

第一條任務到此閉環：從需求描述到上線合併，實現、審查、修復、驗收、合併，全部記錄在同一條時間線裡。

## 組建小隊

MUL-1 的循環跑通了，但每一次銜接都由你發起：驗收後提及 Reviewer，審查後提及 Engineer。協調本身成了你的工作。這層工作也交出去。Multica 為此提供的組織形式是**小隊（squad）**：一組 Agent 和成員的命名集合，由一名隊長 Agent 領導。任務分配給小隊後，接手的是隊長：讀任務、派活、推進狀態；成員有了回覆，它被自動喚醒，決定下一步；收尾時向你彙報交付產物。隊長接手的正是你剛才的角色。

小隊就是已有的分工加一名隊長：

- **Lead**（新建）：隊長，負責管理——分配執行、推進任務狀態、向你彙報交付產物，自己不動手；
- **Engineer**（已有）：開發；
- **Reviewer**（已有）：審查每個 PR；
- **你**：最終驗收。

成員不限於 Agent；每個成員都帶一句角色描述，隊長派活時會參考。

這套設定描述給 Multica helper 就夠了：建立小隊和隊長，成員各司其職，Lead 和 Engineer 各綁定一個 skill（下一節展開），小隊指令寫明工作流——開發派給 Engineer，PR 審查通過才交付，你驗收後由 Engineer 合併。helper 用 CLI 一次完成全部設定：

![helper 一次完成小隊的全部設定](/images/docs/tutorial-helper-create-squad.webp)

開啟側邊欄的**小隊 → Website Team** 檢查結果：隊長、成員和角色描述都在。小隊也可以在這個頁面用表單建立；完整機制見[小隊文件](/squads)：

![小隊詳情頁：隊長、成員和角色](/images/docs/tutorial-squad-detail.webp)

## Skill：可複用的方法

前面把反饋寫進指令，解決的是一個 Agent 的問題——指令只屬於它自己。要讓一套方法被多個 Agent 共享，或者直接借用別人已經寫好的方法，用 **skill**。

Skill 是給 Agent 的知識包：一個 `SKILL.md` 加上可選的支援檔案，告訴 Agent 遇到某類執行該怎麼想、怎麼做。Multica 採用 Anthropic Agent Skills 開放標準，符合規範的 skill 都能直接匯入；掛到 Agent 後，執行時自動同步到執行環境。開啟 **Skills** 頁面，剛才匯入的兩個都在，右側是各自掛載的 Agent：

![工作區的 Skills 頁面](/images/docs/tutorial-skills-list.webp)

點開能看到 skill 的全部檔案：

![tdd skill 的檔案結構](/images/docs/tutorial-skill-detail.webp)

這兩個 skill 一個管做事、一個管說話：

- **tdd** 掛給 Engineer，是工程方法：先寫失敗的測試，再寫恰好讓它通過的實現；
- **i-have-adhd** 掛給 Lead，是彙報風格：第一行永遠是可執行的下一步，多步驟編號，進度可見。隊長的產出全是發給你的彙報，這個 skill 決定你讀到的樣子。

團隊的工作方式沉澱成 skill，新 Agent 掛上就能繼承。匯入也不是唯一來源，**新建 skill** 提供四種方式——手動新建、從本地匯入、從 URL 匯入、從本機執行環境複製——這裡不展開，見 [Skills 文件](/skills)：

![新建 skill 的四種方式](/images/docs/tutorial-skill-new-modal.webp)

匯入第三方 skill 前，先讀一遍它的文件：Multica 不做沙盒隔離，skill 的內容會原樣交給 AI 編程工具。

## 第二條任務：交給小隊

給小隊一件完整的工作：把網站改成通用模板——真實姓名換成佔位的攝影師名字，真實電子郵件換成 `hello@example.com`，佈局和內容結構不動。這次任務不用自己寫：在聊天裡把需求說給 Lead，用**通過 Agent 建立**直接建立，負責人是小隊——小隊和 Agent、成員一樣，可以出現在任何負責人位置：

![在聊天中用「通過 Agent 建立」新建任務](/images/docs/tutorial-create-with-agent.webp)

生成的任務裡，需求已經被整理成結構化描述；標題旁的徽章顯示隊長已經接手：

![MUL-2：Lead 建立任務並開始工作](/images/docs/tutorial-issue-squad-created.webp)

接下來全是隊長的工作。它的派活留言不只是轉發：補上兩條任務裡沒有的約束（佔位身份全站統一、清查範圍列到元資料和 README），再交給 Engineer。Engineer 完成後，把 PR 回報在同一條時間線裡：

![Lead 派活，Engineer 回報 PR](/images/docs/tutorial-squad-dispatch.webp)

審查零發現，Lead 隨即交付：提及你驗收，第一行是結論，往下是 PR 連結、改動說明和兩個需要你判斷的點，結尾一句——你不點頭就不合並：

![Lead 的交付彙報](/images/docs/tutorial-squad-delivery.webp)

從整理需求、確認方案、開發、審查到交付彙報，這條任務沒有一步需要你銜接。驗收方式和 MUL-1 相同——也可以讓它啟動本地服務在瀏覽器裡看，不再展開。「已完成」仍然留給你：回覆合併，或手動改狀態。整條時間線的每一步都有記錄，和人類團隊的任務沒有區別——變的只是執行的人。

## 自動化

到目前為止的每次觸發都由你發起——分配、提及、對話。**自動化**是第四種觸發方式：按時間自動開工。

設定是一句話的事：告訴 Multica helper，每週一早上九點，讓 Reviewer 對網站程式碼庫做一次全面檢查——冗餘和死程式碼、不合理的結構、可以更規範的地方，發現寫進任務留言，不改程式碼：

![helper 建立自動化](/images/docs/tutorial-autopilot-create.webp)

開啟**自動化**頁面，執行者、提示詞和調度（cron + 時區）都已設定好。執行模式有兩種：

- **建立任務**（預設）：每次觸發先建一條任務，工作落在看板上，歷史、留言和普通任務完全一致；
- **僅執行**：不建任務直接執行，只在自動化的執行歷史裡留記錄——這次沒發現問題的話，跑完就什麼都不留。

定期檢查用「建立任務」模式。不想等到週一，點**立即執行**觸發一次：

![自動化詳情頁：調度和立即執行](/images/docs/tutorial-autopilot-detail.webp)

任務隨即建出來，Reviewer 開始檢查。之後每週一到點，同樣的檢查會自動建立新的任務，不再需要任何人觸發：

![自動化建立的任務](/images/docs/tutorial-autopilot-issue.webp)

觸發器除了定時還支援 webhook，執行者也可以指向小隊，見[自動化文件](/autopilots)。

## 多人協作

到這裡，工作區裡的人類成員始終只有你一個。**設定 → 成員**裡用電子郵件邀請其他人加入，他們和你一樣建立任務、@ Agent、加入小隊——多個人和多個 Agent 在同一批任務上協同：

![用電子郵件邀請成員加入工作區](/images/docs/tutorial-invite-member.webp)

## 結語

任務多起來之後還有組織它們的工具：**Project** 把相關的任務歸成一組、當成一個單元跟進（見[專案文件](/projects)）；類似的組織方式還在增加，**Space** 也即將就緒。

回頭看這條路徑：從空工作區開始，連上一臺電腦，建起四名 Agent，跑完兩條任務的完整生命週期，再把協調交給隊長、把週期檢查交給自動化。你的參與逐級後撤，最後只剩兩件事：描述需求，驗收結果。

Agent 是一等成員，一切協作都留在任務的時間線裡——這就是 Multica 提供的工作方式。它還在快速迭代，更多能力見[文件](/)。

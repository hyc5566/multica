自託管 Multica 分成兩部分：

| 部分 | 執行什麼 | 放在哪裡 |
|---|---|---|
| **Multica 服務** | Web、API 和 PostgreSQL | 一臺安裝了 Docker 的機器 |
| **執行電腦** | Multica 守護程序和 AI 編程工具 | 開發者實際工作的電腦 |

它們可以是同一臺機器，也可以分開。自託管替換的只是 Multica Cloud 部分。

這篇文件使用 Docker Compose。Kubernetes 部署見倉庫中的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

## 開始前

執行 Multica 服務的機器需要：

- Docker Engine 或 Docker Desktop，並且 `docker compose` 可以執行
- Git、Make、curl 和 OpenSSL
- 本機的 `3000`、`8080` 端口未被佔用

先確認 Docker 和 Compose 可用：

```bash
docker info
docker compose version
```

Multica 使用 Compose v2，也就是 `docker compose`。舊版的 `docker-compose` v1 不受支援。

執行電腦還需要至少一款已經安裝並登入的 [AI 編程工具](/providers)，例如 Claude Code、Codex 或 Cursor。第 5 步再安裝 Multica CLI。

## 1. 啟動 Multica

在準備執行服務的機器上執行：

```bash
git clone --depth 1 https://github.com/multica-ai/multica.git
cd multica
make selfhost
```

第一次執行環境，`make selfhost` 會：

1. 從 `.env.example` 建立 `.env`
2. 隨機生成 `JWT_SECRET`、PostgreSQL 密碼和 `MULTICA_VCS_SECRET_KEY`（自託管 Git 整合的加密密鑰）
3. 拉取 PostgreSQL、Multica backend 和 Multica frontend 鏡像
4. 建立持久化資料卷並啟動三個容器
5. 等待 backend 開始響應健康檢查

之後再次執行 `make selfhost` 會繼續使用現有的 `.env` 和資料卷，不會重新生成密鑰。

<Callout type="info">
`make selfhost` 拉取已發佈的鏡像，不會編譯當前 checkout 中的程式碼。需要測試本地原始碼時，使用 `make selfhost-build`。

已發佈的鏡像跟隨最新的 **release tag**，而直接 `git clone` 檢出的是 `main`，通常領先於發版。如果你要在這個 checkout 上構建任何東西——CLI，或通過 `make selfhost-build` 構建鏡像——先切換到與鏡像對應的 release tag，讓構建產物和執行中的容器保持同一版本：

```bash
git fetch --tags --depth 1
git checkout $(git tag -l 'v*' --sort=-v:refname | head -1)
```
</Callout>

## 2. 確認服務已經就緒

查看容器狀態：

```bash
docker compose -f docker-compose.selfhost.yml ps
```

`postgres` 顯示為 `healthy`，`backend` 和 `frontend` 應處於執行狀態。然後檢查 backend、資料庫和 migration：

```bash
curl -fsS http://localhost:8080/readyz
```

正常響應是：

```json
{"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

Backend 容器每次啟動時都會先執行資料庫 migration，再啟動服務，不需要手動執行 migration 命令。

## 3. 選擇訪問方式

### 本機訪問

直接開啟 [http://localhost:3000P172。後面執行 `multica setup self-host` 時也不需要傳 URL。

### 遠端訪問

Docker Compose 預設只把 `3000` 和 `8080` 綁定到 `127.0.0.1`。不要直接改成 `0.0.0.0` 暴露到公網；使用帶 HTTPS 的反向代理。

下面以兩個域名為例：

- `app.example.com`：Multica Web
- `api.example.com`：API、健康檢查和守護程序連接

先在 `.env` 中設定公開地址：

```bash
FRONTEND_ORIGIN=https://app.example.com
MULTICA_APP_URL=https://app.example.com
MULTICA_PUBLIC_URL=https://api.example.com
```

以上設定讓瀏覽器流量全部走 app 域，cookie 不跨域，因此不需要設定 `COOKIE_DOMAIN`。如果改為讓瀏覽器直接訪問 api 域，則必須設定它，見[環境變數](/environment-variables)。

然後設定 DNS，並用 Caddy 代理本機端口：

```text
app.example.com {
 # Route browser WebSocket traffic directly to the backend
 @ws path /ws /ws/*
 handle @ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # Route other paths to the frontend, which forwards API and sign-in requests
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}

api.example.com {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
}
```

如果想讓所有流量走**單一 origin**（一個域名，或一臺主機一個端口——小伺服器上常見），把守護程序依賴的路徑顯式轉給 backend，其餘交給 frontend：

```text
multica.example.com {
 # CLI reachability check: `multica setup` GETs <server-url>/health and expects 200.
 # Older frontend versions do not forward this path, so route it directly to the backend.
 handle /health {
 reverse_proxy 127.0.0.1:8080
 }

 # Web realtime WebSocket: the frontend mirror cannot proxy WS upgrades, so route directly to the backend.
 handle /ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # Daemon long connection: it dials {server-url}/api/daemon/ws (not /ws).
 # Without this route, the daemon silently falls back to polling after the handshake fails.
 handle /api/daemon/ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # Route other paths to the frontend, which forwards API and sign-in requests
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}
```

單一 origin 模式下，兩個 URL 都指向它（`.env` 裡的 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL`，以及 `multica setup self-host` 的 `--server-url` 和 `--app-url`）。

Caddy 會申請 TLS 證書並轉發 WebSocket。修改 `.env` 後，用 `up -d` 重新建立容器，讓新設定生效：

```bash
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | grep -o '"daemon_server_url":"[^"]*"'
```

最後一條命令輸出 `daemon_server_url`——daemon 連接 API 用的地址：設了 `MULTICA_DAEMON_SERVER_URL` 時用它，其次是 `MULTICA_PUBLIC_URL`，否則用 app URL（`MULTICA_APP_URL`，未設定時回退到 `FRONTEND_ORIGIN`）。當 `MULTICA_APP_URL` 和 `FRONTEND_ORIGIN` 都沒設時，這個欄位會整個從響應裡省略（上面的 grep 無輸出）——即使設了 `MULTICA_DAEMON_SERVER_URL` 或 `MULTICA_PUBLIC_URL` 也是如此。如果輸出的是 `localhost`，說明 `.env` 裡還是本地預設值：不要依賴從 `.env.example` 複製來的 `${FRONTEND_PORT}` 引用，把 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL` 顯式設定為公網地址，然後重建容器。

<Callout type="warning">
`docker compose restart` 只重啟現有容器，不會重新讀取 `.env`。修改設定後，重新讀取 `.env` 需要執行 `docker compose -f docker-compose.selfhost.yml up -d`。
</Callout>

## 4. 登入並建立工作區

開啟本機的 `http://localhost:3000`，或剛才設定的 `https://app.example.com`，輸入電子郵件獲取驗證碼。

預設沒有設定郵件服務。請求驗證碼後，可以從 backend 日誌中讀取：

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
 | grep "Verification code"
```

日誌中會出現類似內容：

```text
[DEV] Verification code for you@example.com: 123456
```

輸入驗證碼並建立第一個工作區。設定 Resend 或 SMTP 後，驗證碼通過郵件傳送，成員無需讀取容器日誌，具體見[登入與註冊設定](/auth-setup)。

<Callout type="warning">
自託管部署預設使用 `APP_ENV=production`，不會啟用固定驗證碼。不要在公網實例上設定 `MULTICA_DEV_VERIFICATION_CODE`。
</Callout>

## 5. 連接執行電腦

下面的命令在**執行 AI 編程工具的電腦**上執行，不一定是執行 Docker 的伺服器。

<Callout type="warning">
每次執行都擁有守護程序所屬使用者的全部權限——該使用者能讀寫的一切，執行都能讀寫。請用專用 Unix 使用者、容器或虛擬機來執行守護程序，而不是你的個人帳戶。詳見[安全模型](/security-model)。
</Callout>

先安裝 Multica CLI：

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

**Windows PowerShell**

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

如果 Multica 服務也在這臺電腦上，執行：

```bash
multica setup self-host
```

如果 Multica 服務在另一臺機器上，傳入剛才設定的兩個地址：

```bash
multica setup self-host \
 --server-url https://api.example.com \
 --app-url https://app.example.com
```

這條命令會先檢查 `<server-url>/health`，再開啟瀏覽器完成登入。登入完成後，它會儲存本機憑據並啟動守護程序。這一步報 `Server not reachable`，說明 `/health` 沒有通過探測拿到 200：可能是代理把所有流量轉給了不轉發該路徑的舊版 frontend，可能是代理根本沒把 `/health` 路由到 backend，也可能是更底層的問題（DNS、TLS、防火牆、超時、backend 返回 5xx）——見[故障排查](/troubleshooting#multica-setup-報告伺服器不可達)。

確認連接狀態：

```bash
multica daemon status
```

正常情況下，輸出中會顯示：

- `Daemon: running`
- `Agents` 中包含本機已安裝的 AI 編程工具
- `Workspaces` 大於 `0`

## 6. 完成第一次執行

回到 Multica。執行環境列表中出現在線的執行環境後，建立一個 Agent，並把第一個任務分配給它。

執行日誌變為"已完成"、時間線中出現 Agent 的回覆，說明自託管服務、執行電腦和 AI 編程工具已經連通。詳細步驟見[快速上手](/cloud-quickstart)第 3-5 步。

## 常用管理命令

以下命令都在 `multica` 倉庫目錄中執行：

```bash
# Check status
docker compose -f docker-compose.selfhost.yml ps

# View backend logs
docker compose -f docker-compose.selfhost.yml logs -f backend

# Apply .env changes
docker compose -f docker-compose.selfhost.yml up -d

# Stop services and keep data volumes
docker compose -f docker-compose.selfhost.yml down
```

升級已發佈的鏡像：

```bash
git pull --ff-only
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS http://localhost:8080/readyz
```

Docker Compose 部署有兩種升級寫法。在已有部署上兩者**結果相同**——`Makefile` 裡的 `selfhost` target 跑的就是同一套 `docker compose pull` + `up -d`，只是額外多做了兩件事：`.env` 缺失時生成一份，以及等 `/health` 就緒後打印一段狀態彙總。用哪個都行：

```bash
cd multica
git pull
make selfhost
```

```bash
cd multica
git pull
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

### `git pull` 到底更新了什麼

`git pull` 更新的是 **`docker-compose.selfhost.yml` 本身**——新增的環境變數、新增的服務、改過的 healthcheck。它**不是**拉新版本 Multica 的機制。

真正決定你跑哪個版本的是 `docker compose pull`：它去 GHCR 查這個 tag 當前指向哪個鏡像。所以一個幾個月沒更新的 checkout 照樣能拉到今天的 `latest` 鏡像；反過來，只跑 `git pull` 而不拉鏡像、不重建容器，什麼都不會變。

<Callout type="warning">
**如果你在 `.env` 裡釘死了 `MULTICA_IMAGE_TAG`，兩種寫法都升不上去。** 兩個鏡像都寫成 `${MULTICA_IMAGE_TAG:-latest}`（`docker-compose.selfhost.yml`：`services.backend.image`、`services.frontend.image`），而 `.env.example` 裡預設是 `MULTICA_IMAGE_TAG=latest`。一旦你把它改成了具體版本，`pull` 只是把同一個 tag 重拉一遍，版本原地不動——不報錯，也沒有任何警告。升級前先確認：

```bash
grep MULTICA_IMAGE_TAG .env
# MULTICA_IMAGE_TAG=v0.4.5 is pinned; change it to latest (or your preferred version) first.
```
</Callout>

### `.env` 不會被覆蓋

`make selfhost` 只在 `.env` **不存在**的時候才生成它。在已有部署上重複跑，你的 `JWT_SECRET`、Postgres 密碼、郵件設定、`FRONTEND_ORIGIN` 都原樣保留。

### 升級前先備份 Postgres

migration 只往前走、不回滾，所以正式環境升級前先導一份：

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
 pg_dump -U multica multica > multica-backup.sql && gzip multica-backup.sql
```

<Callout type="warning">
**不要把 `pg_dump` 直接管道接給 `gzip`。** shell 取的是管道里**最後一條**命令的退出碼，所以 `pg_dump ... | gzip > backup.sql.gz` 在匯出失敗時照樣返回 `0`，留下一個格式完全合法、但裡面什麼都沒有的 20 字節壓縮包。先重定向到文件，`pg_dump` 自己的退出碼才算數，`&&` 也只會壓縮真正成功的那份匯出。
</Callout>

如果你改過 `POSTGRES_USER` / `POSTGRES_DB`，把 `multica` 換成 `.env` 裡的實際值。資料存在名為 `multica_pgdata` 的 volume 裡，`docker compose down` 不會刪它——但 `down -v` 會。

### migration 自動執行

和[第 1 步](#1-啟動-multica)一樣，backend 容器啟動時會在對外提供服務之前先跑 `./migrate up`（`docker/entrypoint.sh`）。沒有單獨的升級命令——把新鏡像起起來，本身就是升級這一步。想看過程：

```bash
docker compose -f docker-compose.selfhost.yml logs -f backend
```

Migration 在 backend 啟動時自動執行；需要回填歷史資料的 migration（如 103）也會自動完成回填。自動回填極少數情況下失敗，報 `refusing to drop legacy daily rollups`，處理見[故障排查](/troubleshooting#升級時-migration-103-拒絕執行)。

### 用 `/readyz` 驗證，不要用 `/health`

`/health` 是 **liveness** 探針，只要程序還活著就返回 `{"status":"ok"}`，migration 失敗了它照樣是 ok。`/readyz`（`server/cmd/server/router.go` 中註冊的 `readyHandler`，`/healthz` 是它的別名）會真正檢查資料庫和已應用的 migration 集合，升級出問題能被它攔下來：

```bash
curl -s localhost:8080/readyz
# {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

只要不是 HTTP 200 且兩項都是 `ok`，就說明新版本沒把 migration 跑完，先去看 backend 日誌，別急著放流量進來。

### Kubernetes

Helm 有自己的升級路徑：在 values 檔案裡把 `images.backend.tag` / `images.frontend.tag` 設成你要的版本，然後 `helm upgrade`。改 tag 就改了 pod spec，Kubernetes 會拉新鏡像並滾動更新——這是可靠的路徑。

`kubectl -n multica rollout restart` 本身**不是**升級。chart 預設 `pullPolicy: IfNotPresent`（`deploy/helm/multica/values.yaml`），節點上已經緩存過這個 tag 的話，restart 只會用回舊鏡像，什麼都沒變——和釘死 `MULTICA_IMAGE_TAG` 是同一類坑。真要靠浮動 tag 走這條路，得先把 `images.backend.pullPolicy` / `images.frontend.pullPolicy` 設成 `Always`。詳見倉庫的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

<Callout type="warning">
`docker compose down` 會保留 `pgdata` 和 `backend_uploads`。加上 `-v` 會刪除這些資料卷，包括資料庫；除非確定要清空實例，否則不要執行 `docker compose down -v`。
</Callout>

## 常見問題

| 現象 | 先檢查什麼 |
|---|---|
| `/readyz` 沒有返回 `ok` | 執行 `docker compose -f docker-compose.selfhost.yml logs backend postgres`。 |
| 收不到驗證碼 | 請求一次驗證碼，再從 backend 日誌中查找 `Verification code`。 |
| `setup self-host` 提示 server 不可達 | 在執行電腦上請求 `https://api.example.com/health`，確認 DNS、TLS 和反向代理都可達。返回 404 說明代理把 `/health` 轉給了不轉發該路徑的舊版 frontend——改為直通 backend（見[故障排查](/troubleshooting#multica-setup-報告伺服器不可達)）。 |
| 守護程序沒有列出 `Agents` | 確認 AI 編程工具在 `PATH` 中並已登入，然後執行 `multica daemon restart`。 |
| 任務一直排隊 | 執行 `multica daemon status`，確認守護程序正在執行並連接了工作區。 |

更多情況見[故障排查](/troubleshooting)。

自架 Multica 分成兩部分：

| 部分 | 執行內容 | 部署位置 |
|---|---|---|
| **Multica 服務** | Web、API 和 PostgreSQL | 一台安裝了 Docker 的機器 |
| **執行電腦** | Multica 常駐程式和 AI 程式開發工具 | 開發者實際工作的電腦 |

服務和執行電腦可以是同一台機器，也可以分開部署。自架只會取代 Multica Cloud 服務。

這篇文件使用 Docker Compose。Kubernetes 部署見倉庫中的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

## 開始前

執行 Multica 服務的機器需要：

- Docker Engine 或 Docker Desktop，並且 `docker compose` 可以執行
- Git、Make、curl 和 OpenSSL
- 本機的 `3000`、`8080` 連接埠未被占用

先確認 Docker 和 Compose 可正常使用：

```bash
docker info
docker compose version
```

Multica 使用 Compose v2，也就是 `docker compose`。舊版的 `docker-compose` v1 不受支援。

執行電腦還需要至少安裝並登入一款 [AI 程式開發工具](/providers)，例如 Claude Code、Codex 或 Cursor。Multica CLI 會在第 5 步安裝。

## 1. 啟動 Multica

在準備執行服務的機器上執行：

```bash
git clone --depth 1 https://github.com/multica-ai/multica.git
cd multica
make selfhost
```

首次執行 `make selfhost` 時，會：

1. 從 `.env.example` 建立 `.env`
2. 隨機生成 `JWT_SECRET`、PostgreSQL 密碼和 `MULTICA_VCS_SECRET_KEY`（自架 Git 集成的加密密鑰）
3. 拉取 PostgreSQL、Multica backend 和 Multica frontend 映像檔
4. 建立持久化資料卷並啟動三個容器
5. 等待 backend 開始響應健康檢查

之後再次執行 `make selfhost` 時，會沿用現有的 `.env` 和資料卷，不會重新產生密鑰。

<Callout type="info">
`make selfhost` 會下載已發佈的映像檔，不會建置目前 checkout 中的程式碼。若要測試本機原始碼，請使用 `make selfhost-build`。

已發佈的映像檔會跟隨最新的 **release tag**；直接執行 `git clone` 則會檢出 `main`，通常比最新發行版更新。如果要從這個 checkout 建置任何項目（CLI 或透過 `make selfhost-build` 建置的映像檔），請先切換至對應的 release tag，確保建置產物和執行中的容器版本一致：

```bash
git fetch --tags --depth 1
git checkout $(git tag -l 'v*' --sort=-v:refname | head -1)
```
</Callout>

## 2. 確認服務已經就緒

查看容器狀態：

```bash
docker compose -f docker-compose.selfhost.yml ps
```

`postgres` 應顯示為 `healthy`，而 `backend` 和 `frontend` 應在執行中。接著檢查 backend、資料庫和 migration：

```bash
curl -fsS http://localhost:8080/readyz
```

正常響應是：

```json
{"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

Backend 容器每次啟動時都會先執行資料庫 migration，再提供服務，因此不必手動執行 migration 命令。

## 3. 選擇存取方式

### 本機存取

直接開啟 [http://localhost:3000](http://localhost:3000)。稍後執行 `multica setup self-host` 時也不必傳入 URL。

### 遠端存取

Docker Compose 預設只會將 `3000` 和 `8080` 綁定至 `127.0.0.1`。請勿直接改為 `0.0.0.0` 並暴露到公網；請改用支援 HTTPS 的反向代理。

下面以兩個域名為例：

- `app.example.com`：Multica Web
- `api.example.com`：API、健康檢查和常駐程式連接

先在 `.env` 中設定公開位址：

```bash
FRONTEND_ORIGIN=https://app.example.com
MULTICA_APP_URL=https://app.example.com
MULTICA_PUBLIC_URL=https://api.example.com
```

這些設定會讓瀏覽器流量全部經過 app 網域，cookie 不會跨網域傳送，因此不必設定 `COOKIE_DOMAIN`。若改為讓瀏覽器直接連線至 api 網域，就必須設定該變數，請參閱[環境變數](/environment-variables)。

然後設定 DNS，並用 Caddy 代理本機連接埠：

```text
app.example.com {
    # 將瀏覽器的 WebSocket 直接轉送至 backend
 @ws path /ws /ws/*
 handle @ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

    # 其他路徑交由 frontend 處理；它會轉送 API 和登入請求
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}

api.example.com {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
}
```

如果想讓所有流量走**單一 origin**（一個域名，或一台主機一個連接埠——小伺服器上常見），把常駐程式依賴的路徑顯式轉給 backend，其餘交給 frontend：

```text
multica.example.com {
    # CLI 連線測試：`multica setup` 會對 <server-url>/health 發出 GET，並要求回應 200。
    # 舊版 frontend 不會轉送此路徑，因此直接路由至 backend。
 handle /health {
 reverse_proxy 127.0.0.1:8080
 }

    # 網頁端即時 WebSocket：frontend 映像檔無法代理 WS 升級，因此直接轉送至 backend。
 handle /ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

    # daemon 長連線使用 {server-url}/api/daemon/ws（不是 /ws）。
    # 若缺少這條路由，握手失敗後 daemon 會無提示地改用輪詢。
 handle /api/daemon/ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

    # 其他路徑交由 frontend 處理；它會轉送 API 和登入請求
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}
```

在單一 origin 模式下，兩個 URL 都應指向同一個位址（`.env` 中的 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL`，以及 `multica setup self-host` 的 `--server-url` 和 `--app-url`）。

Caddy 會申請 TLS 憑證並轉送 WebSocket。修改 `.env` 後，請執行 `up -d` 重新建立容器，套用新設定：

```bash
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | grep -o '"daemon_server_url":"[^"]*"'
```

最後一條命令會輸出 `daemon_server_url`，也就是 daemon 連線至 API 時使用的位址。若設定了 `MULTICA_DAEMON_SERVER_URL`，就使用該值；其次使用 `MULTICA_PUBLIC_URL`；否則使用 app URL（`MULTICA_APP_URL`，未設定時回退至 `FRONTEND_ORIGIN`）。若 `MULTICA_APP_URL` 和 `FRONTEND_ORIGIN` 都未設定，回應中會完全省略這個欄位（因此 grep 不會輸出內容），即使設定了 `MULTICA_DAEMON_SERVER_URL` 或 `MULTICA_PUBLIC_URL` 也一樣。若輸出 `localhost`，表示 `.env` 仍使用本機預設值：請勿依賴從 `.env.example` 複製的 `${FRONTEND_PORT}` 引用，應明確將 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL` 設為公開位址，再重建容器。

<Callout type="warning">
`docker compose restart` 只會重新啟動現有容器，不會重新讀取 `.env`。修改設定後，請執行 `docker compose -f docker-compose.selfhost.yml up -d`，讓容器重新讀取 `.env`。
</Callout>

## 4. 登入並建立工作區

開啟本機的 `http://localhost:3000`，或剛才設定的 `https://app.example.com`，輸入電子郵件地址以取得驗證碼。

預設未設定電子郵件服務。要求驗證碼後，可從 backend 日誌中查看：

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
 | grep "Verification code"
```

日誌中會出現類似內容：

```text
[DEV] Verification code for you@example.com: 123456
```

輸入驗證碼並建立第一個工作區。設定 Resend 或 SMTP 後，驗證碼會透過電子郵件寄送，成員便不必查看容器日誌。詳情請參閱[登入與註冊設定](/auth-setup)。

<Callout type="warning">
自架部署預設使用 `APP_ENV=production`，不會啟用固定驗證碼。請勿在公開執行個體上設定 `MULTICA_DEV_VERIFICATION_CODE`。
</Callout>

## 5. 連接執行電腦

以下命令請在**執行 AI 程式開發工具的電腦**上執行，不一定是在執行 Docker 的伺服器上。

<Callout type="warning">
每次執行都會取得常駐程式所屬使用者的完整權限，也就是說，該使用者能讀寫的所有內容，執行都能讀寫。請使用專用 Unix 使用者、容器或虛擬機器執行常駐程式，而非個人帳號。詳情請參閱[安全模型](/security-model)。
</Callout>

先安裝 Multica CLI：

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

**Windows PowerShell**

```powershell
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

如果 Multica 服務也在這台電腦上，請執行：

```bash
multica setup self-host
```

如果 Multica 服務在另一台機器上，傳入剛才設定的兩個地址：

```bash
multica setup self-host \
 --server-url https://api.example.com \
 --app-url https://app.example.com
```

此命令會先檢查 `<server-url>/health`，再開啟瀏覽器完成登入。登入後會儲存本機憑證並啟動常駐程式。如果此步驟顯示 `Server not reachable`，表示 `/health` 探測未取得 200 回應。可能是代理將所有流量轉給不會轉送該路徑的舊版 frontend、代理根本未將 `/health` 路由至 backend，或發生較底層的問題（DNS、TLS、防火牆、逾時、backend 回傳 5xx）。請參閱[疑難排解](/troubleshooting#multica-setup-報告伺服器不可達)。

確認連接狀態：

```bash
multica daemon status
```

正常情況下，輸出中會顯示：

- `Daemon: running`
- `Agents` 中包含本機已安裝的 AI 程式開發工具
- `Workspaces` 大於 `0`

## 6. 完成第一次執行

回到 Multica。執行環境列表中出現上線的執行環境後，建立一個 Agent，並將第一個任務指派給它。

執行記錄顯示"已完成"，且時間軸出現 Agent 的回覆，就表示自架服務、執行電腦和 AI 程式開發工具已連線。詳細步驟請參閱[快速入門](/cloud-quickstart)第 3 至 5 步。

## 常用管理命令

以下命令都要在 `multica` 儲存庫目錄中執行：

```bash
# 檢查狀態
docker compose -f docker-compose.selfhost.yml ps

# 查看 backend 日誌
docker compose -f docker-compose.selfhost.yml logs -f backend

# 套用 .env 變更
docker compose -f docker-compose.selfhost.yml up -d

# 停止服務並保留資料卷
docker compose -f docker-compose.selfhost.yml down
```

若要升級至最新發佈的映像檔：

```bash
git pull --ff-only
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS http://localhost:8080/readyz
```

Docker Compose 部署有兩種升級方式。在既有部署上，兩者的**結果相同**：`Makefile` 中的 `selfhost` target 會執行相同的 `docker compose pull` + `up -d`，並額外在 `.env` 不存在時建立該檔案，以及等到 `/health` 就緒後輸出狀態摘要。你可以選擇任一方式：

```bash
cd multica
git pull
make selfhost
```

```bash
cd multica
git pull
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

### `git pull` 實際更新了什麼

`git pull` 更新的是 **`docker-compose.selfhost.yml` 檔案本身**，例如新增的環境變數、新增的服務或變更過的 health check。它**不是**取得新版 Multica 的方式。

實際執行的版本由 `docker compose pull` 決定：該命令會向 GHCR 查詢這個 tag 目前指向的映像檔。因此，即使 checkout 幾個月沒有更新，仍可下載今天的 `latest` 映像檔；反過來說，只執行 `git pull`，卻不下載映像檔或重建容器，任何執行中的內容都不會改變。

<Callout type="warning">
**如果你在 `.env` 中固定了 `MULTICA_IMAGE_TAG`，以上兩種方式都不會升級。** 兩個映像檔都使用 `${MULTICA_IMAGE_TAG:-latest}`（`docker-compose.selfhost.yml` 中的 `services.backend.image` 和 `services.frontend.image`），而 `.env.example` 預設設定為 `MULTICA_IMAGE_TAG=latest`。若你將它改為特定版本，`pull` 只會重新下載相同 tag，版本不會更新，也不會顯示錯誤或警告。升級前請先確認：

```bash
grep MULTICA_IMAGE_TAG .env
# MULTICA_IMAGE_TAG=v0.4.5 ← 已固定版本：先改成 latest（或你要使用的版本）
```
</Callout>

### `.env` 不會被覆蓋

`make selfhost` 只會在 `.env` **不存在**時建立該檔案。在既有部署上再次執行時，你的 `JWT_SECRET`、Postgres 密碼、電子郵件設定和 `FRONTEND_ORIGIN` 都會原樣保留。

### 升級前先備份 Postgres

migration 只會向前套用，不會回滾，因此升級正式環境前請先匯出資料庫備份：

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
 pg_dump -U multica multica > multica-backup.sql && gzip multica-backup.sql
```

<Callout type="warning">
**不要將 `pg_dump` 直接以管線接到 `gzip`。** shell 會回報管線中**最後一個**命令的結束狀態，因此即使匯出失敗，`pg_dump ... | gzip > backup.sql.gz` 仍會回傳 `0`，留下格式有效、內容卻是空的 20 位元組壓縮檔。請先將輸出重新導向至檔案，這樣才能以 `pg_dump` 自己的結束狀態判斷是否成功；`&&` 也只會壓縮成功匯出的檔案。
</Callout>

若你修改過 `POSTGRES_USER` / `POSTGRES_DB`，請將 `multica` 替換為 `.env` 中的實際值。資料儲存在名為 `multica_pgdata` 的 volume 中；`docker compose down` 不會刪除它，但 `down -v` 會。

### migration 自動執行

如同[第 1 步](#1-啟動-multica)，backend 容器會在開始提供服務前，於啟動時執行 `./migrate up`（`docker/entrypoint.sh`）。沒有獨立的升級命令；啟動新版映像檔本身就是 migration 步驟。若要查看執行過程：

```bash
docker compose -f docker-compose.selfhost.yml logs -f backend
```

Migration 會在 backend 啟動時自動執行；需要回填歷史資料的 migration（例如 103）也會自動完成回填。少數情況下，自動回填可能因 `refusing to drop legacy daily rollups` 而失敗，處理方式請參閱[疑難排解](/troubleshooting#升級時-migration-103-拒絕執行)。

### 用 `/readyz` 驗證，不要用 `/health`

`/health` 是 **liveness** 探針；只要程序仍在執行，就會回傳 `{"status":"ok"}`，即使 migration 失敗也一樣。`/readyz`（在 `server/cmd/server/router.go` 註冊的 `readyHandler`；`/healthz` 是它的別名）則會實際檢查資料庫和已套用的 migration，因此能在升級出問題時發出警示：

```bash
curl -s localhost:8080/readyz
# {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

只要回應不是 HTTP 200，或兩項檢查不是都顯示 `ok`，就表示新版尚未完成 migration。請先查看 backend 日誌，不要急著導入流量。

### Kubernetes

Helm 有自己的升級方式：在 values 檔案中將 `images.backend.tag` / `images.frontend.tag` 設為要使用的版本，再執行 `helm upgrade`。變更 tag 會更新 pod spec，Kubernetes 隨即下載新版映像檔並進行滾動更新，這是可靠的升級方式。

單獨執行 `kubectl -n multica rollout restart` **不會升級**。chart 預設使用 `pullPolicy: IfNotPresent`（`deploy/helm/multica/values.yaml`）；若節點已快取該 tag 的映像檔，重新啟動時會繼續使用舊版，內容不會更新，與固定 `MULTICA_IMAGE_TAG` 的情況相同。若要透過浮動 tag 升級，必須先將 `images.backend.pullPolicy` / `images.frontend.pullPolicy` 設為 `Always`。詳情請參閱儲存庫中的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

<Callout type="warning">
`docker compose down` 會保留 `pgdata` 和 `backend_uploads`。加上 `-v` 則會刪除這些資料卷，包括資料庫；除非確定要清空執行個體，否則請勿執行 `docker compose down -v`。
</Callout>

## 常見問題

| 現象 | 先檢查什麼 |
|---|---|
| `/readyz` 沒有回傳 `ok` | 執行 `docker compose -f docker-compose.selfhost.yml logs backend postgres`。 |
| 收不到驗證碼 | 再要求一次驗證碼，然後在 backend 日誌中搜尋 `Verification code`。 |
| `setup self-host` 顯示伺服器無法連線 | 在執行電腦上連線至 `https://api.example.com/health`，確認 DNS、TLS 和反向代理都可連線。若回傳 404，表示代理將 `/health` 傳給了不會轉送該路徑的舊版 frontend；請改為直接路由至 backend（請參閱[疑難排解](/troubleshooting#multica-setup-報告伺服器不可達)）。 |
| 常駐程式沒有列出 `Agents` | 確認 AI 程式開發工具已加入 `PATH` 並登入，然後執行 `multica daemon restart`。 |
| 任務持續排隊 | 執行 `multica daemon status`，確認常駐程式正在執行且已連線至工作區。 |

更多情況見[疑難排解](/troubleshooting)。

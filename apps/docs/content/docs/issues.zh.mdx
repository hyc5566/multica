任務是 Multica 中安排工作的基本單位：一項功能、一個 bug、一次調研，任何需要成員或 Agent 負責推進的工作。圍繞它的討論、狀態變化和每次執行都留在同一處，無需再從聊天記錄或終端日誌中拼接上下文。

## 任務的組成

| 內容 | 用途 |
|---|---|
| **標題和描述** | 目標、背景、要求和驗收條件。 |
| **狀態和優先順序** | 工作處於哪個階段，先處理什麼。 |
| **負責人** | 工作區成員、Agent 或小隊。 |
| **日期、標籤和自定義屬性** | 計劃、分類和團隊自己的欄位。 |
| **專案和父子關係** | 歸入更大的工作範圍，或拆成子任務。 |
| **動態和執行日誌** | 留言、狀態變化、執行和 Agent 返回的結果。 |

![任務詳情：描述、討論、右側屬性與執行日誌](/images/docs/quickstart-run-result.webp)

## 建立任務

在**任務**頁面或專案中新建，填寫標題即可，其餘屬性隨時補充。

每個任務有一個編號，例如 `MUL-123`。數字在工作區內遞增；管理員修改工作區的任務前綴後，編號會用新前綴顯示。詳見[工作區](/workspaces#建立工作區)。

## 選擇負責人

| 負責人 | 效果 |
|---|---|
| **成員** | 由這位成員負責跟進，不建立執行。 |
| **Agent** | 為該 Agent 建立一次執行。 |
| **小隊** | 由小隊 leader 接收，再決定交給誰處理。 |

分配給 Agent 或小隊時，任務不在 `backlog` 就會立即入隊；執行環境離線時，執行留在隊列中等待。已歸檔的 Agent 和小隊不能被分配。

分配不會繞過 Agent 的訪問範圍（Access）；分配給小隊時，校驗的是 leader 的 Access。詳見[分配任務給 Agent](/assigning-issues)。

## 狀態

每個工作區都自帶 7 個內置狀態，歸入 4 個生命週期分類：

| 分類 | 內置狀態 | 含義 |
|---|---|---|
| `unstarted` | `backlog`、`todo` | 還沒開始的工作，不論是已規劃還是暫時擱置。 |
| `started` | `in_progress`、`in_review`、`blocked` | 已經開始、等待檢查，或暫時無法繼續。 |
| `done` | `done` | 順利完成，終態。 |
| `closed` | `cancelled` | 不再繼續，終態，但不算順利完成。 |

分類讓生命週期判斷保持簡單。看板、列表、篩選和排序都按具體狀態來，具體狀態也保留了 Agent 和自動化依賴的那些更細的行為。

| 狀態 | 含義 |
|---|---|
| `backlog` | 暫不啟動。已分配給 Agent 的任務需離開 `backlog` 後才會建立執行。 |
| `todo` | 已明確，等待開始。 |
| `in_progress` | 正在處理。 |
| `in_review` | 已有結果，等待檢查。 |
| `done` | 已完成。 |
| `blocked` | 暫時無法繼續。 |
| `cancelled` | 不再繼續，保留記錄。 |

狀態之間沒有固定流轉，成員和 Agent 都可以直接修改。

Agent 會依任務的實際進度更新狀態：開始產出任務要求的成果時就設為 `in_progress`，無論成果是程式碼、調查、設計或任務要求的審查；交付後改為 `in_review`；跨回合持續處理時維持 `in_progress`。若該回合沒有產出此任務的成果（例如回答問題或協助其他工作），就不變更狀態。Agent 會在執行期間透過 Multica CLI 明確更新狀態；開始或完成執行時，伺服器不會自動變更任務狀態，以下兩種系統例外除外。`done` 通常由人工確認，或在工作區設定 PR 合併後改為 `done` 時，由系統於所有關聯 PR 合併後寫入。

<Callout type="info">
兩個變化由系統執行：

- 執行失敗，且該任務沒有其他執行、也沒有觸發重試時，`in_progress` 回到 `todo`。
- 任務的所有關聯 PR 都合併時，任務改為工作區選定的狀態（預設 `done`），除非工作區設定為不改變，或該任務設定了合併後不改狀態。詳見 [GitHub 整合](/github-integration)。
</Callout>

### 自定義狀態

工作區的 owner 或 admin 可以在**設定 → 任務狀態**裡新增自己的狀態，比如 `Code Review`、`QA`、`Rework`。每個狀態都屬於 4 個生命週期分類之一：

| 分類 | 生命週期含義 |
|---|---|
| `unstarted` | 尚未開始，包含內建的 `backlog` 和 `todo`。 |
| `started` | 處理中，包括等待檢查或等待外部回覆。 |
| `done` | 順利完成，終止狀態。 |
| `closed` | 取消或不再繼續，屬終止狀態，但不代表順利完成。 |

自訂狀態只繼承生命週期分類，不會繼承內建狀態的特定行為。`backlog` 的暫停、`in_review` 結束[自動化](/autopilots)執行、`blocked` 的失敗處理、`in_progress` 的失敗回收都不會被繼承；需要特定行為時，請使用對應的內建狀態。既有自訂狀態也遵循相同規則：`Awaiting Response` 屬於處理中的工作，不會自動結束檢查。指派與建立任務仍遵循通用的 Agent 觸發規則。

平臺自己寫入狀態時——失敗回滾到 `todo`、PR 合併置 `done`——寫的都是內置狀態，不會寫成某個自定義狀態。

對已安裝的客戶端，API 裡原有的分類欄位仍然返回 7 值的傳輸枚舉。新客戶端會把它歸一成 4 個分類；傳輸值本身從不授予任何行為繼承。資料庫裡只存這 4 個生命週期值。

由此有四點：

- **狀態一旦建立，分類就不能再改。** 改分類等於悄悄重寫所有已經在該狀態上的任務的行為，所以編輯時分類是隻讀的。先想清楚要什麼行為，再取名字。
- **按狀態分組用的是具體狀態。** 看板的列、列表的分節、泳道的狀態列，都會把內置狀態和自定義狀態分開。`Code Review` 和 `QA` 各佔一列，即使兩者都屬於 `started`。分類是內部的生命週期劃分，不是用來替代列名的。
- **內置狀態是鎖死的。** 名稱、顏色、分類都不能改，也不能歸檔——從不開啟這個頁面的工作區，看板和原來一模一樣。
- **歸檔是停用，不是刪除。** 已經在該狀態上的任務保持不變，名稱、顏色和行為都不變，只是之後再設定狀態時不再出現這個選項。

內置狀態會按介面語言翻譯，自定義狀態則始終顯示你填的名字。API 和 CLI 通過 key 引用它：`multica issue status MUL-42 code_review`。設定頁裡的 key 由名字生成；API 可以顯式指定，省略時才自動生成。無論哪種方式，key 在建立時就定下來了——之後改名字不會改 key。

## 任務與執行

任務是持續存在的工作記錄；[執行](/tasks)是 Agent 的一次具體執行。一個任務可以先後產生多次執行——第一次實現、補充修改、再次檢查。執行“已完成”只表示這一次執行結束；任務是否完成，以任務的狀態為準。

## 專案和子任務

一個任務最多屬於一個[專案](/projects)，專案為其中的執行提供共享說明和資源；移到另一個專案不會產生副本。

較大的工作可以拆成子任務：父任務保留整體目標，子任務各自獨立推進。父子狀態互不聯動。

子任務可以設定**階段**（stage），按 1、2、3 分批推進。當前最早未完成階段的全部子任務到達 `done` 或 `cancelled` 時，父任務會收到"子任務完成"通知；父任務的負責人是 Agent 時，它會被喚醒並決定是否推進下一階段。未設定階段的子任務視為同一批，全部結束時通知一次。

## 切換視圖

任務頁面提供列表、看板、表格、甘特圖和泳道五種視圖，可按狀態、負責人、專案和其他屬性篩選、排序，展示的都是同一批任務。

## 刪除任務

任何工作區成員都可以刪除任務。

<Callout type="warning">
刪除不可恢復：任務及其留言、附件和關聯記錄會被永久移除，尚未結束的執行會被取消。不再繼續時把狀態改為 `cancelled`，討論和結果仍可查閱。
</Callout>

任務是 Multica 安排工作的基本單位，可以是一項功能、一個 bug、一次調查，或任何需要成員或 Agent 推進的工作。相關討論、狀態變更和每次執行都集中在同一處，不必再從聊天紀錄或終端機日誌拼湊脈絡。

## 任務的組成

| 內容 | 用途 |
|---|---|
| **標題和描述** | 目標、背景、要求和驗收條件。 |
| **狀態和優先順序** | 工作進度，以及處理順序。 |
| **負責人** | 工作區成員、Agent 或小隊。 |
| **日期、標籤和自訂屬性** | 排程、分類和團隊自訂欄位。 |
| **專案和父子關係** | 納入較大的工作範圍，或拆分成子任務。 |
| **動態和執行日誌** | 留言、狀態變更、執行和 Agent 回傳的結果。 |

![任務詳細資訊：描述、討論、右側屬性和執行日誌](/images/docs/quickstart-run-result.webp)

## 建立任務

在**任務**頁面或專案中建立任務時，只要填寫標題即可；其他屬性之後再補上也可以。

每項任務都有編號，例如 `MUL-123`。編號在工作區內依序遞增；管理員修改工作區的任務編號前綴後，編號會改用新前綴。詳情請參閱[工作區](/workspaces#建立工作區)。

## 選擇負責人

| 負責人 | 效果 |
|---|---|
| **成員** | 由該成員負責跟進，不會建立執行。 |
| **Agent** | 為該 Agent 建立一次執行。 |
| **小隊** | 由小隊 leader 接手，再決定交由誰處理。 |

指派給 Agent 或小隊時，只要任務不是 `backlog` 狀態，就會立即排入佇列；若執行環境離線，執行會留在佇列中等待。已封存的 Agent 和小隊不能被指派。

指派不會繞過 Agent 的 Access 範圍；指派給小隊時，系統會檢查 leader 的 Access。詳情請參閱[將任務指派給 Agent](/assigning-issues)。

## 狀態

每個工作區都內建 7 種狀態，分屬 4 種生命週期分類：

| 分類 | 內建狀態 | 含義 |
|---|---|---|
| `unstarted` | `backlog`、`todo` | 還沒開始的工作，不論是已規劃還是暫時擱置。 |
| `started` | `in_progress`、`in_review`、`blocked` | 已經開始、等待檢查，或暫時無法繼續。 |
| `done` | `done` | 順利完成，最終狀態。 |
| `closed` | `cancelled` | 不再繼續，最終狀態，但不算順利完成。 |

分類讓生命週期判斷保持簡單。看板、清單、篩選和排序都依具體狀態運作；Agent 和自動化依賴的細部行為也由具體狀態決定。

| 狀態 | 含義 |
|---|---|
| `backlog` | 暫不開始。指派給 Agent 的任務必須移出 `backlog` 才會建立執行。 |
| `todo` | 已明確，等待開始。 |
| `in_progress` | 正在處理。 |
| `in_review` | 已有結果，等待檢查。 |
| `done` | 已完成。 |
| `blocked` | 暫時無法繼續。 |
| `cancelled` | 不再繼續，保留記錄。 |

狀態之間沒有固定流程，成員和 Agent 都可以直接變更狀態。

Agent 會依任務實際進度更新狀態：開始產出任務要求的成果時，就設為 `in_progress`，不論成果是程式碼、調查、設計或任務要求的審查；交付後改為 `in_review`；工作需要跨回合進行時，維持 `in_progress`。若該回合沒有產出這項任務要求的成果（例如只回答問題或協助其他工作），就不變更狀態。Agent 會在執行期間透過 Multica CLI 明確更新狀態；除下列兩種系統例外外，伺服器不會在執行開始或結束時自動變更任務狀態。`done` 通常由人員確認；若工作區設定在 PR 合併後將任務改為 `done`，系統則會在所有關聯 PR 合併後更新狀態。

<Callout type="info">
系統會在以下兩種情況變更狀態：

- 執行失敗，且該任務沒有其他執行、也沒有等待中的重試時，`in_progress` 會退回 `todo`。
- 任務的所有關聯 PR 都合併時，任務會改為工作區設定的狀態（預設為 `done`）；若工作區設定為不變更，或該任務設定合併後維持原狀，則不會更新。詳情請參閱 [GitHub 整合](/github-integration)。
</Callout>

### 自訂狀態

工作區 `owner` 或 `admin` 可以在**設定 → 任務狀態**新增自訂狀態，例如 `Code Review`、`QA`、`Rework`。每種狀態都屬於 4 種生命週期分類之一：

| 分類 | 生命週期含義 |
|---|---|
| `unstarted` | 尚未開始，包含內建的 `backlog` 和 `todo`。 |
| `started` | 處理中，包括等待檢查或等待外部回覆。 |
| `done` | 順利完成，終止狀態。 |
| `closed` | 取消或不再繼續，屬終止狀態，但不代表順利完成。 |

自訂狀態只繼承生命週期分類，不會繼承內建狀態的特定行為。它不會繼承 `backlog` 的暫停、`in_review` 結束[自動化](/autopilots)執行、`blocked` 的失敗處理或 `in_progress` 的失敗回復等行為；需要特定行為時，請使用對應的內建狀態。既有自訂狀態也遵循相同規則：`Awaiting Response` 屬於處理中的工作，不會自動結束檢查。指派和建立任務仍遵循一般 Agent 觸發規則。

平台寫入狀態時，例如失敗後退回 `todo` 或 PR 合併後設為 `done`，使用的都是內建狀態，不會改成自訂狀態。

為了相容已安裝的用戶端，API 原有的分類欄位仍會回傳 7 值傳輸列舉。新用戶端會將其正規化為 4 種分類；傳輸值本身不會授予任何行為繼承。資料庫只儲存這 4 種生命週期值。

由此有四點：

- **狀態建立後就不能再變更分類。** 變更分類會悄悄改變所有目前處於該狀態的任務行為，因此編輯時分類欄位是唯讀的。請先決定所需行為，再命名狀態。
- **依狀態分組時使用具體狀態。** 看板欄、清單區段和泳道狀態欄都會區分內建和自訂狀態。即使 `Code Review` 和 `QA` 都屬於 `started`，也會各自佔一欄。分類是內部的生命週期劃分，不會取代狀態名稱。
- **內建狀態不可修改。** 名稱、顏色和分類都不能變更，也不能封存；未開啟此設定頁的工作區，看板會維持原樣。
- **封存代表停用，不是刪除。** 目前處於該狀態的任務不受影響，名稱、顏色和行為都會保留；之後設定任務狀態時則不會再提供此選項。

內建狀態會依介面語言翻譯，自訂狀態則會保留你輸入的名稱。API 和 CLI 透過 key 引用狀態，例如 `multica issue status MUL-42 code_review`。設定頁會依名稱產生 key；API 可明確指定 key，省略時才會自動產生。無論使用哪種方式，key 都會在建立時固定，之後更改名稱不會改變 key。

## 任務與執行

任務是持續保存的工作紀錄；[執行](/tasks)則是 Agent 一次具體的工作過程。一項任務可以有多次執行，例如第一次實作、補充修改和再次檢查。執行顯示"已完成"只代表這次工作結束；任務是否完成，仍以任務狀態為準。

## 專案和子任務

一項任務最多屬於一個[專案](/projects)，專案會提供共用說明和資源；將任務移至另一個專案不會建立副本。

較大的工作可以拆成子任務：父任務保留整體目標，子任務分別推進。父子任務的狀態彼此獨立。

子任務可以設定**階段**（stage），依 1、2、3 的順序分批推進。最早尚未完成階段中的所有子任務都達到 `done` 或 `cancelled` 後，父任務會收到"子任務完成"通知；若父任務負責人是 Agent，Agent 會收到觸發並判斷是否進入下一階段。未設定階段的子任務會視為同一批，全部完成時通知一次。

## 切換檢視

任務頁面提供清單、看板、表格、甘特圖和泳道五種檢視方式，可依狀態、負責人、專案和其他屬性篩選與排序；所有檢視顯示的都是同一批任務。

## 刪除任務

任何工作區成員都可以刪除任務。

<Callout type="warning">
刪除後無法復原：任務、留言、附件和關聯紀錄都會永久移除，尚未完成的執行也會取消。如果不再繼續，請將狀態設為 `cancelled`，保留討論和結果供日後查看。
</Callout>

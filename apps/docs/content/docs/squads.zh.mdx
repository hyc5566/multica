小隊由一位 Agent 擔任 leader，並由任意數量的成員組成。將任務指派給小隊不會同時啟動所有 Agent；Multica 會先喚醒 leader，由它閱讀脈絡並決定下一步交給誰。

小隊負責判斷工作該交給誰，不會將多個 Agent 合併成一個新 Agent，也不會自動提高並行數。

## 適用場景

如果工作需要多種能力，且建立任務時還無法確定由誰負責，就適合使用小隊。例如，產品交付小隊可以包含前端、後端和測試 Agent，再由 leader 依每項任務的內容分派工作。

工作範圍明確時，直接指派給相應的 [Agent](/agents) 即可。

## 小隊的組成

| 設定 | 說明 |
|---|---|
| **leader** | 必須是 Agent。接收指派給小隊的工作，並決定如何處理。 |
| **成員** | 可以是 Agent 或工作區成員。同一位成員可以加入多個小隊。 |
| **角色說明** | 說明每位成員適合處理哪些工作。這只是執行脈絡，不會授予權限，也不會自動觸發成員。 |
| **小隊指令** | 記錄分派規則、協作方式和小隊共用背景，只會提供給 leader。 |

建立小隊時需要輸入名稱並選擇 leader。leader 會自動成為小隊成員；之後可以新增成員、填寫角色說明和小隊指令。

## 分配後的執行流程

任務不是 `backlog` 狀態時，指派給小隊後，Multica 會立即為**leader Agent**建立一次執行並排入佇列（不會為每位成員各建立一次）：

1. **執行環境領取執行。** 流程與一般 Agent 指派相同，由 Agent 執行環境在下一次輪詢時領取。
2. **leader 收到工作簡報。** 執行被領取時，Multica 會在 leader 的系統提示中附加三個區塊，詳見下方[leader 每次執行時看到的內容](#leader-每次執行看到的內容)。
3. **leader 發布一則分派留言。** leader 會使用名冊提供的 mention markdown，透過 `@` 提及選定成員；這會為每位被提及的 Agent 觸發新的執行。
4. **leader 記錄評估結果**：`multica squad activity <issue-id> action --reason "..."`。這會在任務活動時間軸新增紀錄，讓成員知道 leader 確實評估了這次觸發。
5. **分派這一輪會讓父任務維持 `in_progress`。** 狀態規則與直接指派 Agent 相同：協調小隊就是在處理父任務，因此父任務會從 `todo` 進入 `in_progress`；分派成員不代表交付，小隊工作期間會維持此狀態。
6. **leader 停止工作。** leader 分派後不會親自實作。成員回報，或子任務／階段條件完成時，leader 會再次收到觸發，閱讀更新後決定是否繼續分派、向上回報、在整體目標達成時將父任務設為 `in_review`，或保持靜默。`done` 留給人工審查者或既有整合處理（例如帶有 close intent 的 PR 合併）。

如果任務處於 `backlog`，指派不會觸發 leader；任務移出 `backlog` 後才會開始執行。

### leader 每次執行看到的內容

每次 leader 執行時，系統都會在指令中附加以下三個區塊：

- **Squad Operating Protocol（小隊運作規範）**——系統固定提供的規則：閱讀任務、用 `@` 分派、保持簡潔（不重述任務內容，受派成員可以自行查看）、每輪都記錄評估、分派後停止（這一輪結束時父任務維持 `in_progress`），並在整體目標達成後才將父任務設為 `in_review`。此規範由系統管理，無法編輯。

  狀態規則只套用到"確實指派給這個小隊"的任務。若 leader 因其他任務中的 `@squad` 提及而醒來，它仍會收到名冊和分派規則，但系統會明確要求它不要變更該任務狀態，因為狀態仍由原任務負責人管理。
- **Squad Roster（小隊名冊）**——leader 自己一列，每位未封存成員各一列。每列都附上可直接複製的 mention markdown（`[@Name](mention://agent/<uuid>)` 或 `[@Name](mention://member/<uuid>)`）；只輸入純文字 `@name` 不會觸發任何人。
- **Squad Instructions（小隊指令）**——你為小隊撰寫的自訂指引（可在小隊詳細資訊頁或透過 `multica squad update --instructions` 設定），例如分派規則（"資料庫工作交給 Alice，前端工作交給 Bob"）、升級處理方式，或任務本身未提供的背景資訊。

## leader 再次收到觸發的時機

第一次分派後，後續大多數留言都會自動喚醒 leader：

| 事件 | 觸發隊長 |
|---|---|
| 非小隊成員（成員或外部 Agent）發表留言 | 會 |
| 小隊成員發布不含 `@` 的進度更新 | 會——leader 會重新評估下一步 |
| 任何人留言時明確 `@` 提及其他 Agent、成員、小隊或 `@all` | 不會——明確的 `@` 是分派訊號，leader 會讓出處理權 |
| leader 自己發表留言 | 不會——避免自行觸發 |
| 留言只有任務交叉參照 | 會——任務引用不算分派訊號 |

此外還有去重規則：如果 leader 已有這項任務的 `queued` 或 `dispatched` 執行，新觸發不會重複排入佇列。

<Callout type="info">
小隊成員留言中若有 `@` 提及，leader 不會被喚醒，因為這表示成員已明確交接工作；再喚醒 leader 只會多出一輪沒有實際工作的執行。例外是 Agent 回報結果時也 `@` 提及另一個 Agent，此時 leader 仍會收到觸發，以便協調整個討論串。
</Callout>

## 指派小隊和 @提及小隊

| 操作 | 是否改變負責人 | 結果 |
|---|---|---|
| **將任務指派給小隊** | 是 | 小隊成為負責人，並觸發 leader。 |
| **在留言中 @提及小隊** | 否 | 只有 leader 會處理這則留言，原負責人不變。 |

直接 @提及某位成員時，工作會交給該成員處理。Multica 也會合併重複觸發，並避免 leader 的留言再次觸發自己，以免形成執行迴圈。

## 小隊與 Access

將 Agent 加入小隊不會繞過其 [Access](/agents#權限與-access)。一般成員建立或管理小隊時，只能選擇自己有權執行的 Agent。

成員能否指派或 @提及小隊，也取決於是否有權執行該小隊的 leader。若 leader 已封存，或目前成員無權執行它，就無法指派或 @提及該小隊。

## 建立和管理權限

任何工作區成員都可以建立小隊。建立者可以修改或封存自己建立的小隊；工作區 `owner` 和 `admin` 可以管理所有小隊。

小隊名稱在工作區中不必唯一。變更 leader 時，新 leader 會自動加入小隊；目前的 leader 無法直接移除，必須先指定另一位 leader。

## 封存小隊

封存後，小隊會從清單、負責人選擇器和 @選單中移除，且無法還原。

為了讓現有工作仍有負責人，目前指派給小隊的任務和自動化會轉交給原 leader Agent。歷史留言和活動紀錄會保留。若之後還需要相同的分派方式，請重新建立小隊。

<Callout type="warning">
封存無法復原。
</Callout>

## 使用 CLI

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
 --member-id <agent-or-member-id> \
 --type agent \
 --role "負責前端實作"
```

完整命令見 [使用 CLI](/cli)。

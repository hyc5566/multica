小隊由一名隊長Agent和若干成員組成。把任務分配給小隊後，不會同時執行所有Agent：Multica 先喚醒隊長，由它閱讀上下文，決定下一步交給誰。

小隊只負責把工作交給合適的人。它不會把多個Agent合併成一個新的Agent，也不會自動提高併發。

## 適用場景

當工作需要多種能力，而且不能在建立任務時就確定具體負責人，可以使用小隊。例如，一個產品交付小隊可以包含前端、後端和測試Agent，由隊長根據每條任務的內容分配。

工作範圍明確時，直接指派給相應的 [Agent](/agents) 即可。

## 小隊的組成

| 設定 | 說明 |
|---|---|
| **隊長** | 必須是一名Agent。接收分配給小隊的工作，並決定如何處理。 |
| **成員** | 可以是Agent，也可以是人類成員。同一成員可以加入多個小隊。 |
| **角色說明** | 告訴隊長每個成員適合處理什麼工作。它只是上下文，不會授予許可權或自動觸發成員。 |
| **小隊指令** | 儲存路由規則、協作方式和需要貫穿全隊的背景，只會提供給隊長。 |

建立小隊時需要填寫名稱並選擇隊長。隊長會自動成為小隊成員；之後可以繼續新增成員、填寫角色說明和小隊指令。

## 分配後的執行流程

任務不是 `backlog` 狀態時，指派給小隊後，Multica 會立即為**leader Agent**建立一次執行並排入佇列（不會為每位成員各建立一次）：

1. **隊長的runtime領走執行**，和普通Agent的分配流程一樣。
2. **隊長拿到 briefing。** 執行被領取時，Multica 會在隊長的指令後面追加三段內容，見下文[隊長每次執行看到的內容](#隊長每次執行看到的內容)。
3. **隊長髮一條派活留言。** 留言裡用花名冊給好的 mention markdown `@` 選中的成員。被 `@` 的Agent會入隊一次新執行，被 `@` 的人類成員會收到通知。
4. **隊長記錄 evaluation**：`multica squad activity <issue-id> <outcome> --reason "..."`。這一行會寫進任務的 activity 時間線，方便人類回溯隊長的每次評估。
5. **派活輪讓父任務處於 `in_progress`。** 和直接分配給Agent同一套狀態約定：協調小隊就是在推進父任務本身的工作，所以父任務從 `todo` 進入 `in_progress`；派活不等於交付，小隊幹活期間保持不變。
6. **隊長停下。** 派完活，隊長不親自動手。被派成員有回覆時，隊長會被自動喚醒，決定下一步：繼續派活、上拋給人類、在整體目標達成後把父任務推到 `in_review`，或保持沉默。`done` 留給人工確認或既有整合（例如帶 close intent 的 PR merge）。

如果任務處於 `backlog`，指派不會觸發 leader；任務移出 `backlog` 後才會開始執行。

### 隊長每次執行看到的內容

每次 leader 執行時，系統都會在指令中附加以下三個區塊：

- **Squad Operating Protocol（小隊工作規範）**：一段硬編碼的規則集，讀任務 → 用 `@` 派活 → 保持簡潔（不復述任務內容，被派的成員自己能讀）→ 每次記 evaluation → 派完就停（派活輪結束時父任務處於 `in_progress`）→ 整體目標達成後才推 `in_review`。這段由系統管理，不可編輯。

 其中狀態相關的規則只對"確實分配給本小隊"的任務生效。隊長被別人任務裡的 `@小隊` 喚醒時，同樣拿到花名冊和派活規則，但會被明確告知不要改動那條任務的狀態，狀態仍歸那條任務自己的負責人。
- **Squad Roster（小隊花名冊）**：隊長一行，加上每個未歸檔成員一行，每行帶可直接複製的 mention markdown（`[@Name](mention://agent/<uuid>)`）。純文字 `@name` 不會觸發任何人。
- **Squad Instructions（小隊指令）**：你為這個小隊寫的自定義內容，包括路由規則（"資料庫相關派給 Alice，前端派給 Bob"）、上報策略，或任務本身不會有的背景。

## leader 再次收到觸發的時機

第一次分派後，後續大多數留言都會自動喚醒 leader：

| 事件 | 觸發隊長 | 說明 |
|---|---|---|
| 非小隊成員（人類、外部Agent）發留言 | 會 | |
| 小隊成員發進展更新，不帶任何 `@` | 會 | 隊長重新評估下一步 |
| 任何留言裡顯式 `@` 了Agent、成員、小隊或 `@all` | 不會 | 顯式 `@` 就是路由訊號，隊長讓位 |
| 隊長自己發的留言 | 不會 | 防止自己觸發自己 |
| 留言裡只有任務互鏈 | 會 | 任務引用不算路由 |

此外還有去重規則：如果 leader 已有這項任務的 `queued` 或 `dispatched` 執行，新觸發不會重複排入佇列。

<Callout type="info">
小隊成員留言中若有 `@` 提及，leader 不會被喚醒，因為這表示成員已明確交接工作；再喚醒 leader 只會多出一輪沒有實際工作的執行。例外是 Agent 回報結果時也 `@` 提及另一個 Agent，此時 leader 仍會收到觸發，以便協調整個討論串。
</Callout>

## 指派小隊和 @提及小隊

| 操作 | 是否改變負責人 | 結果 |
|---|---|---|
| **把任務分配給小隊** | 是 | 小隊成為負責人，並觸發隊長。 |
| **在留言中 @小隊** | 否 | 只讓隊長處理這條留言，原負責人不變。 |

直接 @某名成員時，工作會交給該成員處理。

## 小隊與 Access

將 Agent 加入小隊不會繞過其 [Access](/agents#權限與-access)。一般成員建立或管理小隊時，只能選擇自己有權執行的 Agent。

成員能否分配或 @某個小隊，取決於其是否有權執行小隊的隊長。若隊長已歸檔，或當前成員無權執行它，這個小隊就無法被分配或 @提及。

## 建立和管理權限

任何工作區成員都可以建立小隊。建立者可以修改或封存自己建立的小隊；工作區 `owner` 和 `admin` 可以管理所有小隊。

小隊名稱不要求在工作區中唯一。更換隊長時，新隊長會自動加入小隊；當前隊長不能直接移除，需要先指定另一名隊長。

## 封存小隊

封存後，小隊會從清單、負責人選擇器和 @選單中移除，且無法還原。

為避免現有工作失去負責人，當前分配給小隊的任務和自動化會轉給原隊長Agent。歷史留言和活動記錄仍然保留。如果之後還需要相同的路由，需要重新建立小隊。

<Callout type="warning">
封存無法復原。
</Callout>

## 使用 CLI

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
 --member-id <agent-or-member-id> \
 --type agent \
 --role "負責前端實作"
```

完整命令見 [使用 CLI](/cli)。

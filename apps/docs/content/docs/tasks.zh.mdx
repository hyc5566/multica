每次 Agent 開始工作，Multica 都會建立一筆**執行紀錄**。紀錄會說明這次執行由什麼觸發、交由哪個 Agent 處理、目前進度，以及最後是否成功。

## 任務與執行

任務保存工作的目標、討論、負責人和最終狀態；執行紀錄則記錄 Agent 處理這項工作的一次過程。

| | 任務 | 執行 |
| --- | --- | --- |
| 記錄內容 | 持續推進的一項工作 | Agent 的一次執行 |
| 持續時間 | 可反覆討論、補充和重新指派 | 從觸發開始，直到完成、失敗或取消 |
| 數量關係 | 一項任務可以有多次執行 | 每次執行都有獨立紀錄 |

因此，同一項任務可以先後交由不同 Agent 處理，也可以在失敗後重新執行。每次都會建立新的執行紀錄，不會覆蓋舊紀錄。

## 觸發來源

以下操作都可能觸發一次執行：

- 將任務指派給 Agent 或小隊。
- 在留言中 @提及 Agent。
- 在 Chat 中傳送訊息給 Agent。
- 由自動化依排程或外部事件觸發。

不同入口提供的脈絡不同，但執行方式相同：Multica 建立執行，由執行環境領取，再呼叫 Agent 設定的 AI 程式開發工具。

## 執行過程

一次執行通常會經過以下狀態：

| 狀態 | 意義 |
| --- | --- |
| `deferred` | 已安排稍後觸發，到達指定時間後進入佇列 |
| `queued` | 等待執行環境領取 |
| `dispatched` | 執行環境已領取，正在啟動 AI 程式開發工具 |
| `waiting_local_directory` | 目標本機目錄正由另一項執行使用，等待目錄鎖釋放 |
| `running` | AI 程式開發工具正在執行 |
| `completed` | 這次執行已正常結束 |
| `failed` | 執行出錯或中斷 |
| `cancelled` | 執行被手動停止 |

執行環境在線時，新執行通常很快就會開始；若執行排入佇列後環境離線，執行會留在佇列中等待環境恢復。單純排隊不會讓執行逾期：只要執行環境仍持續傳送心跳，就代表它仍在線，佇列中的工作可以持續等待。只有**同時**符合以下兩個條件，排隊中的執行才會失敗：執行綁定的環境超過重新連線寬限期都沒有心跳，**而且**該執行本身也已排隊超過相同時間。第二個條件是為了處理"指派給已休眠的電腦"；這種情況下，執行仍會保留完整寬限期，讓你有時間喚醒電腦，而不會立刻失敗。

<Callout type="info">
如果系統在觸發前已知道目標執行環境離線，部分即時操作會直接提示目前無法執行，不會繼續建立無法領取的執行。
</Callout>

只要執行環境持續正常傳送心跳，長時間執行就不會僅因耗時太久而被伺服器強制終止。執行環境會依實際活動判斷程序是否卡住；相關設定請參閱[環境變數](/environment-variables#常駐程式設定)。

## 查看執行記錄

任務的所有執行都會列在右側欄的 **執行日誌**中，不必切換到其他頁面或分頁。這個區塊預設會展開：進行中的執行固定在最上方，已結束的則收在 **顯示歷史執行（N）**下。每列會顯示觸發來源、執行的 Agent、狀態和時間。如果沒有看到這個區塊，請使用任務頂部的面板按鈕開啟右側欄；視窗較窄時，右側欄預設會收合。

頁面保持開啟時，執行日誌會透過即時連線自動更新；新的執行、狀態變更和 Agent 留言都會直接顯示，不必手動重新載入。

Agent 工作期間，任務頂部也會出現即時狀態列，例如"Engineer 正在處理"。將游標移到狀態列上，就能查看目前的執行，不必離開頁面。

你可以在這裡：

- 點選某列的 **查看紀錄**，檢視 Agent 訊息、工具呼叫和錯誤資訊。執行仍在進行時，內容會在對話框開啟期間即時追加；也可以選擇 **最新的在前**調整事件順序。
- 停止已排定稍後觸發、正在排隊、啟動中、等待本機目錄或正在執行的工作。
- 重試失敗或已取消的執行。

![任務右側欄中的執行日誌：進行中的執行在上方，歷史紀錄在下方](/images/docs/quickstart-run-result.webp)

![執行紀錄：狀態時間軸、Agent 摘要和逐項工具呼叫](/images/docs/task-transcript.webp)

<Callout type="warning">
變更任務負責人或狀態，不會停止已開始的執行。若要中斷，請在執行日誌中停止對應的執行。刪除任務時，關聯中尚未結束的執行才會一併取消。
</Callout>

## 失敗與自動重試

執行環境短暫離線、常駐程式重新啟動、執行逾時或 AI 程式開發工具網路中斷等暫時性故障，都可能觸發自動重試。一般執行預設最多嘗試兩次；工具網路中斷最多嘗試三次。

Agent 本身回報的錯誤通常不會自動重試。例如驗證失效、用量不足、設定錯誤或模型無法完成要求，都必須先排除原因，再手動重試。

自動化的**只執行**模式不會自動重試，以免和下一次排程重疊。**建立任務**模式會建立一般任務執行，遇到基礎架構故障時仍依上述規則重試。兩種模式的最終結果都能在自動化的執行紀錄中查看。

當任務沒有其他進行中的執行，也沒有等待重試的執行時，執行失敗會將 `in_progress` 任務退回 `todo`。

## 失敗原因參考

執行日誌和用量統計中的常見失敗原因分成兩類：沒有前綴的原因碼由平台記錄；`agent_error.*` 則是依 AI 程式開發工具的錯誤分類。

**平台側**

| 原因 | 含義 | 處理 |
| --- | --- | --- |
| `runtime_offline` | 執行期間執行環境離線 | 環境恢復後重試，請參閱[常駐程式與執行環境](/daemon-runtimes) |
| `queued_expired` | 執行環境超過重新連線寬限期沒有心跳，且該執行也已排隊相同時間 | 確認執行環境在線後重試 |
| `runtime_recovery` | 常駐程式重新啟動後，回收中斷的執行 | 直接重試 |
| `environment_prepare_failed` | 常駐程式無法準備本次執行環境，例如工作目錄或其中的本機執行環境設定 | 先檢查原始錯誤，找出失敗步驟，再檢查該電腦的磁碟空間、權限、目錄是否仍被佔用，以及 AI 程式開發工具的本機設定 |
| `cancelled` | 手動停止，或隨封存、刪除一併取消 | 不必處理 |
| `timeout` | 超過常駐程式設定的執行時間上限 | 縮小任務範圍，或調整常駐程式的 `agent_timeout` |
| `iteration_limit` | 達到執行輪次上限 | 縮小任務範圍 |
| `agent_blocked` | Agent 主動回報無法繼續 | 依照 Agent 在留言中的說明補充資訊 |
| `api_invalid_request` | 平台 API 拒絕了非法請求 | 重試；反覆出現時報告問題 |
| `codex_semantic_inactivity` | Codex 長時間沒有有效輸出，因此被判定為停滯 | 重試，或調整 Codex 停滯逾時設定 |

**工具側（`agent_error.*`，前綴省略）**

| 原因 | 含義 | 處理 |
| --- | --- | --- |
| `provider_auth_or_access` | 模型服務驗證失敗或沒有存取權限（401/403） | 在該 AI 程式開發工具中重新登入，或檢查 API key |
| `provider_quota_limit` | 配額或餘額用盡（402） | 儲值或更換帳號 |
| `provider_capacity_or_rate_limit` | 遭到限流或服務容量不足（429/529） | 稍後重試 |
| `provider_server_error` | 模型服務發生錯誤（5xx） | 稍後重試 |
| `provider_network` | 連線至模型服務時發生網路故障 | 系統會自動重試；若問題持續，請檢查執行電腦的網路 |
| `model_not_found_or_unavailable` | 模型不存在或目前無法使用 | 在 Agent 設定中改選可用模型 |
| `context_overflow` | 上下文超出模型上下文視窗 | 縮小任務範圍或減少輸入內容 |
| `missing_config` | 缺少 API key 等必要設定 | 補上 Agent 環境變數或工具設定 |
| `runtime_missing_executable` | 找不到 AI 程式開發工具的可執行檔 | 重新安裝該工具，請參閱[安裝 AI 程式開發工具](/install-agent-runtime) |
| `runtime_version_unsupported` | AI 程式開發工具版本過舊 | 升級該工具 |
| `process_failure` | 工具程序異常結束 | 查看執行日誌，找出原因後再重試 |
| `empty_or_unparseable_output` | 工具沒有輸出，或輸出內容無法解析 | 重試；若問題重複發生，請檢查工具安裝 |
| `agent_timeout` | 工具長時間沒有回應，因此遭到終止 | 重試或縮小任務範圍 |
| `unknown` | 無法分類的失敗 | 查看執行日誌中的原始錯誤 |

## 手動重試

在執行日誌中點選某列的重試按鈕，會再次呼叫**當時負責這次執行的 Agent**。即使任務後來換了負責人，也不會改用新的負責人。

重試會盡量保留上次寫入本機目錄的檔案。如果原工作階段仍可安全使用，且由同一個執行環境領取，也會接續先前的工作階段。若遇到脈絡溢位或無效要求等可能污染工作階段的錯誤，系統會在原工作目錄開啟新的工作階段。若原目錄已不存在，則會改用新的工作目錄。

你也可以透過 CLI 重新執行目前的任務：

```bash
multica issue rerun <issue-id>
```

這個指令沒有指定特定的歷史執行，因此會使用目前的任務負責 Agent，並從新的工作階段和工作目錄開始。

## 執行完成與任務完成

`completed` 只表示這次執行正常結束，不代表任務目標已確認完成。你仍可以檢查結果、繼續討論、補充要求或再次觸發 Agent。

任務是否完成，應以實際進度和任務狀態為準。

## 狀態與逾時速查

以下數值是伺服器的預設設定，可供排查時快速參照。

| 狀態 | 含義 | 逾時與後果 |
| --- | --- | --- |
| `deferred` | 已排定稍後觸發 | 到達預定時間後進入 `queued`，再依下方規則計時 |
| `queued` | 等待執行環境領取 | 只要執行環境仍傳送心跳，就會持續等待；而且無論如何，排入佇列後至少會保留一個重新連線寬限期。兩段時間都過去後才會失敗，且不會自動重試 |
| `dispatched` | 執行環境已領取，正在啟動工具 | 停留超過 **5 分鐘**就會視為失敗 |
| `waiting_local_directory` | 等待本機目錄鎖釋放 | 沒有獨立逾時；目錄釋放後會回到啟動流程 |
| `running` | AI 程式開發工具正在執行 | 沒有固定時長上限；以執行環境心跳判定是否仍在線。心跳每 15 秒傳送一次；執行環境失去心跳後，最遲約 3 分鐘會判定為離線，其上的執行也會失敗 |

自動重試只適用於以下暫時性故障，而且只會用在任務或 Chat 觸發的執行（自動化的**只執行**模式除外）：

| 可自動重試的失敗原因 | 執行次數上限 |
| --- | --- |
| 執行環境離線 | 預設 2 次（首次執行 + 1 次重試） |
| 常駐程式重新啟動後回收執行 | 預設 2 次 |
| 平台判定執行逾時 | 預設 2 次 |
| Codex 長時間無有效輸出 | 預設 2 次 |
| skill 套件下載失敗 | 預設 2 次（此時 Agent 程序尚未啟動；已下載的套件會使用本機快取） |
| 工具網路中斷 | 最多 3 次，最後一次延遲約 5 秒發起 |

其他失敗原因（驗證、用量、設定或模型等）都不會自動重試，必須先排除問題再手動重試。

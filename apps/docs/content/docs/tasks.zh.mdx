Agent每開始一次工作，Multica 就建立一條**執行記錄**，寫明這次執行由什麼觸發、交給了哪個Agent、進行到哪裡、最後是否成功。

## 任務與執行

任務保存工作的目標、討論、負責人和最終狀態；執行紀錄則記錄 Agent 處理這項工作的一次過程。

| | 任務 | 執行 |
| --- | --- | --- |
| 記錄內容 | 持續推進的一項工作 | Agent 的一次執行 |
| 持續時間 | 可反覆討論、補充和重新指派 | 從觸發開始，直到完成、失敗或取消 |
| 數量關係 | 一項任務可以有多次執行 | 每次執行都有獨立紀錄 |

同一個任務可以先後交給不同的Agent，也可以在失敗後重新執行。每次都產生一條新的執行記錄，舊記錄不會被覆蓋。

## 觸發來源

以下操作會觸發一次執行：

- 把任務分配給Agent或小隊。
- 在留言中提及Agent。
- 在對話中向Agent傳送訊息。
- 由自動化按計劃或外部事件觸發。
- [任務喚醒](/issue-wakeups)的事件、時間或條件到了。

入口不同，Agent拿到的上下文也不同，執行方式則是一樣的：Multica 建立執行，runtime領取它，再呼叫Agent配置的 AI 開發工具。

## 執行過程

一次執行通常會經過以下狀態：

| 狀態 | 意義 |
| --- | --- |
| `deferred` | 已安排稍後觸發，到達指定時間後進入佇列 |
| `queued` | 等待執行環境領取 |
| `dispatched` | 執行環境已領取，正在啟動 AI 程式開發工具 |
| `waiting_local_directory` | 目標本機目錄正由另一項執行使用，等待目錄鎖釋放 |
| `running` | AI 程式開發工具正在執行 |
| `completed` | 這次執行已正常結束 |
| `failed` | 執行出錯或中斷 |
| `cancelled` | 執行被手動停止 |

runtime線上時，新執行通常很快開始；執行入隊後runtime離線，執行會留在佇列中等它恢復。排得久不會讓執行過期：runtime還在發心跳，就說明它只是忙，積壓的執行可以一直排下去。排隊中的執行要**同時**滿足兩個條件才會失敗：繫結的runtime心跳缺席超過重連寬限期，**並且**這條執行自己也已經排隊滿這麼久。第二個條件照顧的是"指派給一臺已經休眠的機器"的情況：執行不會立刻失敗，你有完整的一個寬限期把機器喚醒。

<Callout type="info">
如果觸發前系統已經知道目標runtime離線，部分即時操作會直接提示當前無法執行，不再建立一條沒人能領取的執行。
</Callout>

只要執行環境持續正常傳送心跳，長時間執行就不會僅因耗時太久而被伺服器強制終止。執行環境會依實際活動判斷程序是否卡住；相關設定請參閱[環境變數](/environment-variables#常駐程式設定)。

## 查看執行記錄

任務產生的所有執行都列在任務右側欄的**執行日誌**裡。這一段預設展開：進行中的執行固定在最上面，下面是**最近**結束的 3 次執行；更早的記錄點**開啟時間線**檢視。每一行顯示觸發來源、執行Agent和狀態。沒看到這一段時，用任務頂部的面板按鈕開啟右側欄；視窗較窄時它預設收起。

頁面開著時，執行日誌透過即時連線自動更新，新的執行、狀態變化和Agent的留言會直接出現，不用手動重新整理。

Agent工作期間，任務頂部還有一個即時狀態條，例如 "Engineer 在工作"。懸停可以看到同樣的進行中執行，不用離開當前頁面。

在執行日誌裡：

- 點選某一行的 **檢視記錄**，檢視Agent的訊息、工具呼叫和錯誤資訊。執行還在進行時，彈窗開著的這段時間內容會即時追加，也可以用 **最新在前**切換事件順序。
- 停止排隊中、啟動中、等待本地目錄或正在工作的執行。
- 對失敗或已取消的執行發起重試。

執行日誌還彙總這條任務的**已花費**、**Token** 和**Agent工作**時長，每次執行對應一根費用條。點合計、費用條或**開啟時間線**，開啟**執行記錄**對話方塊：按次或累計檢視費用，按Agent和模型拆分，並列出失敗和取消的次數。費用是估算值，怎麼算的以及整個工作區的用量見[統計](/analytics#任務的花費)。

## 失敗與自動重試

執行環境短暫離線、常駐程式重新啟動、執行逾時或 AI 程式開發工具網路中斷等暫時性故障，都可能觸發自動重試。一般執行預設最多嘗試兩次；工具網路中斷最多嘗試三次。

Agent自身返回的錯誤通常不會自動重試。鑑權失效、額度不足、配置錯誤、模型無法完成請求，都要先處理原因，再手動重試。

自動化的**只執行**模式不會自動重試，以免和下一次排程重疊。**建立任務**模式會建立一般任務執行，遇到基礎架構故障時仍依上述規則重試。兩種模式的最終結果都能在自動化的執行紀錄中查看。

當任務沒有其他進行中的執行，也沒有等待重試的執行時，執行失敗會將 `in_progress` 任務退回 `todo`。

## 失敗原因參考

執行日誌和[統計](/analytics#錯誤頁籤)裡的失敗原因分兩類：不帶字首的原因碼由平臺記錄，`agent_error.*` 由 AI 開發工具的報錯歸類而來。

## 手動重試

在執行日誌中點選某列的重試按鈕，會再次呼叫**當時負責這次執行的 Agent**。即使任務後來換了負責人，也不會改用新的負責人。

重試會盡量保留上一次已經寫入本地目錄的檔案。原會話仍然安全、又由同一個runtime領取時，會接著之前的會話繼續。上下文溢位、無效請求這類會汙染會話的錯誤，會在原工作目錄上開新會話；原目錄已經不存在時，改用新的工作目錄。

透過 CLI 找到原執行，再重試：

```bash
multica issue runs <issue-id> --full-id
multica issue rerun-task <run-id>
```

使用完整執行 UUID 時可以省略 `--issue`；短 ID 字首必須用 `--issue` 指定任務。命令會沿用原Agent和觸發上下文，會話與目錄的複用規則和重試按鈕相同。新增 `--fresh` 可從新的會話和工作目錄開始。

舊命令 `multica issue rerun <issue-id>` 已棄用，並從幫助列表中隱藏。現有指令碼仍可使用它，行為保持為讓當前負責人從新會話和工作目錄開始。

## 執行完成與任務完成

`completed` 只表示這一次執行正常結束，不代表任務的目標已經確認達成。執行結束後，仍然可以檢查結果、繼續討論、補充要求或再次觸發Agent；任務是否完成，看它的狀態。

## 狀態與逾時速查

以下數字是伺服器的預設配置。

| 狀態 | 含義 | 逾時與後果 |
| --- | --- | --- |
| `deferred` | 已安排稍後觸發 | 到達預定時間後進入 `queued`，再按下面的規則計時 |
| `queued` | 等待runtime領取 | 只要runtime還在心跳就一直等待，並且無論如何都會在入隊後至少保留一個重連寬限期；兩個視窗都過去才會失敗，且不會自動重試 |
| `dispatched` | runtime已領取，正在啟動工具 | 停留超過 **5 分鐘**按失敗處理 |
| `waiting_local_directory` | 等待本地目錄鎖釋放 | 沒有獨立超時；目錄釋放後回到啟動流程 |
| `running` | AI 開發工具正在執行 | 不設固定時長上限；以runtime心跳判定存活，心跳每 15 秒一次，失去心跳的runtime最遲約 3 分鐘被判為離線。其上的執行要等心跳缺席超過重連寬限期（`MULTICA_RUNTIME_RECONNECT_GRACE`，預設 3 小時）才失敗；daemon重啟時，會直接回收這些執行 |

自動重試只適用於以下暫時性故障，而且只會用在任務或 Chat 觸發的執行（自動化的**只執行**模式除外）：

| 可自動重試的失敗原因 | 執行次數上限 |
| --- | --- |
| 執行環境離線 | 預設 2 次（首次執行 + 1 次重試） |
| 常駐程式重新啟動後回收執行 | 預設 2 次 |
| 平台判定執行逾時 | 預設 2 次 |
| Codex 長時間無有效輸出 | 預設 2 次 |
| skill 套件下載失敗 | 預設 2 次（此時 Agent 程序尚未啟動；已下載的套件會使用本機快取） |
| 工具網路中斷 | 最多 3 次，最後一次延遲約 5 秒發起 |

其他失敗原因（驗證、用量、設定或模型等）都不會自動重試，必須先排除問題再手動重試。

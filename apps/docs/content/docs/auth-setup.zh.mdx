Multica 預設使用電子郵件驗證碼登入，也可額外啟用 Google OAuth。既有使用者隨時都能再次登入；註冊限制只決定能否建立新帳號。

## 電子郵件驗證碼

使用者輸入電子郵件地址後，Multica 會寄送 6 位數驗證碼。驗證碼的有效期限為 15 分鐘；驗證成功後，瀏覽器會收到登入 cookie。本繁中分支的有效期限為 15 分鐘，與英文原文提到的 10 分鐘不同。

郵件可透過 Resend 或 SMTP 寄送。兩者都已設定時，會優先使用 `SMTP_HOST`。

### 使用 Resend

1. 在 [Resend](https://resend.com/) 驗證寄件網域並建立 API key。
2. 設定：

 ```dotenv
 RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
 RESEND_FROM_EMAIL=noreply@example.com
 ```

3. 重新啟動 API 服務。

`RESEND_FROM_EMAIL` 必須使用已在 Resend 驗證的網域。

### 使用 SMTP

至少需要設定主機和寄件地址：

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

常見連線方式：

| 場景 | 設定 |
|---|---|
| 內部匿名 relay | `SMTP_PORT=25`，帳號和密碼留空 |
| STARTTLS | `SMTP_PORT=587`；伺服器支援時預設會升級為 TLS |
| 隱含 TLS | `SMTP_PORT=465`，或明確設定 `SMTP_TLS=implicit` |

如果未設定 `SMTP_FROM_EMAIL`，會改用 `RESEND_FROM_EMAIL`。私有 CA 或自簽憑證需要將 CA 加入容器的信任存放區；`SMTP_TLS_INSECURE=true` 會略過憑證驗證，只應在可信任的內部網路中暫時使用。

有些要求較嚴格的 relay 還需要有效的 EHLO 名稱：

```dotenv
SMTP_EHLO_NAME=mail.example.com
```

### 無郵件服務時的行為

伺服器仍會啟動，但驗證碼和邀請連結只會寫入日誌，不會寄出郵件。這適合本機開發，不適合正式環境。

啟動日誌會說明目前使用的是 `Resend API`、`SMTP relay` 還是 `DEV mode`。

## 本機固定驗證碼

本機自動化測試可以設定固定驗證碼：

```dotenv
APP_ENV=development
MULTICA_DEV_VERIFICATION_CODE=888888
```

驗證碼必須是 6 位數字。`APP_ENV=production` 時會忽略固定驗證碼。

<Callout type="warning">
請勿在可從公網連線的執行個體啟用固定驗證碼。正式環境應設定 `APP_ENV=production`，並讓 `MULTICA_DEV_VERIFICATION_CODE` 保持空白。
</Callout>

## Google 登入

1. 在 [Google Cloud Console](https://console.cloud.google.com/) 建立 OAuth 2.0 client。
2. 將 Multica 前端的回呼網址加入 **Authorized redirect URIs**：

 ```text
 https://multica.example.com/auth/callback
 ```

3. 設定：

 ```dotenv
 GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
 GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxx
 GOOGLE_REDIRECT_URI=https://multica.example.com/auth/callback
 ```

4. 重新啟動 API 服務。

Google Console 和 `GOOGLE_REDIRECT_URI` 中的網址必須完全一致，包括通訊協定、連接埠和結尾斜線。設定生效後，登入頁會顯示 Google 登入按鈕；不需要重新建置前端映像檔。

## 註冊範圍控制

三個變數共同決定能否建立新帳號：

| 變數 | 作用 |
|---|---|
| `ALLOWED_EMAILS` | 允許註冊的完整電子郵件地址，多個值以逗號分隔 |
| `ALLOWED_EMAIL_DOMAINS` | 允許註冊的電子郵件網域，多個值以逗號分隔 |
| `ALLOW_SIGNUP` | 未設定任何允許清單時，是否允許註冊；預設 `true` |

依下列順序判斷：

1. 電子郵件地址符合 `ALLOWED_EMAILS`，允許註冊；
2. 或電子郵件網域符合 `ALLOWED_EMAIL_DOMAINS`，允許註冊；
3. 未設定允許清單且 `ALLOW_SIGNUP=true`，允許註冊；
4. 否則，若該地址有待接受且未過期的工作區邀請，也允許註冊；
5. 其他情況均拒絕。

常見設定方式：

```dotenv
# 允許公司網域和受邀使用者
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# 另外允許一位外部協作者
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
即使 `ALLOW_SIGNUP=false`，兩份允許清單仍可作為明確的例外清單。
</Callout>

## 邀請與註冊限制

待接受且未過期的工作區邀請可讓該電子郵件地址建立帳號，即使 `ALLOW_SIGNUP=false`，或地址不符合 `ALLOWED_EMAILS`、`ALLOWED_EMAIL_DOMAINS` 也一樣。`ALLOW_SIGNUP=true` 且已設定允許清單時也適用這項例外：允許清單不會排除持有有效邀請的使用者。

既有使用者仍可登入。新使用者若不符合允許清單，且未開放不受限制的註冊，就需要有待接受且未過期的邀請；邀請不存在、已過期、已接受、已拒絕或已撤銷時，都不會取得註冊權限。要求登入碼時會檢查邀請，建立帳號時也會再次檢查，包括透過 Google 登入建立帳號的情況。

一般受邀者不必另外加入 `ALLOWED_EMAILS`，也不必重新啟動伺服器。建立帳號後，仍須透過一般邀請流程接受邀請，才能加入工作區。

撤銷邀請不會刪除透過該邀請建立的帳號，也不會阻止該帳號登入。

## 登入有效期

工作階段會採用滑動續期。下方的有效期限是**閒置時間**上限，不是從登入時開始倒數：工作階段剩餘時間少於一半時，下一個請求會將它延長至完整期限，因此持續使用的帳號不會定時登出。沒有絕對期限上限。

這項限制只會在單一方向生效。只有剩餘期限低於一半時才會續期，因此若最後一次使用時還剩超過一半期限，工作階段就不會延長。可確保工作階段維持有效的閒置時間是下方期限的一半，而非全部期限。

可透過 `AUTH_TOKEN_TTL` 調整，接受 Go duration 或正整數秒數：

```dotenv
AUTH_TOKEN_TTL=720h
```

最小值為 `60s`；更小的值會提高至 `60s`，並在啟動時記錄警告。低於此值時，伺服器計算出的續期檢查間隔會小於用戶端設定的下限，導致用戶端檢查續期的頻率低於工作階段的存活時間。

修改後請重新啟動 API 服務。新值會套用到之後簽發或續期的工作階段；既有工作階段會在下次續期時採用新的有效期限。

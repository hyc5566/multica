<Callout type="warn">
**僅適用於自部署的 Multica。** 此整合只在你**自己部署 Multica** 時可用，Multica 雲端不提供。這裡的「自託管」指的是 **Multica 本身自部署**——通常是為了讓它能訪問你自己網路內的 Git 實例。需要服務端運維開啟（`MULTICA_VCS_INTEGRATION_ENABLED=true`）並設定 `MULTICA_VCS_SECRET_KEY`；在此之前，設定 → 程式碼裡不會出現該行。
</Callout>

Multica 按工作區連接自託管的 Git 程式碼託管：**Forgejo**、**Gitea** 或 **GitLab**。連接後，任何在分支名或標題中包含任務編號（例如 `MUL-123`）、或在正文的關閉關鍵字後寫出該編號（`Closes MUL-123`）的 Pull Request（GitLab 為 Merge Request）都會**自動關聯**到對應的 [任務](/issues)，出現在任務側欄的 **Pull requests** 中；任務的所有關聯 PR 都合併後，任務會改為工作區選定的狀態（預設「完成」）。head commit 的 CI 會以檢查條的形式顯示在卡片上。

這些程式碼託管與 GitHub 並行工作：一個工作區可任意組合使用。

<Callout type="info">
與 GitHub 不同，這些程式碼託管沒有「App」模型。每個工作區儲存自己的實例地址和訪問令牌，並在其倉庫或組織上註冊 Webhook。令牌和 Webhook 密鑰均加密儲存。
</Callout>

## 前置條件（服務端）

先為該部署開啟此整合。它預設關閉，未開啟時該板塊不會出現：

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

官方自部署 `docker compose` 檔案（`docker-compose.selfhost.yml`）已為你設定好。

再設定一個 base64 編碼的 32 字節密鑰，供服務端加密儲存的憑據。未設定時，連接表單將不可用。

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 32 字節密鑰>
```

兩者都必需：開關決定是否提供該功能，密鑰用於加密儲存的令牌與 Webhook 密鑰。連接、Webhook、輪換都要求兩者同時滿足。

設定 `MULTICA_PUBLIC_URL` 為服務端的公網基礎地址，Multica 即可直接給出可粘貼的 Webhook 地址；否則介面只顯示 Webhook 路徑，需自行拼接來源地址。

## 連接工作區

1. 在程式碼託管中建立具備倉庫讀取權限的訪問令牌：
 - **Forgejo / Gitea**：設定 → 應用。
 - **GitLab**：具備 `read_api` 權限的個人（或群組/專案）訪問令牌。
2. 在 Multica 中開啟 **設定 → 程式碼**，在 **自託管 Git** 一行點擊 **連接**。
3. 選擇**提供方**，填寫實例地址（例如 `https://forgejo.example.com`）和訪問令牌，點擊 **連接**。Multica 會先用該令牌訪問實例進行校驗，再儲存。
4. 複製連接後顯示的 **Webhook 地址** 與 **Webhook 密鑰**。

<Callout type="warn">
Webhook 密鑰只顯示一次，請在離開頁面前複製。重新連接同一實例會輪換令牌與密鑰。
</Callout>

### 實例使用私有 CA

如果點擊 **連接** 後提示提供方的證書 "is signed by a certificate authority this server does not trust"，說明實例的 HTTPS 證書由內部 CA 簽發（或是自簽名證書），而 Multica 服務端不信任這個 CA。需要由服務端管理員把該 CA 加入後端的信任庫：使用 Helm 時設定 `backend.extraCACerts.configMap`；使用 Docker Compose 時掛載 CA 並設定 `SSL_CERT_DIR`。具體步驟見 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)。

Multica 不提供跳過證書校驗的選項，因為連接請求會攜帶你的訪問令牌。如果提示證書與主機名不匹配，或證書校驗失敗（例如已過期），需要修復證書本身，信任 CA 解決不了。

## 註冊 Webhook

在倉庫（或組織/群組，以覆蓋所有倉庫）：

**Forgejo / Gitea** —— 設定 → Webhook → 新增 Webhook → Forgejo/Gitea：

- **目標 URL**：上一步的 Webhook 地址。
- **HTTP 方法** `POST`，**內容類型** `application/json`。
- **密鑰**：Webhook 密鑰（用於校驗 `X-Gitea-Signature` HMAC）。
- **觸發事件**：勾選 **Pull Request**，並勾選 **Commit Status** 以鏡像 CI。

**GitLab** —— 設定 → Webhooks：

- **URL**：Webhook 地址。
- **Secret token**：Webhook 密鑰（作為 `X-Gitlab-Token` 傳送並逐字比對）。
- **觸發器**：啟用 **Merge request events**，並啟用 **Pipeline events** 以鏡像 CI。

Multica 會用儲存的密鑰校驗每次投遞，因此沒有匹配密鑰的 Webhook 會被拒絕。

## 鏡像的內容

- **Pull / Merge Request** —— open、closed、merged、draft 狀態，以及作者、分支和（在程式碼託管提供時）diff 統計。
- **任務關聯** —— 標題或分支中的編號會將 PR 關聯到任務，正文中的編號只有緊跟關閉關鍵字時才會關聯；正文中的普通提及不會建立任何關聯。任務的所有關聯 PR（包括 GitHub 與自託管平臺上的）都合併後，任務會改為工作區選定的狀態，遵循與 [GitHub](/github-integration) 相同的設定和規則。連接平臺後，本頁也會顯示同一項 **PR 合併後，任務狀態改為** 設定。
- **CI** —— Forgejo/Gitea 的提交狀態與 GitLab 的流水線會彙總為 head commit 的通過/失敗/進行中檢查條。

## Agent 建立 Pull Request

建立 PR 無需在 Multica 中進行任何程式碼託管設定。Agent 在執行環境中檢出倉庫，並使用執行環境主機自身的 Git 憑據推送分支和建立 PR。要讓 Agent 在某個程式碼託管上工作，確保 daemon 主機能對其完成認證即可——例如 SSH 部署密鑰，或主機 Git 憑據助手中的令牌——再像往常一樣新增倉庫地址。倉庫檢出支援任意 Git URL，因此無需提供方專屬設定。

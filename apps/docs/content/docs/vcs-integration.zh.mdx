<Callout type="warn">
**僅適用於自行部署的 Multica。** 此整合只在你**自己部署 Multica** 時可用，Multica 雲端不提供。這裡的"自行託管"指的是 **Multica 本身自行部署**——通常是為了讓它能存取你自己網路內的 Git 實例。需要伺服器端維運人員開啟（`MULTICA_VCS_INTEGRATION_ENABLED=true`）並設定 `MULTICA_VCS_SECRET_KEY`；在此之前，設定 → 程式碼裡不會出現該行。
</Callout>

Multica 按工作區連線自行託管的 Git 平台：**Forgejo**、**Gitea** 或 **GitLab**。連線後，任何在分支名或標題中包含任務編號（例如 `MUL-123`）、或在內文的關閉關鍵字後寫出該編號（`Closes MUL-123`）的 Pull Request（GitLab 為 Merge Request）都會**自動關聯**到對應的 [任務](/issues)，出現在任務側欄的 **Pull requests** 中；任務的所有關聯 PR 都合併後，任務會改為工作區選定的狀態（預設"完成"）。head commit 的 CI 會以檢查條的形式顯示在卡片上。

這些 Git 平台與 GitHub 並行工作：一個工作區可任意組合使用。

<Callout type="info">
與 GitHub 不同，這些 Git 平台沒有"App"模型。每個工作區儲存自己的實例位址和存取權杖，並在其儲存庫或組織上註冊 Webhook。權杖和 Webhook 金鑰均加密儲存。
</Callout>

## 前置條件（伺服器端）

先為該部署開啟此整合。它預設關閉，未開啟時這個區塊不會出現：

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

官方自行部署 `docker compose` 文件（`docker-compose.selfhost.yml`）已為你設定好。

再設定一個 base64 編碼的 32 位元組金鑰，供伺服器端加密儲存的憑證。未設定時，連線表單將不可用。

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 編碼的 32 位元組金鑰>
```

兩者都必需：開關決定是否提供該功能，金鑰用於加密儲存的權杖與 Webhook 金鑰。連線、Webhook、輪換都要求兩者同時滿足。

設定 `MULTICA_PUBLIC_URL` 為伺服器端的公網基礎位址，Multica 即可直接給出可貼上的 Webhook 位址；否則介面只顯示 Webhook 路徑，需自行拼接來源位址。

## 連線工作區

1. 在 Git 平台中建立具備儲存庫讀取權限的存取權杖：
 - **Forgejo / Gitea**：設定 → 應用。
 - **GitLab**：具備 `read_api` 權限的個人（或群組/專案）存取權杖。
2. 在 Multica 中開啟 **設定 → 程式碼**，在 **自行託管 Git** 那一列點選 **連線**。
3. 選擇**供應商**，填寫實例位址（例如 `https://forgejo.example.com`）和存取權杖，點選 **連線**。Multica 會先用該權杖存取實例進行驗證，再儲存。
4. 複製連線後顯示的 **Webhook 位址** 與 **Webhook 金鑰**。

<Callout type="warn">
Webhook 金鑰只顯示一次，請在離開頁面前複製。重新連線同一實例會輪換權杖與金鑰。
</Callout>

### 實例使用私有 CA

如果點選 **連線** 後提示供應商的憑證 "is signed by a certificate authority this server does not trust"，說明實例的 HTTPS 憑證由內部 CA 簽發（或是自簽憑證），而 Multica 伺服器端不信任這個 CA。需要由伺服器端管理員把該 CA 加入後端的信任庫：使用 Helm 時設定 `backend.extraCACerts.configMap`；使用 Docker Compose 時掛載 CA 並設定 `SSL_CERT_DIR`。具體步驟見 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)。

Multica 不提供跳過憑證驗證的選項，因為連線請求會攜帶你的存取權杖。如果提示憑證與主機名稱不匹配，或憑證驗證失敗（例如已過期），需要修復憑證本身，信任 CA 解決不了。

## 註冊 Webhook

在儲存庫（或組織/群組，以覆蓋所有儲存庫）：

**Forgejo / Gitea** —— 設定 → Webhook → 新增 Webhook → Forgejo/Gitea：

- **目標 URL**：上一步的 Webhook 位址。
- **HTTP 方法** `POST`，**內容型別** `application/json`。
- **金鑰**：Webhook 金鑰（用於驗證 `X-Gitea-Signature` HMAC）。
- **觸發事件**：勾選 **Pull Request**，並勾選 **Commit Status** 以鏡像 CI。

**GitLab** —— 設定 → Webhooks：

- **URL**：Webhook 位址。
- **Secret token**：Webhook 金鑰（作為 `X-Gitlab-Token` 傳送並逐字比對）。
- **觸發器**：啟用 **Merge request events**，並啟用 **Pipeline events** 以鏡像 CI。

Multica 會用儲存的金鑰驗證每次投遞，因此沒有匹配金鑰的 Webhook 會被拒絕。

## 鏡像的內容

- **Pull / Merge Request** —— open、closed、merged、draft 狀態，以及作者、分支和（在Git 平台提供時）diff 統計。
- **任務關聯** —— 標題或分支中的編號會將 PR 關聯到任務，內文中的編號只有緊跟關閉關鍵字時才會關聯；內文中的普通提及不會建立任何關聯。任務的所有關聯 PR（包括 GitHub 與自行託管平台上的）都合併後，任務會改為工作區選定的狀態，遵循與 [GitHub](/github-integration) 相同的設定和規則。連線平台後，本頁也會顯示同一項 **PR 合併後，任務狀態改為** 設定。
- **CI** —— Forgejo/Gitea 的提交狀態與 GitLab 的管線會匯總為 head commit 的通過/失敗/進行中檢查條。

## Agent 建立 Pull Request

建立 PR 無需在 Multica 中進行任何程式碼託管設定。Agent 在執行環境中簽出儲存庫，並使用執行環境主機自身的 Git 憑證推送分支和建立 PR。要讓 Agent 在某個 Git 平台上工作，確保 daemon 主機能對其完成認證即可——例如 SSH 部署金鑰，或主機 Git 憑證輔助程式中的權杖——再像往常一樣新增儲存庫位址。儲存庫簽出支援任意 Git URL，因此無需供應商專屬設定。

Multica 在程序啟動時讀取環境變數。修改後通常需要重新啟動對應的 API、Web 或常駐程式。Docker Compose 的 `docker compose restart` 不會重新讀取 `.env`，要用 `up -d` 重建容器才能生效。

本頁只列面向部署者的設定；測試變數和內部執行變數不在這裡展開。本頁是分組參考；完整部署步驟見[自行託管快速上手](/self-host-quickstart)。

## 正式環境最小設定

```dotenv
DATABASE_URL=postgres://user:password@postgres:5432/multica?sslmode=require
JWT_SECRET=<long-random-secret>
APP_ENV=production
FRONTEND_ORIGIN=https://multica.example.com
MULTICA_APP_URL=https://multica.example.com
MULTICA_PUBLIC_URL=https://api.multica.example.com
```

還需要選擇一種電子郵件服務，否則驗證碼和邀請只會寫入伺服器端日誌。

<Callout type="warning">
`JWT_SECRET` 在正式環境為必填：當 `APP_ENV=production` 時，後端會在金鑰為空或等於已知預留值時拒絕啟動（用 `openssl rand -hex 32` 產生）。也不要在正式環境設定 `MULTICA_DEV_VERIFICATION_CODE`。
</Callout>

## API 與資料庫

| 變數 | 預設值 | 說明 |
|---|---|---|
| `DATABASE_URL` | 本機 `multica` 資料庫 | PostgreSQL 連線位址 |
| `DATABASE_MAX_CONNS` | `25` | 單一 API 程序的最大資料庫連線數 |
| `DATABASE_MIN_CONNS` | `5` | 單一 API 程序保留的最小連線數 |
| `DATABASE_SEARCH_WORK_MEM_MB` | `64` | 每個搜尋計畫節點的 PostgreSQL `work_mem` 上限（MB）；設為 `1`–`64` 可調低，設為 `0` 則沿用資料庫/工作階段預設值 |
| `DATABASE_REPLICA_URL` | 空 | 可選的 PostgreSQL 唯讀複本資料庫連線位址；新連線會強制驗證唯讀狀態，業務仍需在程式碼中明確選擇最終一致性的讀取 |
| `DATABASE_REPLICA_MAX_CONNS` | `10` | 單一 API 程序的最大複本資料庫連線數 |
| `DATABASE_REPLICA_MIN_CONNS` | `0` | 單一 API 程序保留的最小複本資料庫連線數 |
| `MULTICA_DATABASE_STARTUP_TIMEOUT` | `3m` | 容器啟動過程中，migration 與 API 共用的暫時性資料庫故障重試時長；設為 `0` 時每個階段只嘗試一次 |
| `MULTICA_DATABASE_CONNECT_TIMEOUT` | `5s` | 啟動期間單次資料庫連線的備援逾時；pgx 原生 `connect_timeout`、`PGCONNECT_TIMEOUT` 或 service 設定優先 |
| `PORT` | `8080` | API 監聽連接埠 |
| `JWT_SECRET` | 正式環境必填 | 登入 JWT、部分簽章流程使用的金鑰；正式環境對空值或已知預留值拒絕啟動 |
| `APP_ENV` | 空 | 正式環境設為 `production` |
| `AUTH_TOKEN_TTL` | `720h`（30 天） | 瀏覽器 JWT 與 cookie 有效期；接受 Go duration 或正整數秒數。工作階段會滑動續期：有效期經過一半後，持續使用的工作階段會被續期而不是到期。低於 `60s` 的取值會按 `60s` 處理 |
| `LOG_LEVEL` | 應用預設 | 日誌層級 |
| `MULTICA_SHUTDOWN_HOLD_DURATION` | `0` | 收到終止訊號後，開始平順關閉前等待多久 |
| `MULTICA_RUNTIME_RECONNECT_GRACE` | `3h` | 執行環境離線後可重新連線且不終止進行中的執行的寬限時間；低於 `150s` 時按 `150s` 處理 |

在 Kubernetes 中設定 shutdown hold 時，`terminationGracePeriodSeconds` 要大於 hold 與實際退出所需時間之和。

主要資料庫與複本資料庫的連線上限彼此獨立，需要按全部 API 程序的連線數總和預留 PostgreSQL 叢集連線額度。複本資料庫連線預設五分鐘回收一次，以便在提升為主要資料庫後重新驗證唯讀狀態。複本資料庫連線失敗時，基礎設施會自動改用主要資料庫並短暫開啟被動熔斷器，不會增加背景資料庫探測。應用不保證複本資料庫資料的最長延遲時間；請在資料庫層監控複製延遲，一致性敏感的讀取繼續走主要資料庫。

## 對外位址與瀏覽器存取

| 變數 | 預設值 | 說明 |
|---|---|---|
| `FRONTEND_ORIGIN` | 空 | 使用者存取的前端 origin；用於 CORS、cookie 和邀請連結 |
| `MULTICA_APP_URL` | 回退到 `FRONTEND_ORIGIN` | 使用者可存取的 Web 位址；CLI 登入和帳號綁定連結使用它 |
| `MULTICA_PUBLIC_URL` | 空 | 公網 API 位址；用於 webhook URL 和執行環境連線說明 |
| `MULTICA_DAEMON_SERVER_URL` | 回退到 `MULTICA_PUBLIC_URL`，再回退到 `MULTICA_APP_URL` / `FRONTEND_ORIGIN` | API 程序寫入 `multica setup self-host` 命令的伺服器端位址；常駐程式存取 API 的位址與公網 webhook 位址不同時設定 |
| `CORS_ALLOWED_ORIGINS` | 空 | 額外允許的 HTTP origin，逗號分隔 |
| `ALLOWED_ORIGINS` | 回退到 CORS / 前端位址 | WebSocket origin 允許清單，逗號分隔 |
| `COOKIE_DOMAIN` | 空 | 前後端不同 host 且瀏覽器直接存取 API 域時必須設定；單域部署保持為空 |

<Callout type="warning">
`MULTICA_DAEMON_SERVER_URL` 會由無需認證的 `/api/config` 介面回傳，用戶端可以讀取。請將它視為公開設定，切勿填入憑證、權杖或其他金鑰。
</Callout>

前端和 API 使用不同 host、且瀏覽器直接存取 API 域時，必須設定 `COOKIE_DOMAIN`，否則瀏覽器讀不到 CSRF cookie——所有寫入請求回傳 `403 CSRF validation failed`，而讀請求一切正常。取值用能同時覆蓋兩個 host 的最窄父域（`.agent.example.com` 優於 `.example.com`）。它會把登入工作階段 cookie 擴散到該域下的所有 host，只有這些 host 都由同一個可信任的單位維運時才可用。修改後需要在兩個 host 上清除舊 cookie 並重新登入。若採用[自行託管快速上手](/self-host-quickstart#3-選擇存取方式)的同源設定範例（瀏覽器只存取 app 域），保持為空即可。不要填寫 IP 位址，瀏覽器會忽略帶 IP Domain 的 cookie。

<Callout type="warning">
自行託管部署需要設定 `FRONTEND_ORIGIN`。缺少它時，邀請連結、cookie 安全屬性和 WebSocket origin 驗證都可能與實際網域名稱不一致。
</Callout>

認證限流需要設定 `REDIS_URL`；未設定時，啟動日誌會提示認證限流已關閉。邀請限流在沒有 Redis 時仍使用程序記憶體，設定 Redis 後則在多個副本間共用額度。如果已設定的 Redis 暫時不可用，認證限流仍選擇放行，而邀請建立會回傳可重試的 `503`，不會在失去防護時傳送電子郵件。

## 伺服器端 LLM

這組設定用於伺服器端的輔助內容產生功能，例如對話標題；它不是 Agent 執行環境使用的 AI 程式開發工具憑證。

| 變數 | 預設值 | 說明 |
|---|---|---|
| `MULTICA_LLM_API_KEY` | 空 | OpenAI 相容 API key |
| `MULTICA_LLM_BASE_URL` | 空 | OpenAI 相容 endpoint |
| `MULTICA_LLM_DEFAULT_MODEL` | `gpt-5.6-luna` | 請求未指定模型時使用 |
| `MULTICA_LLM_MAX_RETRIES` | `2` | 單次呼叫的重試上限；`0` 表示停用重試，`1`–`5` 表示最多重試 N 次 |
| `MULTICA_LLM_DISABLE_THINKING` | `false` | 在每個請求中附帶 `chat_template_kwargs: {"enable_thinking": false}`，供支援該欄位的閘道關閉模型思考 |

`MULTICA_LLM_MAX_RETRIES` 是重試策略的唯一設定來源。不設定時使用預設的 2 次；設為 `0` 表示每次呼叫只發一個請求；設為 1–5 表示最多重試這麼多次。它是上限而不是配額：只有可重試的失敗才會消耗它，請求成功或呼叫方自身的逾時都會讓呼叫提前結束。其它取值（負數、非數字、大於 5）會讓服務啟動失敗，而不是被靜默糾正。上限是一個延遲預算：退避從 0.5s 開始翻倍，上限 8s，更大的預算會超出呼叫方自身的逾時，把可重試的失敗變成逾時失敗。重試覆蓋連線失敗以及 HTTP 408、409、429 和 5xx；其餘 4xx 直接回傳。服務啟動時會以 `llm retry policy` 印出生效策略，其中不包含任何憑證。

`MULTICA_LLM_DISABLE_THINKING` 面向"模型會先跑一段推理（thinking）並吃掉輔助呼叫延遲預算"的閘道。設為 `true`（或 `1`）時，伺服器端會在每個請求主體中附帶 `chat_template_kwargs: {"enable_thinking": false}`；支援轉送該欄位的閘道（vLLM/sglang 類部署、部分 GLM/Qwen 系的 LiteLLM 路由）會因此跳過思考階段。標準 OpenAI 端點會拒絕未知的請求主體欄位，所以僅在上游接受時啟用。GPT-5.6 系模型在後續提問建議請求中已由伺服器端附帶 `reasoning_effort: none`。工作階段自動命名不傳送推理欄位；只有當所設定的上游接受 `chat_template_kwargs` 時，此項才會影響它。可接受的取值為 `true`/`false` 和 `1`/`0`（不區分大小寫）；其它取值會讓服務啟動失敗。啟動日誌會在重試策略旁印出生效狀態。

有兩個功能會使用這一層，它們都會把聊天內容傳送到你設定的 endpoint：

- **對話標題自動產生** —— 傳送新對話中使用者的第一則訊息，原文傳送。附件不會包含在內。
- **後續提問建議**（Agent 回覆下方的按鈕）—— 傳送對話末尾的內容：最多 6 則訊息，其中被追問的那條回覆上限 3000 字元，更早的每條上限 800 字元。

API key 與 base URL 都為空時，這一層關閉，不會發出任何上游請求——上面兩個功能都不再傳送內容。如果你的政策不允許這一層把聊天內容發到部署之外，這就是受支援的設定方式：對話繼續使用用戶端根據第一則訊息產生的標題，後續提問按鈕不再出現，其餘功能不受影響。

<Callout type="info">
這只覆蓋輔助產生這一層。Agent 執行是另一條資料路徑：Agent 回覆對話時，由你的常駐程式呼叫該 Agent 的 AI 程式開發工具，用的是那個工具自己的憑證，常駐程式不會把上面的 `MULTICA_LLM_*` 設定傳給它。（Agent 自身需要的執行級 Multica 連線變數由常駐程式單獨注入。）把上面的變數留空不影響這條路徑——它由 Agent 的執行環境設定決定。
</Callout>

## 常駐程式設定

下面的變數在執行 Agent 的電腦上讀取，不是在 API 容器中讀取。

| 變數 | 預設值 | 說明 |
|---|---|---|
| `MULTICA_SERVER_URL` | `ws://localhost:8080/ws` | Multica API / WebSocket 位址，也接受 `http(s)` |
| `MULTICA_DAEMON_DEVICE_NAME` | 主機名稱 | 執行環境列表中的裝置名 |
| `MULTICA_AGENT_RUNTIME_NAME` | `Local Agent` | 執行環境顯示名 |
| `MULTICA_DAEMON_POLL_INTERVAL` | `30s` | 沒有喚醒事件時的執行輪詢間隔 |
| `MULTICA_DAEMON_WS_CLAIM_POLL_INTERVAL` | `3m` | 健康 WebSocket 下 claim 安全輪詢的上限，與 `MULTICA_DAEMON_POLL_INTERVAL` 獨立設定；向下抖動後預設實際為 `2m30s`–`2m45s`，舊 Server 或結果不確定的 claim 仍使用普通輪詢間隔 |
| `MULTICA_DAEMON_HEARTBEAT_INTERVAL` | `15s` | 心跳間隔 |
| `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` | `20` | 單一常駐程式的同時執行數上限 |
| `MULTICA_AGENT_TIMEOUT` | `0` | 單次執行的絕對時限；`0` 表示不設定 |
| `MULTICA_AGENT_IDLE_WATCHDOG` | `2h` | 沒有輸出且沒有工具執行時的靜默上限；`0` 表示整套 watchdog 關閉 |
| `MULTICA_AGENT_TOOL_WATCHDOG` | 同 `MULTICA_AGENT_IDLE_WATCHDOG` | 單一工具呼叫持續靜默的上限；只有希望工具比模型有更多餘量時才單獨設定，`0` 表示工具執行期間永不強制停止。Cursor 的背景 shell 在它啟動的程序退出前一直算作執行中；到達這個上限時，常駐程式會停止這些程序，並給 Cursor 一段新的 watchdog 預算來產出最終狀態結果。若程序歸屬或清理無法驗證，則回到普通的執行取消策略 |
| `MULTICA_OPENCODE_IDLE_WATCHDOG` | `10m` | OpenCode 專用靜默門檻 |
| `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` | 同 `MULTICA_AGENT_IDLE_WATCHDOG` | Codex 語意靜默門檻。Codex 自己的計時器看不到工具是否在執行，因此跟隨 idle / tool 預算中較大的那個，而不再單獨保留一個更短的上限 |
| `MULTICA_CODEX_FIRST_TURN_TIMEOUT` | `0` | 明確覆蓋 Codex 首輪無進展上限；`0` 保持預設值。實際首輪等待仍受 `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` 和總執行逾時限制——需將 `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` 設為嚴格大於此值（並留出餘量），否則等待會被截斷至該值，且會跳過模型目錄啟動重試。設為相等還不夠：語意計時器先啟動，兩者相等時仍可能丟失該重試 |
| `MULTICA_CODEX_HANDSHAKE_TIMEOUT` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 啟動握手上限；明確設定後會統一覆蓋兩類預算 |
| `MULTICA_CODEX_TURN_INTERRUPT_TIMEOUT` | `2s` | 任務取消後等待 Codex app-server 確認 `turn/interrupt` 並發出 `turn/completed` 的寬限期，以便在強制清理程序前保留最終 token 用量。主機異常緩慢時，可根據 daemon 日誌記錄的中斷延遲調整 |
| `MULTICA_DAEMON_AUTO_UPDATE` | Cloud `true`；自行託管 `false` | 是否自動檢查並更新 CLI |
| `MULTICA_DAEMON_AUTO_UPDATE_INTERVAL` | `6h` | 檢查更新的間隔 |
| `MULTICA_DAEMON_AUTO_RELOAD` | `true` | 是否在 `multica` 二進位執行檔被帶外替換（`brew upgrade`、重新下載、本機建置）後重新啟動到新二進位執行檔。與 `MULTICA_DAEMON_AUTO_UPDATE` 相互獨立 |
| `MULTICA_WORKSPACES_ROOT` | `~/multica_workspaces` | 執行工作目錄的根目錄 |
| `MULTICA_AGENT_TEMP_BASE` | `/tmp`（Linux/macOS） | 僅適用於 Linux/macOS。每次執行的私有暫存目錄的父目錄；必須是現有、可寫的絕對路徑，無效值會使執行啟動失敗，不會回退到 `/tmp`。請選擇較短的路徑——子工具可能會在其中綁定 AF_UNIX socket；Linux 的 `sun_path` 上限為 108 位元組，macOS 為 104 位元組 |
| `MULTICA_KEEP_ENV_AFTER_TASK` | `false` | 保留執行目錄供除錯使用 |

常駐程式注入 Agent task 的內部上下文見 [執行時的環境變數](/daemon-runtimes#執行環境中的任務變數)。

各 AI 程式開發工具可以使用 `MULTICA_<PROVIDER>_PATH` 覆蓋命令路徑；支援模型覆蓋的工具還可以使用 `MULTICA_<PROVIDER>_MODEL`。QwenPaw 和 MiniMax Code 沒有模型變數，因為 Multica 不會向它們傳模型；MiniMax Code 的路徑變數是 `MULTICA_MCODE_PATH`。詳見 [AI 程式開發工具對比](/providers#模型來源)。DeepSeek Harness 支援 `MULTICA_DSH_PATH` 和 `MULTICA_DSH_MODEL`（取值為 dsh 模型目錄中的模型 id，例如 `deepseek-official/deepseek-chat`）。

DeepSeek Harness 另外支援 `MULTICA_DSH_PROFILE_BUNDLE`：當 `multica` profile 缺失時，用它指定要安裝的 bundle，多個候選用逗號分隔、按序嘗試，每項可以是 npm 套件名稱、目錄或封裝好的 tarball。該變數預設不設定；Multica 驅動的 `--stdio` 協議正是由這個 profile 提供，所以不設定時不會改動 DSH 的安裝，常駐程式會報告缺少 profile，而不是註冊一個不可用的執行環境。Multica 自己的橋接還沒有發布到公開 npm registry，如何選取值見[安裝 AI 程式開發工具](/install-agent-runtime)；這裡填的東西會在沒有二次確認的情況下裝進每一台常駐程式主機的 DSH 家目錄，請當作供應鏈決策來對待。`MULTICA_DSH_PROFILE_BUNDLE` 開啟的安裝被刻意限制了範圍：每個常駐程式生命週期最多執行一次，只在探測確認 profile 確實缺失時執行；失敗時會把套件管理器自身的輸出記入日誌，且只有重新啟動常駐程式後才會重試。探測逾時、或回傳本常駐程式不支援的協議版本時，只做報告，絕不覆蓋安裝——常駐程式不會覆蓋一個明顯是刻意裝上去的 profile。排查時在常駐程式日誌中搜尋 `DSH runtime profile`；要撤銷安裝，刪除 `$DSH_HOME/profiles/multica`（預設 `~/.dsh/profiles/multica`）。

`MULTICA_DSH_PLUGIN_PATH` 用於覆蓋安裝時解析 pnpm 的目錄。`dsh plugin` 轉發到的那個 pnpm 由 DSH Desktop 放在它私有的 runtime-commands 目錄裡，macOS 和 Windows 都是如此，常駐程式會自動找到並加到 PATH 最前——包括較新版 Desktop 採用的帶版本號目錄結構。所以只有常駐程式找不到的安裝位置、或者你想讓安裝使用自己的 pnpm 時，才需要這個變數。一旦設定就完全取代自動查找：目錄不存在時，安裝會退回使用常駐程式 `PATH` 上的 pnpm，而不是內建的那個。Linux 上沒有 DSH Desktop，安裝始終使用 `PATH`。

Dim 支援 `MULTICA_DIM_PATH` 和 `MULTICA_DIM_MODEL`（dim 模型清單中的模型 ID）。ZeroClaw 支援 `MULTICA_ZEROCLAW_PATH`，但沒有模型變數；模型由 ZeroClaw 的 Agent 設定管理。

全機預設參數 `MULTICA_<PROVIDER>_ARGS` 目前支援 Claude Code、Codex、CodeBuddy、Qwen Code 和 QwenPaw 五款工具。對應變數是 `MULTICA_CLAUDE_ARGS`、`MULTICA_CODEX_ARGS`、`MULTICA_CODEBUDDY_ARGS`、`MULTICA_QWEN_ARGS` 和 `MULTICA_QWENPAW_ARGS`。例如：

```dotenv
MULTICA_CLAUDE_PATH=/opt/bin/claude
MULTICA_CLAUDE_ARGS=--max-turns 40
```

Cursor 已驗證的背景清理需要 Linux 6.9 及以上（程序群組 pidfd）、macOS 核心對程序身分查詢與 audit token 發訊號的支援，或 Windows 上成功分配的巢狀 Job Object。在 macOS 上，每個程序都按核心驗證的 PID version 發訊號，不需要加入同一 session 的程序群組；這些 macOS 介面是私有的，會在捕獲時做探測。無法認領的背景啟動會回傳它原本的工具結果並回到普通的 idle watchdog，工具 watchdog 為 `0` 時同樣如此。已經認領的工作在清理無法確認時會繼續算作執行中。當工具 watchdog 設為 `0` 時則完全沒有這個邊界：已認領的背景工作只要還活著就一直讓執行處於執行中，此時執行僅受 `MULTICA_AGENT_TIMEOUT` 約束，而它預設也是 `0`。

執行正常結束時，被認領的 Cursor 背景程序同樣會被停止，因此該次執行啟動的背景服務不會有意地在收尾之後繼續存活。macOS 可以透過保留的原始父程序身分識別後期產生的子程序，但無法證明中間程序在被觀察到之前就已消失的那條鏈路。這類程序、離開被追蹤程序群組的工作，以及持續的歸屬或發訊號錯誤，都可能留下殘餘的背景工作。未確認的清理會被記錄下來，且永遠不會換取一次"清理成功"的復原時間範圍；不會僅憑數字 PID 或程序群組就去終止未知程序。

優先順序為命令列 flag → 環境變數 → `~/.multica/config.json` → 內建預設。watchdog 的行為見[常駐程式與執行環境](/daemon-runtimes)。

### 常駐程式設定的持久化

常駐程式側的常用設定也可以寫入 `~/.multica/config.json`，不必依賴 shell 環境變數；命名 profile 的設定檔案在 `~/.multica/profiles/<name>/config.json`：

```bash
multica config set poll_interval 10s
multica config show
```

支援的鍵：

| 鍵 | 預設值 | 說明 |
|---|---|---|
| `server_url` | `ws://localhost:8080/ws` | Multica API / WebSocket 位址 |
| `app_url` | 空 | 瀏覽器登入使用的 Web 位址 |
| `workspace_id` | 空 | 預設工作區 |
| `device_name` | 主機名稱 | 執行環境列表中的裝置名 |
| `runtime_name` | `Local Agent` | 執行環境顯示名 |
| `workspaces_root` | `~` 下按 profile 區分的路徑 | 執行工作目錄的根目錄 |
| `max_concurrent_tasks` | `20` | 同時執行數上限；`0` 或留空表示未設定 |
| `poll_interval` | `30s` | 執行輪詢間隔 |
| `ws_claim_poll_interval` | `3m` | 健康 WebSocket 下 claim 安全輪詢的上限，與 `poll_interval` 獨立設定；Daemon 會應用向下抖動 |
| `heartbeat_interval` | `15s` | 心跳間隔 |
| `agent_timeout` | 不限制 | 單次執行的絕對時限 |
| `codex_semantic_inactivity_timeout` | 派生 | Codex 語意靜默門檻。未設定時取 idle 與 tool watchdog 預算中較大的那個；tool 預算為 `0` 時回落到 idle 預算；只有整套 watchdog 關閉時才保留 Codex 自己的 `10m` |
| `codex_handshake_timeout` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 啟動握手上限；明確設定後會統一覆蓋兩類預算 |
| `disable_auto_update` | 跟隨環境 | `true` 關閉自動更新；`false` 清除本機覆蓋，回到環境變數或預設 |
| `auto_update_check_interval` | `6h` | 檢查更新的間隔 |
| `disable_auto_reload` | 跟隨環境 | `true` 讓常駐程式不再跟隨磁碟上被替換的二進位執行檔；`false` 清除本機覆蓋。與 `disable_auto_update` 分開解析 |

幾條取值規則：

- duration 類鍵接受正的 Go duration（如 `10s`、`2h`），`0s` 和負值會被拒絕。唯一例外是 `agent_timeout`：`0s` 合法，表示明確關閉執行時限。
- 傳空字串清除已持久化的值，回到環境變數或內建預設，例如 `multica config set poll_interval ""`。
- `max_concurrent_tasks` 要求非負整數。
- 相對的 `workspaces_root` 值在儲存時會轉換為絕對路徑。

## 觀測與統計

| 變數 | 預設值 | 說明 |
|---|---|---|
| `DO_NOT_TRACK` | 空（預設開啟遙測） | 設為 `1` 或 `true`（不區分大小寫）後，停止第一方匿名自行託管遙測的收集與傳送 |
| `ANALYTICS_DISABLED` | `false` | 設為 `true` 關閉 PostHog 上報 |
| `POSTHOG_API_KEY` | 空 | 不設定時統計上報關閉；接入自己的 PostHog 專案時填寫 |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog 位址 |
| `METRICS_ADDR` | 空 | Prometheus metrics 監聽位址；空表示不啟動 |
| `REALTIME_METRICS_TOKEN` | 空 | 保護 `/health/realtime` 的 bearer token |

第一方自行託管遙測每天按 UTC 傳送一份部署級快照，固定且不可設定的位址為 `https://telemetry.multica.ai/v1/telemetry/events`。快照只包含正式發布版本、工作區數/去重成員數/活躍 Agent 數/過去 24 小時活躍常駐程式數的分桶，以及過去 24 小時執行的開始、完成、失敗和取消總數。不會傳送名稱、電子郵件或網域名稱、IP、業務識別字、主機或裝置資訊、程式碼儲存庫、模型或 plugin、prompt/output、留言或聊天、檔案路徑、token/費用、憑證、錯誤文字、stack 或日誌。此資料只用於瞭解自行託管版本採用、部署規模區間與聚合使用量，不用於計費、授權、認證或安全決策。

`DO_NOT_TRACK` 與 `ANALYTICS_DISABLED` 相互獨立：前者控制這份第一方匿名快照，後者控制可選的 PostHog 整合。

自動化用來執行反覆發生的工作，例如每天彙總進展、定期檢查依賴，或在外部系統發來事件時啟動 Agent。

每條自動化儲存一份 Runbook、一個執行方和一個或多個觸發器。觸發後，Multica 會建立任務或直接執行 Agent，並保留每一次執行記錄。

## 建立自動化

在側邊欄開啟**自動化**，選擇模板或從空白開始，然後設定：

- **名稱**：說明這條自動化負責什麼；
- **Runbook**：Agent 每次執行環境讀取的目標、背景、約束和步驟；
- **執行方**：一個 Agent 或小隊；
- **關聯專案**：可選，讓自動建立的任務進入指定專案；
- **輸出模式**：建立任務，或僅執行；
- **訂閱者**：自動建立任務後需要收到通知的成員；
- **觸發方式**：時間表或 Webhook。

儲存後自動化預設為啟用狀態；**立即執行**可隨時手動執行一次完整流程。

## 選擇輸出模式

| 模式 | 行為 | 適合 |
|---|---|---|
| **建立任務** | 每次觸發先建立一條任務，再分配給執行方；討論、狀態和執行記錄都保留在任務中。 | 需要團隊查看、確認或繼續處理的工作。 |
| **僅執行** | 直接建立執行，不產生任務；結果只在自動化的執行歷史中查看。 | 無需協作記錄的後臺執行。 |

**建立任務**模式與普通任務使用相同的執行隊列：執行環境離線時可以先建立任務，執行會等待執行環境上線。

**僅執行**要求執行環境在觸發時可用；否則本次執行會顯示為"已跳過"，不會留下一個等待中的任務。

## 按時間執行

時間表編輯器可以選擇執行時間、重複日期、時間窗口和時區，並預覽接下來的執行時間。一條自動化可以新增多個時間表；單獨啟停某個觸發器通過 CLI 的 `autopilot trigger-update` 完成，參數見 [CLI 命令](/cli)。

需要更復雜的規則時，可以直接編輯標準 5 欄位 cron：

```text
分 時 日 月 星期
```

例如：

| Cron | 時區 | 含義 |
|---|---|---|
| `0 9 * * 1-5` | `Asia/Shanghai` | 工作日 9:00 |
| `*/30 * * * *` | `UTC` | 每 30 分鐘 |
| `0 3 * * *` | `UTC` | 每天 3:00 |

Cron 不包含秒，時區使用 `Asia/Shanghai` 這樣的 IANA 名稱。儲存前，用頁面顯示的"接下來"時間核對結果。

## 通過 Webhook 執行

新增 Webhook 觸發器後，Multica 會生成一個唯一 URL。向它傳送 JSON 對象或數組，即可觸發自動化：

```bash
curl -X POST "$MULTICA_WEBHOOK_URL" \
 -H "Content-Type: application/json" \
 -H "Idempotency-Key: demo-001" \
 -d '{"event":"build.completed","eventPayload":{"status":"success"}}'
```

Payload 會儲存在投遞和執行記錄中，並交給 Agent。建立任務模式還會把事件內容附在任務描述中。

Webhook 請求的約束：

- Body 必須是有效的 JSON 對象或數組，最大 256 KiB；
- `Idempotency-Key` 可以避免傳送方重試時重複執行；GitHub 也會使用 `X-GitHub-Delivery` 去重；
- 沒有穩定冪等鍵時，Multica 無法保證重複請求只執行一次；
- 觸發器已禁用或事件不匹配時，投遞會記錄為"已忽略"，不會建立執行。

### 過濾事件

同一個來源會傳送多種事件時，可以為觸發器新增事件過濾。每行包含一個事件名，以及可選的 action 列表；任意一行命中即可執行，全部留空則接收所有事件。

例如，事件名填寫 `workflow_run`，Actions 填寫 `completed, failed`，只會接收這兩類 `workflow_run` 結果。Multica 會從常見請求頭和 payload 中識別事件與 action，包括 GitHub 的 `X-GitHub-Event` 和 body 中的 `action`。

### 保護 Webhook URL

<Callout type="warning">
Webhook URL 中的 token 就是調用憑證。不要把完整 URL 放進公開倉庫、任務或截圖。URL 洩漏後，點擊 URL 旁的**重新生成 URL**按鈕，並立即更新傳送方；舊 URL 會馬上失效。
</Callout>

只有自動化建立者、工作區 owner/admin 和獲得訪問權限的協作者可以查看完整 URL。介面預設隱藏 URL 中的 token，複製不需要先顯示；點擊 URL 或眼睛圖示可以查看完整地址。

### Webhook 響應速查

調試傳送方時，可以對照下表理解 Multica 的響應：

| HTTP 狀態 | 響應狀態 | 含義 |
|---|---|---|
| 200 | `accepted` | 已受理並建立執行，返回投遞和執行 ID。 |
| 200 | `skipped` | 已受理，但本次執行被跳過（例如僅執行模式下執行環境離線），附帶原因。 |
| 200 | `ignored` | 未建立執行：觸發器已禁用、自動化已暫停或歸檔，或事件被過濾，`reason` 欄位說明原因。 |
| 200 | `duplicate` | 冪等鍵命中已有投遞，返回原投遞 ID，不會重複執行。 |
| 400 | 錯誤資訊 | Body 為空、不是有效 JSON，或不是 JSON 對象/數組。 |
| 401 | `rejected` | 觸發器設定了簽名密鑰，但請求缺少簽名或簽名不匹配。 |
| 404 | 錯誤資訊 | URL 中的 token 無效或已被重新生成。 |
| 413 | 錯誤資訊 | Body 超過 256 KiB。 |
| 429 | 錯誤資訊 | 請求過於頻繁，按響應頭 `Retry-After` 稍後重試。 |
| 500 | 錯誤資訊 | Multica 內部錯誤，傳送方可稍後重試。 |

暫停、歸檔和事件過濾這類業務性忽略返回的是 200 而不是 4xx，避免傳送方反覆重試。

事件與 action 的推斷順序：

1. body 中帶有字符串 `event` 欄位時直接使用；
2. 否則嘗試 `X-GitHub-Event` 請求頭，它會與 body 中的 `action` 拼成 `github.<event>.<action>`；
3. 再嘗試 `X-Gitlab-Event` 請求頭；
4. 再嘗試 `X-Event-Type` 請求頭；
5. 再到 body 中的 `event`、`type`、`action` 欄位；
6. 全部缺失時記為 `webhook.received`。

## 查看執行和投遞記錄

執行歷史會顯示觸發來源、時間、狀態、關聯任務或執行，以及失敗或跳過的原因。Webhook 觸發器還會儲存單獨的投遞記錄，包括解析出的事件、響應、去重資訊和失敗原因。

處理完成的 Webhook 投遞可以從詳情中重放。重放會建立一次新的投遞和執行，不會改寫原記錄；簽名校驗失敗或仍在排隊的投遞不能重放，重放也不參與去重。

## 失敗、暫停和刪除

僅執行模式中的執行失敗後不會自動重試；下一次時間表仍會按原計劃觸發。建立任務模式產生的是普通任務執行，基礎設施故障按照[執行](/tasks#失敗與自動重試)中的規則處理。

Multica 會定期檢查近期執行是否持續失敗：過去 7 天內已完成或失敗的執行不少於 50 次且失敗率達到 90% 時，系統會暫停這條自動化並通知建立者；修復原因後可以手動恢復。

手動暫停會停止時間表、Webhook 和"立即執行"。刪除實際是歸檔：停止後續觸發，執行和投遞歷史保留。

## 管理權限

- 任何工作區成員都可以建立自動化；
- 建立者和工作區 owner/admin 可以編輯、執行、刪除及管理觸發器；
- 建立者和 owner/admin 可以把協作者加入"管理訪問"；
- 協作者可以編輯、執行和管理觸發器，但不能繼續授予其他人權限；
- 能管理自動化不代表一定能執行它使用的 Agent，Agent Access 仍然生效。

## 使用 CLI

```bash
multica autopilot get <autopilot-id> --output json
multica autopilot trigger <autopilot-id>
multica autopilot runs <autopilot-id>
multica autopilot trigger-rotate-url <autopilot-id> <trigger-id>
```

`autopilot get` 預設把 `webhook_token`、`webhook_path` 和 `webhook_url` 設為 `null`，並返回 `has_webhook_token` 與 `webhook_token_hint`。只有確實需要獲取當前有效憑證時才新增 `--show-secrets`；CLI 會把警告輸出到 stderr，確保管道中的 JSON 仍然有效。

完整參數見[使用 CLI](/cli)。

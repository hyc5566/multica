自動化適合處理重複工作，例如每日彙整進度、定期檢查相依項目，或在外部系統傳送事件時啟動 Agent。

每項自動化都會保存一份 Runbook、一個負責對象和一個以上的觸發條件。觸發後，Multica 會建立任務或直接啟動 Agent，並保存每次執行的紀錄。

## 建立自動化

在側邊欄開啟**自動化**，選擇範本或從空白開始，再設定以下項目：

- **名稱**：說明這項自動化負責的工作；
- **Runbook**：Agent 每次執行時會讀取的目標、背景、限制和步驟；
- **負責對象**：Agent 或小隊；
- **專案**：選填；自動建立的任務會加入指定專案；
- **執行模式**：建立任務，或只執行 Agent；
- **通知對象**：任務自動建立後會收到通知的成員；
- **觸發方式**：排程或 Webhook。

儲存後自動化預設為啟用；你可以隨時按**立即執行**手動跑完一次流程。

## 選擇輸出模式

| 模式 | 行為 | 適合 |
|---|---|---|
| **建立任務** | 每次觸發都先建立任務，再指派給負責對象；討論、狀態和執行紀錄都保留在任務中。 | 需要團隊檢視、確認或接續處理的工作。 |
| **只執行** | 直接建立一次執行，不建立任務；結果只會出現在自動化的執行紀錄中。 | 不需要協作紀錄的背景工作。 |

**建立任務**模式使用一般任務的執行佇列：即使執行環境離線，任務仍會建立，執行會等到環境上線。

**只執行**要求觸發時執行環境可用；否則這次執行會標示為"已略過"，也不會留下等待中的任務。

## 依排程執行

排程編輯器可設定執行時間、重複日、時間範圍和時區，並預覽接下來的執行時間。一項自動化可以設定多個排程；個別觸發條件需透過 CLI 的 `autopilot trigger-update` 啟用或停用，參數請參閱[使用 CLI](/cli)。

需要更複雜的規則時，可以直接編輯標準 5 字段 cron：

```text
分 时 日 月 星期
```

例如：

| Cron | 時區 | 含義 |
|---|---|---|
| `0 9 * * 1-5` | `Asia/Shanghai` | 工作日 9:00 |
| `*/30 * * * *` | `UTC` | 每 30 分鐘 |
| `0 3 * * *` | `UTC` | 每天 3:00 |

Cron 不包含秒數欄位，時區使用 `Asia/Shanghai` 這類 IANA 名稱。儲存前，請核對頁面顯示的"接下來的執行時間"。

## 透過 Webhook 觸發

新增 Webhook 觸發條件後，Multica 會產生唯一 URL。傳送 JSON 物件或陣列到該網址，即可觸發自動化：

```bash
curl -X POST "$MULTICA_WEBHOOK_URL" \
 -H "Content-Type: application/json" \
 -H "Idempotency-Key: demo-001" \
 -d '{"event":"build.completed","eventPayload":{"status":"success"}}'
```

Payload 會保存在傳送紀錄和執行紀錄中，並提供給 Agent。使用建立任務模式時，事件內容也會附加到任務描述。

Webhook 請求的約束：

- Body 必須是有效的 JSON 物件或陣列，大小上限為 256 KiB；
- `Idempotency-Key` 可避免傳送方重試時重複執行；GitHub 傳送事件也會依 `X-GitHub-Delivery` 去重；
- 沒有穩定的冪等鍵時，Multica 無法保證重複請求只會執行一次；
- 觸發條件已停用或事件不符時，傳送紀錄會標示為"已忽略"，也不會建立執行。

### 過濾事件

同一來源會傳送多種事件時，可以為觸發條件加入事件篩選。每一列包含一個事件名稱和選填的 action 清單；符合任一列就會觸發執行，全部留白則接受所有事件。

例如，事件名稱設為 `workflow_run`，Actions 設為 `completed, failed`，就只會接受這兩種 `workflow_run` 結果。Multica 會從常見的請求標頭和 payload 欄位辨識事件與 action，包括 GitHub 的 `X-GitHub-Event` 和 Body 中的 `action`。

### 保護 Webhook URL

<Callout type="warning">
Webhook URL 中的 token 就是呼叫憑證。請勿將完整 URL 放在公開儲存庫、任務或截圖中。若 URL 外洩，請按旁邊的**輪替 URL**按鈕，並立即更新傳送方；舊 URL 會立刻失效。
</Callout>

只有自動化建立者、工作區 `owner`／`admin` 和獲准協作管理的人可以查看完整 URL。介面預設會隱藏 URL 中的 token；複製時不必先顯示 token，點選 URL 或眼睛圖示則可查看完整網址。

### Webhook 回應速查

排查傳送方問題時，可以參照下表解讀 Multica 的回應：

| HTTP 狀態 | 回應狀態 | 意義 |
|---|---|---|
| 200 | `accepted` | 已受理並建立執行，回傳傳送紀錄和執行 ID。 |
| 200 | `skipped` | 已受理，但略過這次執行（例如只執行模式下執行環境離線）；回應會附上原因。 |
| 200 | `ignored` | 未建立執行：觸發條件已停用、自動化已暫停或封存，或事件遭篩選；`reason` 欄位會說明原因。 |
| 200 | `duplicate` | 冪等鍵符合既有傳送紀錄，會回傳原紀錄 ID，不會再次執行。 |
| 400 | 錯誤訊息 | Body 為空、不是有效 JSON，或不是 JSON 物件／陣列。 |
| 401 | `rejected` | 觸發條件設定了簽章密鑰，但請求沒有簽章或簽章不符。 |
| 404 | 錯誤訊息 | URL 中的 token 無效或已輪替。 |
| 413 | 錯誤訊息 | Body 超過 256 KiB。 |
| 429 | 錯誤訊息 | 請求過於頻繁；請依回應標頭 `Retry-After` 指示稍後重試。 |
| 500 | 錯誤訊息 | Multica 內部錯誤；傳送方可稍後重試。 |

暫停、封存和事件篩選等業務性忽略會回傳 200，而非 4xx，以免傳送方不斷重試。

事件和 action 的判定順序如下：

1. 如果 Body 中有字串型別的 `event` 欄位，就直接使用；
2. 否則使用 `X-GitHub-Event` 請求標頭，並與 Body 中的 `action` 組成 `github.<event>.<action>`；
3. 接著檢查 `X-Gitlab-Event` 請求標頭；
4. 再檢查 `X-Event-Type` 請求標頭；
5. 最後檢查 Body 中的 `event`、`type` 和 `action` 欄位；
6. 若都沒有值，則記錄為 `webhook.received`。

## 查看執行和傳送紀錄

執行紀錄會顯示觸發來源、時間、狀態、關聯任務或執行，以及失敗或略過原因。Webhook 觸發條件也會另存傳送紀錄，包括解析出的事件、回應、去重資訊和失敗原因。

已處理完成的 Webhook 傳送可以從詳細資訊頁重新播放。重新播放會建立新的傳送紀錄和執行，不會改寫原紀錄；簽章驗證失敗或仍在佇列中的傳送無法重新播放，重新播放也不會參與去重。

## 失敗、暫停和刪除

只執行模式下的執行失敗後不會自動重試；下一次排程仍會照常觸發。建立任務模式產生的是一般任務執行，基礎架構故障則依照[執行](/tasks#失敗與自動重試)中的規則處理。

Multica 會定期檢查近期執行是否持續失敗：過去 7 天內至少有 50 次已完成或失敗的執行，且失敗率達到 90% 時，系統會暫停這項自動化並通知建立者。修正問題後可以手動恢復。

手動暫停會停止排程、Webhook 和**立即執行**。刪除實際上會封存自動化：停止後續觸發，但保留執行和傳送紀錄。

## 管理權限

- 任何工作區成員都可以建立自動化；
- 建立者和工作區 `owner`／`admin` 可以編輯、執行、刪除及管理觸發條件；
- 建立者和 `owner`／`admin` 可以授予協作者管理權限；
- 協作者可以編輯、執行和管理觸發條件，但不能再授權給其他人；
- 有權管理自動化不代表一定有權執行其中的 Agent，Agent 的 Access 設定仍然適用。

## 使用 CLI

```bash
multica autopilot get <autopilot-id> --output json
multica autopilot trigger <autopilot-id>
multica autopilot runs <autopilot-id>
multica autopilot trigger-rotate-url <autopilot-id> <trigger-id>
```

`autopilot get` 預設會將 `webhook_token`、`webhook_path` 和 `webhook_url` 設為 `null`，並回傳 `has_webhook_token` 和 `webhook_token_hint`。只有確實需要目前有效的憑證時才加上 `--show-secrets`；CLI 會將警告輸出到 stderr，確保管線中的 JSON 仍有效。

完整參數見[使用 CLI](/cli)。

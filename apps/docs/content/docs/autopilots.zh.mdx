每天彙總進展、定期檢查依賴、外部系統發來事件時啟動Agent，這類反覆發生的工作交給自動化。

每條自動化儲存一份 Runbook、一個執行方和一個或多個觸發器。觸發後，Multica 建立任務或直接執行Agent，每一次執行都留有記錄。

## 自動化還是任務喚醒 [#vs-wakeups]

自動化按時間表或 Webhook 開始新的工作，每次可以新建一條任務。如果是想讓Agent在某個時間、或者等任務上發生某件事之後，回到一條已有的任務接著做，就給那條任務加[喚醒](/issue-wakeups)。自動化頁面的**任務喚醒**標籤列出整個工作區的喚醒。

## 建立自動化

在側邊欄開啟**自動化**，選擇範本或從空白開始，再設定以下項目：

- **名稱**：說明這項自動化負責的工作；
- **Runbook**：Agent 每次執行時會讀取的目標、背景、限制和步驟；
- **負責對象**：Agent 或小隊；
- **專案**：選填；自動建立的任務會加入指定專案；
- **執行模式**：建立任務，或只執行 Agent；
- **通知對象**：任務自動建立後會收到通知的成員；
- **觸發方式**：排程或 Webhook。

儲存後自動化預設啟用。**立即執行**隨時手動執行一次完整流程，不用等時間表。

下面是一條輸出模式為"建立任務"的自動化。點**立即執行**，或者快進到下次runtime間，看它建立任務、交給Agent，再到這次執行完成。

## 選擇輸出模式

| 模式 | 行為 | 適合 |
|---|---|---|
| **建立任務** | 每次觸發都先建立任務，再指派給負責對象；討論、狀態和執行紀錄都保留在任務中。 | 需要團隊檢視、確認或接續處理的工作。 |
| **只執行** | 直接建立一次執行，不建立任務；結果只會出現在自動化的執行紀錄中。 | 不需要協作紀錄的背景工作。 |

**建立任務**模式和普通任務用同一個執行佇列：runtime離線時照樣先建立任務，執行等runtime上線後開始。

**只執行**要求觸發時執行環境可用；否則這次執行會標示為"已略過"，也不會留下等待中的任務。

## 依排程執行

時間表編輯器可以選擇執行環境間、重復日期、時間窗口和時區，並預覽接下來的執行環境間。一條自動化可以添加多個時間表；要修改或單獨啓停某個觸發器，點「觸發器」中該行的編輯按鈕，或用 CLI 的 `autopilot trigger-update`，參數見 [CLI 命令](/cli)。

規則更復雜時，直接編輯標準 5 欄位 cron：

```text
分 时 日 月 星期
```

例如：

| Cron | 時區 | 含義 |
|---|---|---|
| `0 9 * * 1-5` | `Asia/Shanghai` | 工作日 9:00 |
| `*/30 * * * *` | `UTC` | 每 30 分鐘 |
| `0 3 * * *` | `UTC` | 每天 3:00 |

Cron 不包含秒數欄位，時區使用 `Asia/Shanghai` 這類 IANA 名稱。儲存前，請核對頁面顯示的"接下來的執行時間"。

## 透過 Webhook 觸發

新增 Webhook 觸發條件後，Multica 會產生唯一 URL。傳送 JSON 物件或陣列到該網址，即可觸發自動化：

```bash
curl -X POST "$MULTICA_WEBHOOK_URL" \
 -H "Content-Type: application/json" \
 -H "Idempotency-Key: demo-001" \
 -d '{"event":"build.completed","eventPayload":{"status":"success"}}'
```

Payload 會保存在傳送紀錄和執行紀錄中，並提供給 Agent。使用建立任務模式時，事件內容也會附加到任務描述。

Webhook 請求的約束：

- Body 必須是有效的 JSON 物件或陣列，大小上限為 256 KiB；
- `Idempotency-Key` 可避免傳送方重試時重複執行；GitHub 傳送事件也會依 `X-GitHub-Delivery` 去重；
- 沒有穩定的冪等鍵時，Multica 無法保證重複請求只會執行一次；
- 觸發條件已停用或事件不符時，傳送紀錄會標示為"已忽略"，也不會建立執行。

### 過濾事件 [#事件過濾]

同一個來源會發送多種事件時，給觸發器加上事件過濾。點 **添加規則**，填一個事件名，加可選的 action 列表；任意一條規則命中就運行，沒有規則則接收所有事件。要編輯某個 Webhook 的過濾，點「觸發器」中該行的 **編輯 Webhook**。

例如，事件名稱設為 `workflow_run`，Actions 設為 `completed, failed`，就只會接受這兩種 `workflow_run` 結果。Multica 會從常見的請求標頭和 payload 欄位辨識事件與 action，包括 GitHub 的 `X-GitHub-Event` 和 Body 中的 `action`。

GitLab 的事件名就是 GitLab 發送的 `X-Gitlab-Event` 請求頭原值，例如 `Merge Request Hook`、`Issue Hook`、`Note Hook`，空格和大小寫都要一致；payload 里的 `object_kind`（`merge_request`）不會命中。Actions 中的每個值會同時與 `object_attributes.action` 和 `object_attributes.state` 比較，任意一個相等即命中。下面這條規則接收新建、更新和重新打開的 merge request，忽略合併和關閉：

```json
{ "event": "Merge Request Hook", "actions": ["open", "update", "reopen"] }
```

Actions 請填寫動作詞（`open`、`update`、`reopen`、`merge`、`close`），不要填寫狀態詞（`opened`、`merged`、`closed`）。匹配是精確比較，兩種寫法之間不會互相轉換；狀態詞會命中所有讓對象處於該狀態的事件。向打開的 merge request 推送提交會發送 `"action": "update"` 和 `"state": "opened"`，批准會發送 `"action": "approval"` 和同樣的狀態，所以填寫 `opened` 時，這些事件和新建 merge request 一樣都會啓動運行。

- `Issue Hook` 加 `close`：接收被關閉的 issue。
- `Note Hook` 加 `create`：接收新評論；編輯評論發送的是 `update`。
- GitLab 規則的 Actions 留空時，接收該事件名下的所有事件。
- 只在失敗時運行，可以將 **Actions** 設為 `failed`，事件名填寫 `Pipeline Hook`（`object_kind: "pipeline"`，狀態讀取 `object_attributes.status`）或 `Job Hook`（`object_kind: "build"`，狀態讀取 `build_status`）。`success`、`running` 等其他狀態會被過濾；Actions 留空則接收該事件的所有狀態。這兩個 CI 狀態欄位僅用於各自的對象類型，參見 [GitLab 事件 payload](https://docs.gitlab.com/user/project/integrations/webhook_events/#pipeline-events)。

每條規則還可以設置針對 payload 欄位的 `conditions`：點選該規則的 **添加條件**，或通過 API 設置。所有條件都滿足時該規則才命中；被過濾的事件在任何運行開始前就會被忽略。`path` 用點號訪問 payload，數字表示數組下標，`*` 表示任意元素（`pull_request.labels.*.name`）。`op` 可選 `equals`、`not_equals`、`contains`、`in` 或 `exists`，`ignore_case` 作用於文本。使用 `*` 時，`equals`、`contains`、`in` 和 `exists` 只要有一個元素匹配即成立，`not_equals` 要求沒有任何元素匹配。欄位不存在時永遠不命中，`exists` 會忽略 `null`。例如，下面這條規則只接收已就緒、帶有 `needs-review` 標籤、目標分支為 `main` 或 `release`、且不是由機器人建立的 pull request：

```json
{
  "event": "pull_request",
  "actions": ["opened", "synchronize"],
  "conditions": [
    { "path": "pull_request.draft", "op": "equals", "value": false },
    { "path": "pull_request.labels.*.name", "op": "equals", "value": "needs-review" },
    { "path": "pull_request.base.ref", "op": "in", "values": ["main", "release"] },
    { "path": "sender.type", "op": "not_equals", "value": "Bot" }
  ]
}
```

每條規則最多 20 個條件，欄位路徑最多 256 個字符，`in` 候選值列表最多 100 項。建立或更新觸發器時，超出上限的條件會返回 HTTP 400。

`*` 展開空數組時，`not_equals` 成立；路徑不存在時仍不命中。事件或動作不匹配記為 `event_filtered`，事件匹配但正文條件不滿足記為 `payload_filtered`。兩者都返回 HTTP 200，不建立運行或任務。投遞列表顯示原因和第一個不滿足條件的欄位，詳情顯示接收時保存的條件及實際值。之後修改規則不會改變這份記錄。預覽最多顯示 10 個值，每個值最多 256 個字符；完整值見原始正文。

也可以通過 CLI 的 `--event-filters-file` 完整設定這些條件。更新時不傳過濾參數就保留原值；`--clear-event-filters` 明確清空條件、恢復接收所有事件。JSON 格式和命令見 [CLI 示例](/cli#webhook-event-filters)。

### 保護 Webhook URL

<Callout type="warning">
Webhook URL 中的 token 就是呼叫憑證。請勿將完整 URL 放在公開儲存庫、任務或截圖中。若 URL 外洩，請按旁邊的**輪替 URL**按鈕，並立即更新傳送方；舊 URL 會立刻失效。
</Callout>

只有自動化建立者、工作區 `owner`／`admin` 和獲准協作管理的人可以查看完整 URL。介面預設會隱藏 URL 中的 token；複製時不必先顯示 token，點選 URL 或眼睛圖示則可查看完整網址。

### Webhook 回應速查

除錯傳送方時，對照下表看 Multica 的響應：

| HTTP 狀態 | 回應狀態 | 意義 |
|---|---|---|
| 200 | `accepted` | 已受理並建立執行，回傳傳送紀錄和執行 ID。 |
| 200 | `skipped` | 已受理，但略過這次執行（例如只執行模式下執行環境離線）；回應會附上原因。 |
| 200 | `ignored` | 未建立執行：觸發條件已停用、自動化已暫停或封存，或事件遭篩選；`reason` 欄位會說明原因。 |
| 200 | `duplicate` | 冪等鍵符合既有傳送紀錄，會回傳原紀錄 ID，不會再次執行。 |
| 400 | 錯誤訊息 | Body 為空、不是有效 JSON，或不是 JSON 物件／陣列。 |
| 401 | `rejected` | 觸發條件設定了簽章密鑰，但請求沒有簽章或簽章不符。 |
| 404 | 錯誤訊息 | URL 中的 token 無效或已輪替。 |
| 413 | 錯誤訊息 | Body 超過 256 KiB。 |
| 429 | 錯誤訊息 | 請求過於頻繁；請依回應標頭 `Retry-After` 指示稍後重試。 |
| 500 | 錯誤訊息 | Multica 內部錯誤；傳送方可稍後重試。 |

暫停、歸檔、事件過濾這類業務上的忽略返回 200，不返回 4xx，以免傳送方反覆重試。

事件和 action 的判定順序如下：

1. 如果 Body 中有字串型別的 `event` 欄位，就直接使用；
2. 否則使用 `X-GitHub-Event` 請求標頭，並與 Body 中的 `action` 組成 `github.<event>.<action>`；
3. 接著檢查 `X-Gitlab-Event` 請求標頭；
4. 再檢查 `X-Event-Type` 請求標頭；
5. 最後檢查 Body 中的 `event`、`type` 和 `action` 欄位；
6. 若都沒有值，則記錄為 `webhook.received`。

## 查看執行和傳送紀錄

執行紀錄會顯示觸發來源、時間、狀態、關聯任務或執行，以及失敗或略過原因。Webhook 觸發條件也會另存傳送紀錄，包括解析出的事件、回應、去重資訊和失敗原因。

已處理完成的 Webhook 傳送可以從詳細資訊頁重新播放。重新播放會建立新的傳送紀錄和執行，不會改寫原紀錄；簽章驗證失敗或仍在佇列中的傳送無法重新播放，重新播放也不會參與去重。

## 失敗、暫停和刪除

只執行模式下的執行失敗後不會自動重試；下一次排程仍會照常觸發。建立任務模式產生的是一般任務執行，基礎架構故障則依照[執行](/tasks#失敗與自動重試)中的規則處理。

Multica 定期檢查近期執行是否持續失敗：過去 7 天內已完成或失敗的執行不少於 50 次、且失敗率達到 90% 時，系統暫停這條自動化並通知建立者，修復原因後可以手動恢復。

手動暫停會停止排程、Webhook 和**立即執行**。刪除實際上會封存自動化：停止後續觸發，但保留執行和傳送紀錄。

## 管理權限

- `owner`、`admin` 和 `member` 都可以建立自動化。
- 建立者和工作區 owner/admin 可以編輯、運行、刪除及管理觸發器；
- 建立者和 owner/admin 可以把協作者加入"管理訪問"；
- 協作者可以編輯、運行和管理觸發器，但不能繼續授予其他人權限；
- 能管理自動化不代表一定能運行它使用的Agent，Agent Access 仍然生效。

## 使用 CLI

```bash
multica autopilot get <autopilot-id> --output json
multica autopilot trigger <autopilot-id>
multica autopilot runs <autopilot-id>
multica autopilot trigger-rotate-url <autopilot-id> <trigger-id>
```

`autopilot get` 預設把 `webhook_token`、`webhook_path` 和 `webhook_url` 設為 `null`，並返回 `has_webhook_token` 與 `webhook_token_hint`。確實需要拿到當前有效憑證時才加 `--show-secrets`；CLI 把警告輸出到 stderr，管道中的 JSON 不受影響。

完整參數見[使用 CLI](/cli)。

先確認問題發生在哪一層：Multica 服務、常駐程式、執行環境，還是 AI 程式開發工具。下面幾條命令通常足以找到第一個有意義的錯誤：

```bash
multica version
multica auth status
multica daemon status --output json
multica daemon logs --lines 100
```

自行託管實例還可以直接檢查服務：

```bash
curl -i https://api.example.com/health
curl -i https://api.example.com/readyz
```

`/health` 只表示 API 程序能回應；`/readyz` 還會檢查資料庫和 migration。回報問題時，請附上錯誤訊息、相關日誌、CLI 版本和作業系統，並在提交前移除權杖、電子郵件地址等敏感資訊。

## 常駐程式連線失敗

先執行：

```bash
multica auth status
multica daemon status --output json
multica daemon logs --lines 100
```

常見原因包括：

- CLI 尚未登入，或本機儲存的權杖已經失效；
- 常駐程式連線了錯誤的 Multica 服務；
- 執行電腦無法存取 API，或 DNS、TLS、防火牆攔截了連線；
- 目前帳號已經不在目標工作區中；
- 本機沒有安裝任何受支援的 AI 程式開發工具，常駐程式因此無法啟動。

重新登入並重新啟動常駐程式：

```bash
multica login
multica daemon restart
```

自行託管部署還需要從**執行電腦**請求 API 的 `/health`——伺服器本機測試無法暴露執行電腦側的 DNS、TLS 或防火牆問題。需要修改位址時，重新執行 `multica setup self-host`，或檢查目前 profile 的 `server_url`：

```bash
multica config show
```

## 任務未開始執行

開啟任務的**執行日誌**，先看執行的目前狀態和等待原因。

### `queued` 狀態

`queued` 表示執行還在等待執行環境領取。依次檢查：

1. Agent 綁定的執行環境是否在線；
2. 執行環境是否偵測到了該 Agent 設定的 AI 程式開發工具；
3. Agent 的同時執行數是否尚未達到上限；
4. 常駐程式是否還有全域執行容量。

Agent 預設最多允許 6 個執行同時進行；單一常駐程式的預設上限是 20 個。達到上限時，新的執行會留在佇列，等前面的執行結束。執行環境離線時也會繼續排隊；只有環境停止回報心跳的時間超過重新連線寬限期，而且該執行本身也已等待這麼久，才會判定失敗。因此，忙碌環境中的長佇列不會只因等待過久而失敗；指派給已離線的機器時，也仍有一個完整寬限期可讓機器重新上線。

```bash
multica daemon status --output json
multica agent get <agent-id>
multica issue runs <issue-id>
```

如果執行環境列表缺少預期工具，先在同一個系統帳號和 `PATH` 中確認工具可以執行並且已經登入，再執行 `multica daemon restart`。

### `waiting_local_directory` 狀態

這表示另一次進行中的執行正在使用同一個本機目錄。Multica 會等待目錄鎖釋放，避免兩個 Agent 同時修改同一份檔案。

這種等待只存在於目錄的 `in_place`（"原地"）模式。如果這個目錄是 git 儲存庫，把資源切到 `worktree`（"並行"）就沒有佇列了：每次執行拿到自己的 worktree，並以分支形式交回結果，誰都不用等誰。見[專案資源](/project-resources#執行如何共用這個目錄)。

否則通常只需等前一次執行結束。若前一次已經卡住，可以從它的執行日誌中停止；也可以為目前 Agent 選擇其他本機目錄。這個目錄互斥由常駐程式在記憶體中維護，不寫磁碟鎖檔案；懷疑鎖狀態異常時執行 `multica daemon restart` 即可釋放，沒有需要手動刪除的檔案。

## AI 程式開發工具啟動失敗

常駐程式在線不代表工具本身可用。開啟這次執行的詳細記錄，重點檢查：

- 工具是否已經完成登入；
- API key、額度或模型權限是否可用；
- Agent 選擇的模型和思考強度是否被該工具支援；
- 本機工作目錄是否存在並且可寫；
- Agent 的自訂參數或環境變數是否有效。

先在執行電腦的終端機中直接執行同一款工具。工具自身也無法開始時，先修復工具登入或設定，再從執行日誌重試執行。

## 升級 CLI 後 macOS 上的執行卡住

透過 Homebrew 安裝的 `multica` CLI 升級後（無論是 `brew upgrade`、`multica update`、**執行環境**頁面上的**更新**，還是常駐程式自動更新），讀取 `~/Desktop`、`~/Documents`、`~/Downloads`、iCloud 雲端硬碟或其他受保護資料夾的執行可能停滯：Agent 程序不佔用 CPU，執行既不結束也不失敗。

這種情況出現在 macOS 把隱私權限（TCC）記在常駐程式本身名下時，由 launchd 啟動的常駐程式（例如 LaunchAgent）就是如此：等待中的對話框顯示的是 `multica`，Agent 啟動的所有工具都沿用常駐程式的授權。Homebrew 版 CLI 沒有使用固定身分簽章，macOS 只能把授權綁定到這一次建置及其解析後的路徑，例如 `/opt/homebrew/Cellar/multica/<version>/bin/multica`。升級後，macOS 把新二進位執行檔當作另一個應用，重新請求授權；在有人處理之前檔案存取會一直阻塞，常駐程式也無法感知有授權對話框在等待。

恢復存取權：

1. 在這台 Mac 上找到等待中的"想要存取"對話框，點選**允許**，卡住的執行會繼續。
2. 無人值守的 Mac 請給新二進位執行檔授予完整磁碟存取權。用 `realpath "$(command -v multica)"` 印出路徑，然後在**系統設定 → 隱私與安全性 → 完整磁碟存取權**中刪除舊的 `multica` 項目並新增該路徑（在檔案選擇器中按 ⌘⇧G 貼上路徑）。
3. 按啟動常駐程式時的方式重新啟動它：`multica daemon restart`；LaunchAgent 則用 `launchctl kickstart -k gui/$(id -u)/<label>`。

每次升級 CLI 後都需要重複這些步驟。只有連線 Multica Cloud 的常駐程式預設開啟自動更新；用 `--no-auto-update` 啟動常駐程式後，只在你手動升級時更新。[桌面應用](/desktop-app)內建的官方 CLI 使用 Developer ID 簽章，授權在升級後依然有效。繁中客製 App 的簽章方式則依實際成品而定，不能套用這項假設；請參閱[繁中版安裝與驗收](https://github.com/hyc5566/multica/blob/zh-tw/docs/lan-installation.zh-tw.md)。

## 即時更新失效

工作仍能執行，但留言和狀態無法即時顯示時，通常是 WebSocket 未連線。

在瀏覽器開發者工具的 **Network → WS** 中查看 `/ws` 連線。自行託管部署重點檢查：

- `FRONTEND_ORIGIN` 是否和瀏覽器實際開啟的位址一致；
- HTTPS 頁面是否透過 `wss://` 連線；
- 反向代理是否轉發 WebSocket 的 Upgrade 請求；
- 瀏覽器登入是否已經過期。

直接用 `curl` 存取 `/ws` 回傳 HTTP 400 是正常現象：該端點要求帶 workspace 相關的查詢參數，裸握手在進入 WebSocket 升級之前就會被拒。所以 backend 日誌裡出現 400/401 記錄，只能說明普通 HTTP 路由已經到達 backend——並不能證明代理保留了 WebSocket `Upgrade` 標頭。要驗證真正的連線，請開啟瀏覽器開發者工具的 Network → WS 面板（或用支援 WebSocket 的用戶端），看是否出現 `101` 握手。

自行部署注意：daemon 的長連線撥的是 `/api/daemon/ws`（不是 `/ws`），同樣要直通後端；握手失敗時 daemon 會靜默回退到輪詢，backend 日誌裡該路徑反覆出現 `status=400` 便是這類問題的徵兆。

容器只在建立時讀取 `.env`，修改後需要重新建立：

```bash
docker compose -f docker-compose.selfhost.yml up -d
```

完整的反向代理範例見[自行託管快速上手](/self-host-quickstart#3-選擇存取方式)。

## `multica setup` 報告伺服器不可達

CLI 的可達性探測會 GET `<server-url>/health` 並要求 200。backend 提供這個路徑。新版 web 前端會把 `/health` 轉發給 backend，舊版不會——把所有流量都轉給舊版 frontend 的反向代理會回傳 404，於是 CLI 誤判服務不可用，而服務實際是健康的。

在代理裡把 `/health` 明確轉交 backend（8080 連接埠），對所有版本都適用——[自行託管快速上手](/self-host-quickstart#3-選擇存取方式)裡的兩個 Caddy 範例都包含這條。確認方法：

```bash
curl -fsS <server-url>/health
```

## `multica login` 報告 TLS 握手逾時

`multica login` 能開啟瀏覽器、網頁登入也能完成，但 CLI 仍以 "Sign-in did not complete" 或 "TLS 握手逾時" 失敗。`multica --debug login` 在 `POST /api/tokens` 上顯示 `net/http: TLS handshake timeout`，而同一台機器上的 `curl.exe -I https://api.multica.ai` 或瀏覽器都能正常連線。

TCP 連線已建立，但 TLS 握手始終沒有完成。Go 用戶端（包括 Multica CLI 和常駐程式）預設在 TLS ClientHello 中攜帶後量子金鑰交換，訊息約 1.5 KB，會拆成兩個封包傳送。部分安全軟體、VPN、路由器和防火牆會丟棄這種握手；curl 的 ClientHello 小得多，所以能通過。

先關閉後量子金鑰交換重試，確認是否為此原因：

```powershell
$env:GODEBUG = 'tlsmlkem=0'
multica --debug login
```

```bash
GODEBUG=tlsmlkem=0 multica --debug login
```

如果這樣能成功，請為執行 CLI 和常駐程式的使用者永久設定 `GODEBUG=tlsmlkem=0`——Windows 上執行 `[Environment]::SetEnvironmentVariable('GODEBUG', 'tlsmlkem=0', 'User')` 後重新開啟終端機——然後重新啟動常駐程式或桌面應用。調高 `MULTICA_HTTP_TIMEOUT` 無效，它不控制握手。根本解決需要在網路側處理：升級或重新設定丟棄分段 TLS 握手的裝置或軟體。

## 驗證碼與邀請電子郵件未送達

先查看 backend 啟動日誌。日誌會說明目前使用 `SMTP relay`、`Resend API` 還是 `DEV mode`：

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
 | grep "EmailService:"
```

- **DEV mode**：電子郵件不會發出，驗證碼和邀請連結只寫入 backend 日誌；
- **Resend**：確認 API key 有效，且寄件地址的網域名稱已經驗證；
- **SMTP**：確認主機、連接埠、憑證和寄件地址，並從錯誤日誌判斷失敗發生在連線、TLS、認證還是投遞階段。

`SMTP_HOST` 和 Resend 同時設定時，Multica 會優先使用 SMTP。設定方式見[登入與註冊](/auth-setup#電子郵件驗證碼)。

<Callout type="warning">
正式環境不要依賴日誌中的驗證碼，也不要啟用固定本機測試驗證碼。
</Callout>

## 附件上傳或下載失敗

先檢查 backend 日誌和回應狀態碼。常見原因是：

- 反向代理限制了請求主體大小；
- 本機上傳目錄不可寫或沒有掛載持久化磁碟區；
- S3 bucket、region、endpoint 或憑證不匹配；
- 下載位址經過代理後使用了錯誤的公開網域名稱或協議。

使用 Docker Compose 時，預設的 `backend_uploads` volume 儲存本機附件。重建容器不會刪除它，但 `docker compose down -v` 會刪除資料磁碟區。S3 相關設定見[環境變數](/environment-variables#附件儲存)。

## 用量（Usage）為 0

Usage 頁面讀取按小時匯總的資料，不直接讀取每次執行的原始用量。先確認原始資料和匯總表：

```sql
SELECT count(*) FROM task_usage;
SELECT count(*) FROM task_usage_hourly;

SELECT plan_time, status, error_code, error_msg
FROM sys_cron_executions
WHERE job_name = 'rollup_task_usage_hourly'
ORDER BY plan_time DESC
LIMIT 20;
```

如果 `task_usage` 有資料、匯總表為空，並且排程記錄顯示失敗，先確認 migration 已經全部套用；升級被 migration 103 拒絕執行的情況見下一節。也可以手動執行一次匯總來區分 SQL 和排程問題：

```sql
SELECT rollup_task_usage_hourly();
```

手動執行後數字正常，說明匯總函式可用，問題在 backend 的定時排程；手動 SQL 只補一次匯總，不會恢復排程。按小時匯總由 backend 內建排程執行，不需要自行設定 pg_cron。

## 升級時 migration 103 拒絕執行

正常升級不需要為 103 做任何事：`migrate up` 在套用它之前會自動回填歷史用量資料——空資料庫直接通過，有歷史資料的實例自動按月補齊後繼續。

如果 backend 啟動仍報 `refusing to drop legacy daily rollups`，說明自動回填沒有完成（例如回填中途失敗，或沒有透過 `migrate up` 而是直接執行了 SQL）。此時手動執行回填命令，完成後重新啟動 backend：

```bash
cd server
DATABASE_URL='postgres://...' go run ./cmd/backfill_task_usage_hourly
```

常用 flag：`--dry-run` 只預覽不寫入；`--sleep-between-slices` 在切片之間加間隔，降低對繁忙實例的讀壓。命令按月切片、冪等，中斷後可以直接重跑；它持有 advisory lock，與伺服器端的定時匯總互斥，不會產生重複或不一致的匯總資料。完成後重新啟動 backend，用 `/readyz` 確認 `migrations` 為 `ok`。

## 連接埠佔用

本機常用連接埠包括 API 的 `8080`、Web 的 `3000` 和常駐程式健康檢查連接埠。先找出佔用者：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN # macOS / Linux
netstat -ano | findstr :8080 # Windows
```

如果它是另一個 Multica checkout，先在那個目錄執行 `make stop`。否則正常停止佔用連接埠的程序，或修改目前服務連接埠。公網 80/443 由 Caddy、Nginx 等反向代理監聽。

## 日誌位置

| 元件 | 查看方式 |
| --- | --- |
| 背景常駐程式 | `multica daemon logs --lines 100` |
| 即時跟隨常駐程式日誌 | `multica daemon logs --follow` |
| 預設 profile 的日誌檔 | `~/.multica/daemon.log` |
| 預設 profile 的啟動或崩潰日誌 | `~/.multica/daemon.err.log` |
| 命名 profile | `~/.multica/profiles/<name>/` 下的對應日誌 |
| Docker backend | `docker compose -f docker-compose.selfhost.yml logs -f backend` |
| 瀏覽器 | 開發者工具中的 Console 和 Network |

哪個檔案是目前活躍的日誌，取決於常駐程式啟動時使用的 profile；早前常駐程式殘留的舊日誌同樣能正常讀出來，最容易讓人查錯檔案。不要靠猜去開檔案：`multica daemon logs` 會在輸出日誌內容前先印出它解析到的絕對路徑。讀命名 profile 的日誌時加上 `--profile <name>`。

需要直接觀察常駐程式啟動過程時，可以改為前景執行：

```bash
multica daemon stop
multica daemon start --foreground
```

仍然無法定位時，到 [GitHub issue](https://github.com/multica-ai/multica/issues) 搜尋已有問題或提交新的 issue。
